# Plan: RFC 0020 Kernel (kernel-v8)

RFC 0020 is accepted. It defines the kernel: `Int`, `Bool`, `Text`, bindings, functions, `io`, `if`, `while`, `return`, examples, four traps, and `print`. Subtasks 1 to 5 need only the toolkit and can be built and tested now. Everything from subtask 6 on needs the lexer and the diagnostic, CLI and spec files from RFC 0004, RFC 0011 and RFC 0014, and none of those exist in this checkout (`compiler/stage0/` is absent, and so are `spec/`, `conformance/` and `spec/errors.json`).

## Prerequisites outside this plan

- RFC 0014 lexer. Subtasks 6 to 8 need `compiler/stage0/src/lexer/token.ts` (`Kind`, `Token`) and `lexer/index.ts` (`lex`). These come from `rfcs/0014.plan.md` subtasks 2 and 9, and so do the lexer's dependencies. If a file is missing when you reach a subtask, stop there and report it. Do not create a stand-in.
- RFC 0004 diagnostics. Subtasks 6 to 14 emit records through `diagnostic.ts` and `toJsonLine`, use `span.ts`, and add catalogue entries to `spec/errors.json`. They come from `rfcs/0004.plan.md` subtasks 1, 2, 4, 5 and 8.
- RFC 0011 CLI. Subtasks 16 to 18 need `cli.ts` and the source-file rule from `rfcs/0011.plan.md` subtasks 3 and 4.
- Spec layout. Subtask 25 (spec core and card) needs `spec/` from RFC 0004 subtask 8. Subtask 26 (`spec/grammar.peg`) needs `spec/` too.
- Gate baseline. `bin/glyphc` runs `compiler/stage0/src/main.ts`, which does not exist yet. Until the prerequisites land, the gate fails for reasons outside this plan. Say so in the PR body; do not work around it.
- Relation to RFC 0014's plan. `rfcs/0014.plan.md` subtasks 13 to 15 are blocked on "an accepted kernel". This plan supplies one. When it lands, the architect should decide whether to re-plan those subtasks against RFC 0020. The run tests `lex/*` in RFC 0014 are written in RFC 0014's own form, so they can be checked against the grammar here.

## Conflicts and decisions

- Runner, run tests. `tools/check/conformance.py` checks only stdout and exit for the `run` kind. RFC 0020 says a run test states stderr too, so for a `run` test the stderr check is not enforced. Decision: write run tests in the runner's form (`expect-stdout`, `expect-exit`), and put no stderr claim in them. The trap tests use the `trap` kind, which checks exit and an `expect-stderr` substring, as RFC 0020 requires.
- Runner, trap tests. The `trap` kind does not check stdout. `trap-step` expects stdout `before`, and that is not checked. Decision: write the test with the RFC's program, leave the stdout claim out of the test file, and note it in the PR body. Ask the architect to add an `expect-stdout` check to the `trap` kind.
- Runner, compile-error tests. The `compile-error` kind compares only (code, line) and uses `check --json`. RFC 0020 section 7 (RFC 0004) wants code, span and fix. Decision: write compile-error tests in the runner's form now, since (code, line) is checkable, and say in each PR body that span and fix are not compared. This differs from RFC 0014's plan, which waits for the runner. Reopen it with the architect before the batch in subtask 23 if they prefer the wait.
- Trap test typo. The RFC's `trap-step` row reads `while true { } }` with a stray brace. Write it as `while true { }` inside `main`. The architect should fix the RFC text.
- Examples and the execution caps. `governance/RULES.md` gives `fuel: 10000000000` for the gate. `err-example-budget` runs TR3's 1000000000 steps. A loop iteration takes several wasm instructions, so the fuel cap can run out before the step limit. Then the example reports fuel exhaustion, not `step-exhausted`, and the run does not match E0202's message. The toolkit's Node fallback also has a 10 s timeout and no fuel limit, so the same test can exit 124 there. Decision: subtask 19 maps fuel exhaustion and exit 124 to a failed example with a message that says so, and does not invent a trap. The architect must decide whether TR3's limit or the fuel cap changes. Do not edit `toolkit/` or `governance/`.
- Leading zero. RFC 0014 rule 8 gives `007` E0006. RFC 0004's `diag/fix-present.test` expects E0001. The kernel tests do not use leading zeros, so this plan does not decide it.
- Catalogue first emission. RFC 0014's plan says a catalogue entry is added by the PR that first emits its code. This plan therefore adds E0003, E0100 and E0500 in the parser subtasks (6 to 8), and E0200 to E0202, E0300 to E0303 and E0400 in the checker subtasks (9 to 13). RFC 0014's open question 3 (where E0003 sits) is still open, and it decides which block E0003 belongs to. Resolve it before subtask 8.
- RFC 0020 status. The frontmatter says `accepted`, and the body says `Status: draft`. This plan treats it as accepted, as the assignment does.
- Spec size. The RFC estimates about 3,000 core tokens and about 700 card tokens. Neither is measured. Subtask 25 measures them with `tools/check/tokens.py`.
