# Plan: RFC 0050 Diagnostic style (diagnostic-style-v2)

RFC 0050 is accepted. It replaces RFC 0004's record. A record is `code`, optional `severity` (absent means error), `span` as `{start,end}`, and optional `fix`. It has no `message`, `file`, `line` or `column`. It also changes the runtime trap line and the catalogue (`message` goes, `meaning` stays). It amends RFC 0005 only in the trap line.

Subtasks 1 to 4 need nothing blocked. They come first, so the queue never stops on a blocked line. Subtasks 5 to 11 are each blocked on a named decision (B1 to B4 below). Do not start a blocked subtask until its decision is recorded in the RFC or the PR thread.

## Blocked decisions

- **B1. Trap exit status and kind spelling conflict with accepted RFC 0020 (blocks 6, 7, 8).** RFC 0050 section 5 says the trap status and kinds are "unchanged" from RFC 0005. That is not what the repo says now:
  - RFC 0005 says exit status 3 and kinds `overflow`, `divide by zero`, `stack exhausted`. RFC 0006, 0008, 0009 and 0010 also say status 3.
  - RFC 0013, 0015, 0016 and the accepted RFC 0020 (TR1) say status 1 and kinds `overflow`, `divide-by-zero`, `stack-exhausted`, `step-exhausted`.
  - The code follows RFC 0020: `compiler/stage0/src/kernel/types.ts` (`TRAP_LINE`), `kernel/rt-trap.ts` (`proc_exit(1)`), and `spec/card.md` (status 1).
  - RFC 0050 amends only RFC 0004 and 0005. Its own section on the trap line changes RFC 0020 TR1 without naming it, and the constitution requires a new RFC to name the RFC it amends.
  - `step-exhausted` (RFC 0020 TR3) is not in RFC 0005's list, though RFC 0050 says the kinds are those RFC 0005 lists.
  
  Decision needed: either (a) RFC 0050 names RFC 0020 TR1 as amended and states the status (1 or 3) and the exact spelling of each kind, including `step-exhausted`; or (b) RFC 0050 is revised to keep status 1 and the hyphenated spellings. Either way its claim "unchanged" must be corrected.

- **B2. Owner ruling of 2026-11-20 (blocks 5).** The ruling sets the message-sentence rule for records and requires `compiler/stage0/src/message.ts` to accept `source file does not end in .gl`. RFC 0050 removes message text, and says the owner must confirm the supersession before merge. Need owner confirmation in the RFC thread.

- **B3. E0006 fix is not specified (blocks 9, and 10 for `fix-present`).** RFC 0050's `diag/fix-present` expects E0006 at `007` bytes 0 to 3, with fix `7`. Neither RFC 0014 nor RFC 0048 gives E0006 a fix; `compiler/stage0/src/lexer/records.ts` attaches none. RFC 0048 rule 7 raises the same test and says it expects E0001, while rule 8 says E0006. Need the lexical group to rule on the code and the fix.

- **B4. Compile-error and run tests need a working `check` path (blocks 10, 11).** `compiler/stage0/src/cli.ts` answers `check FILE` with `glyphc: no front end yet` and exit 2. `compile.ts` returns reason strings, not records. The runner requires exit 1 for a compile-error test, so none of these tests can pass until `check` writes records from the lexer and parser. That wiring belongs to another RFC's plan (RFC 0014 or RFC 0020 in `main.ts`/`cli.ts`), not this one. Do not write those tests before it lands.

- **B5. Runner limits (not ours to change).** `tools/` is off limits to the implementer, so these stand as written. Consequences:
  - `(check)` is not a conformance kind (`TEST_KINDS` in `tools/check/conformance.py` is `run`, `compile-error`, `trap`, `fmt`, `fix`). RFC 0050's `diag/keys`, `diag/catalogue` and `diag/retired` would be refused by `parse_test`, and the publisher would refuse the whole update. They become node tests (subtask 4).
  - The `run` kind checks only stdout and exit. The `trap` kind checks exit and a stderr substring. RFC 0050's "writes nothing to stderr" and "writes exactly" cannot be enforced by a conformance test. They are checked in node tests (subtasks 7 and 11).
  - The `CODE LINE` form of `expect-errors` compares `span.line`, which this RFC removes. RFC 0037's plan (`rfcs/0037.plan.md`, subtask 5) uses that form for `ord-mixed.test` and `ord-le.test`. Those expectations stop matching after subtask 1. New tests here use the JSON form only. The RFC 0037 plan needs its owner to change it.
  - Compile-error matching ignores keys the expected record does not give. A test cannot catch an extra `file`, `line`, `column` or `message`. Node tests (subtask 4) do.
  
  The architect should decide whether to ask for `(check)` and an exact-stderr check in the runner, or whether RFC 0050's test plan should name node tests instead.

- **B6. Exit status for a failed compile.** RFC 0050 leaves it open. The runner requires exit 1 (`rc != 1` fails a compile-error test). This plan keeps exit 1 for a failed compile. The RFC should state it.
