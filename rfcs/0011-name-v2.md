# RFC draft: The language name

Class: language
Slug: name-v2

## Summary

The language is called **Glyph**. Source files end in `.gl`. The compiler command is `glyphc`. This RFC adds no grammar, no types and no runtime behaviour. It fixes the name, the one source file extension the toolchain needs, and the one diagnostic code that rule uses.

## Motivation

The repository already calls the language Glyph in `README.md`, `docs/SPEC.md`, the compiler command and the site. Keeping the name costs nothing. The check job and the publisher need one fixed suffix to recognise language sources, so the extension is fixed here.

The file-name rule runs before the file is read, so it works even when the content is not valid Glyph. Its code is in the lexical block, `E0001` to `E0099` (RFC 0004 section 4). `E0010` is the next free code in that block and no other RFC uses it.

## Design

Normative.

1. The language name is `Glyph`. The core spec section is `spec/core/name.md` and starts with the title `Glyph`. The spec card is `spec/card.md` and starts with the title line `Glyph`. The implementing PR removes the word `codename` from the title line of `README.md`.
2. A source file uses the extension `.gl`, in lower case. Its final component is the part of the path after the last `/`. A path is a source file when its final component has at least one character before a suffix that is exactly `.gl`. Matching is case-sensitive.
   - Source files: `main.gl`, `dir/prog.gl`, `a.b.gl`.
   - Not source files: `main.glyph`, `prog.txt`, `PROG.GL`, `main.gl.bak`, `.gl`, `dir/`, and the empty string.
3. The compiler executable is `glyphc`. Its subcommands are `check`, `run` and `build`. Later RFCs define what they do.
4. Names are case-sensitive. `Glyph` is the only spelling of the name in the spec.
5. When `glyphc` is given a path that is not a source file, for any subcommand that takes a path, it does not read the file. It writes one diagnostic record to standard error in the form RFC 0004 section 2 defines, writes nothing to standard output, and exits with status 1. The record is:
   - `code`: `E0010`
   - `severity`: `error`
   - `message`: `source file does not end in .gl`
   - `span`: `{"file": <path as given>, "start": 0, "end": 0, "line": 1, "column": 1}`. The file is not read, so the span is the start of the file.
   - no `fix`. Renaming the file is the author's choice, not a mechanical edit.
6. The code `E0010` is added to `spec/errors.json` by the first implementing PR, with the message above and the meaning `the path given is not a source file`. Codes are never reused.

## Alternatives

- **Keep "Glyph" as a codename and pick a new name later.** Rejected. It postpones a decision that costs nothing now and leaves the extension question open.
- **Pick a new name.** Rejected. Every existing file and tool would need changing. Renaming stays cheap until a release exists, so a later RFC can rename the language if a collision is found.
- **No file extension rule.** Rejected. The publisher and check job need one suffix to find sources.
- **Accept `.glyph` as well as `.gl`.** Rejected. A second suffix is a second way to name the same thing, which breaks principle 1.
- **Use a diagnostic code with a `GLY` prefix.** Rejected. RFC 0004 fixes the `E` plus four digits format.

## Cost

Measured with `tools/check/tokens.py`.

- **Core spec:** `spec/core/name.md` is 177 tokens. It holds the name, the source-file rule, the subcommand names and the reference to `E0010`. The `spec/errors.json` entry is not in the core spec and is not counted here.
- **Spec card:** `Glyph` is 1 token and `Source: *.gl, compiler glyphc` is 8 tokens. Net change is 9 tokens.
- **Removes:** nothing.
- **Diagnostics:** one new code, `E0010`, in the lexical block.
- **Grammar:** no production is added, so grammar coverage is unchanged.

## Test plan

- **run:** `conformance/name/run-title.test`. A `main.gl` prints `Glyph` with `print`, which RFC 0005 (kernel) defines.
- **compile-error:** `conformance/name/bad-extension.test`. `glyphc check prog.txt` gives exactly one record, as JSON: `{"code":"E0010","severity":"error","message":"source file does not end in .gl","span":{"file":"prog.txt","start":0,"end":0,"line":1,"column":1}}`, with no `fix` field and exit status 1. The runner compares `code`, `span` and `fix`, as RFC 0004 section 7 requires.
- **compile-error:** `conformance/name/upper-extension.test`. `glyphc check PROG.GL` gives `E0010`, because the extension is lower case only.
- **unit (not conformance):** `compiler/stage0/src/source-file.test.ts` checks every path listed in Design 2. `compiler/stage0/src/cli.test.ts` checks the record in Design 5 for `check`, `run` and `build` on `prog.txt`, `PROG.GL`, `main.glyph` and `missing.txt`, and checks that no read error is reported for the missing file.

No grammar production is added, so the coverage script has nothing new to match.

## Memory allocation

Not applicable. This RFC adds no heap values.

## Open questions

- RFC 0005's address example `main.glyph::add` must read `main.gl::add` before RFC 0005 is accepted. This RFC does not edit RFC 0005.
- No accepted RFC defines `print` yet, so the run test has no definition to rely on until one is accepted.
- A second extension is not accepted by this RFC. A later RFC must remove or justify any second suffix.
- The name has not been checked against existing software or trademarks. That needs a network check outside this session.

## Owner ruling (2026-11-20)

The one-sentence rule in RFC 0004 section 2 does not treat a full stop inside a file name or extension, such as `.gl` or `main.gl`, as a sentence break. The RFC 0011 message `source file does not end in .gl` is valid as written. The message checker in `compiler/stage0/src/message.ts` must accept it, with a test. This settles the conflict between RFC 0004 and RFC 0011 (issues 54 and 59).
