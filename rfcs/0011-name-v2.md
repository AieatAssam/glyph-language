# RFC draft: The language name

Class: language
Slug: name-v2
Author: designer-min
Status: draft

## Summary

The language is called **Glyph**. Source files end in `.gl`. The compiler command is `glyphc`. This RFC adds no grammar, no types and no runtime behaviour. It fixes the name in the spec title, the one source file extension the toolchain needs, and the one diagnostic code that rule uses.

## Motivation

The constitution leaves the name to the agents. The repository already calls the language Glyph in `README.md`, `docs/SPEC.md`, the compiler command and the site. Every other choice would mean renaming all of that before any kernel code exists.

The file extension is needed now. The check job and the publisher need one fixed suffix to recognise language sources. Without a rule, each component would pick its own.

The check runs on the file name before the file is read, so it works even when the content is not valid Glyph. That is why it is a file-name rule, even though its code sits in the lexical block.

## Design

Normative.

1. The name of the language is `Glyph`. The spec title is `Glyph`.
2. A source file uses the extension `.gl`. The match is case-sensitive. Take the part of the path after the last `/`. It is a source file when it ends in `.gl` and has at least one character before `.gl`. So `main.gl`, `dir/prog.gl` and `a.b.gl` are source files. `main.glyph`, `prog.txt`, `PROG.GL`, `main.gl.bak`, `.gl`, `dir/` and the empty string are not.
3. The compiler executable is `glyphc`. Its subcommands are `check`, `run` and `build`. This RFC does not define those subcommands; later RFCs do.
4. Names in this RFC are case-sensitive. `Glyph` is the only spelling of the name in the spec.
5. When `glyphc` is given a path that is not a source file, it does not read the file. It writes exactly one diagnostic record, as defined by RFC 0004 section 2, to standard error, and exits with status 1. The record is one JSON line:
   `{"code":"E0010","severity":"error","message":"source file does not end in .gl","span":{"file":"<path as given>","start":0,"end":0,"line":1,"column":1}}`
   It has no `fix`. Renaming the file is the author's choice, not a mechanical edit. Nothing is written to standard output.
6. Under RFC 0004 section 2, a full stop followed by a letter inside a file name or extension is not a sentence break. The message in (5) is therefore valid under RFC 0004. This is the owner ruling of 2026-11-20 and it amends nothing else in RFC 0004.
7. The code `E0010` has the message in (5) and the meaning "the path given is not a source file". It is in the lexical block `E0001` to `E0099` and is the only code this RFC adds. Codes are never reused.

## Alternatives

- **Keep "Glyph" as a codename and pick a new name later.** Rejected. It postpones a decision that costs nothing now and leaves the extension question open.
- **Pick a new name.** Rejected. Every existing file and tool would need changing. Collision with other projects was not checked, because this session has no network access. A later RFC can rename the language if a collision is found; renaming is cheap until a release exists.
- **No file extension rule.** Rejected. The publisher and check job need one suffix to find sources.
- **Accept `.glyph` as well as `.gl`.** Rejected. A second suffix is a second way to name the same thing, which breaks principle 1.
- **Use a diagnostic code from another prefix.** Rejected. RFC 0004 fixes the `E` plus four digits format.

## Cost

Counted with `tools.check.tokens`:

- The E0010 message `source file does not end in .gl`: 8 tokens.
- Spec card addition, the lines `Glyph` and `Source: *.gl, compiler glyphc`: 10 tokens. Removes nothing. The card stays far under its 2,000-token cap.
- Spec core addition: the title, the `.gl` rule (section 2), the executable name with its subcommands (section 3) and the `E0010` entry. Not yet written, so not yet counted. The implementing PR for subtask 5 counts it with the same tool.
- Removes nothing from the core.
- Grammar: no production is added, so grammar coverage is unchanged.

## Test plan

- compile-error (node): `compiler/stage0/src/cli.test.ts`. For each of `check`, `run` and `build`, and each of the paths `prog.txt`, `PROG.GL`, `main.glyph` and `missing.txt`, standard error is exactly the JSON line in Design 5, the exit status is 1, standard output is empty, and the file is not opened (a missing file gives the same line, not ENOENT).
- node unit: `compiler/stage0/src/source-file.test.ts`. The cases listed in Design 2 give the stated results.
- node unit: `compiler/stage0/src/message.test.ts`. The message in Design 5 passes `checkMessage` with an empty problem list.
- node unit: `compiler/stage0/src/e0010.test.ts`. `spec/errors.json` has the `E0010` entry exactly once, its code is in the lexical block, and its message is the one in Design 5.
- run: `conformance/name/run-title.test`. A program in `main.gl` calls `print` with the text `Glyph` and nothing else; its standard output is `Glyph` and its exit status is 0. `print` is defined by the kernel RFC, not by this one.

No grammar production is added, so the coverage script has nothing new to match.

## Memory allocation

Not applicable. This RFC adds no heap values.

## Open questions

- Whether the language should accept a second extension later. This RFC says no. A later RFC must remove or justify any second suffix.
- The name has not been checked against existing software or trademarks. That needs a network check outside this session.
