# RFC draft: The language name

Class: language
Slug: name-v2
Author: designer-min
Status: draft

## Summary

The language is called **Glyph**. Source files end in `.gl`. The compiler command is `glyphc`, as already used in `bin/glyphc`. This RFC adds no grammar, no types and no runtime behaviour. It fixes the name in the spec title, the one source file extension the toolchain needs, and the one diagnostic code that rule uses.

## Motivation

The repository already calls the language Glyph in `README.md`, `docs/SPEC.md`, the compiler command and the site. Renaming would touch all of them before any kernel code exists, so the name in use is the one fixed here.

The check and the publisher need one fixed source suffix. The rule runs on the file name before the file is read, so it works even when the content is not valid Glyph. That is why it is a file-name rule, even though its code sits in the lexical block.

## Design

Normative.

1. The name of the language is `Glyph`. The spec title is `Glyph`. The word "codename" is removed from `README.md` when the first RFC that creates `spec/` is implemented. This RFC does not edit that file.
2. A source file uses the extension `.gl`, in lower case. Take the part of the path after its last `/`. The path is a source file when that name has at least one character before a final `.gl`. The match is case-sensitive. `main.gl` and `a.b.gl` are source files. `main.glyph`, `prog.txt`, `PROG.GL`, `main.gl.bak`, `.gl`, `dir/` and the empty string are not.
3. The compiler executable is `glyphc`. Its subcommands are `check`, `run` and `build`. This RFC defines their behaviour only as far as item 5; later RFCs define the rest.
4. Names in this RFC are case-sensitive. `Glyph` is the only spelling of the name in the spec.
5. For each of `check`, `run` and `build`: when the path given is not a source file, `glyphc` does not open the file. It writes exactly one diagnostic record, as defined by RFC 0004 section 2, to standard error, writes nothing to standard output, and exits with status 1. The record has:
   - `code`: `E0010`
   - `severity`: `error`
   - `message`: `source file does not end in .gl`
   - `span`: `{"file": <path as given>, "start": 0, "end": 0, "line": 1, "column": 1}`. The file is not read, so the span is the start of the file.
   - no `fix`. Renaming the file is the author's choice, not a mechanical edit.
6. The code `E0010` has one entry in `spec/errors.json`: message `source file does not end in .gl`, meaning `the path given is not a source file`. Codes are never reused.

## Alternatives

- **Keep "Glyph" as a codename and pick a new name later.** Rejected. It postpones a decision that costs nothing now and leaves the extension question open.
- **Pick a new name.** Rejected. Every existing file and tool would need changing. This RFC does not check collisions with other software. A later RFC can rename the language if one is found. Renaming is cheap until a release exists.
- **No file extension rule.** Rejected. The publisher and check job need one suffix to find sources.
- **Accept `.glyph` as well as `.gl`.** Rejected. A second suffix is a second way to name the same thing, which breaks principle 1.
- **Use a `GLY` prefix for the code.** Rejected. RFC 0004 section 2 fixes the `E` plus four digits format.

## Cost

Counted with `tools/check/tokens.py`:

- **Core spec adds:** 21 tokens for the title and the rule, counted from the wording `Glyph. Source file: last suffix exactly .gl, case-sensitive. Other paths are not source files.` Plus 11 tokens for the `E0010` code and message `E0010 source file does not end in .gl`. Total about 32 tokens against the 12,000-token cap.
- **Removes:** nothing.
- **Spec card:** adds `Glyph` (1 token) and `Source: *.gl, compiler glyphc` (8 tokens). Net +9 tokens against the 2,000-token cap.
- **Diagnostics:** one new code, `E0010`, in the lexical block. It is the only code this RFC adds.
- **Grammar:** no production is added, so grammar coverage is unchanged.

## Test plan

- **run:** `conformance/name/run-title.test`. A program `main.gl` prints `Glyph` with `print`.
- **compile-error (node test):** `compiler/stage0/src/cli.test.ts`. For each of `check`, `run` and `build`, and each of the paths `prog.txt`, `PROG.GL`, `main.glyph` and `missing.txt`, the output on standard error is exactly one JSON record with `code` `E0010`, the `span` in item 5 with `file` set to the path given, and no `fix`. The exit status is 1 and standard output is empty. The file is not opened, so `missing.txt` gives the same record. The test compares `code`, `span` and `fix`, as RFC 0004 section 7 requires.
- **compile-error (node test):** `compiler/stage0/src/source-file.test.ts`. The cases in item 2 are each classified correctly.
- **check (node test):** `compiler/stage0/src/message.test.ts`. The `E0010` message passes `checkMessage`. The full stop inside `.gl` is not a sentence break.

No grammar production is added, so the coverage script has nothing new to match.

## Memory allocation

Not applicable. This RFC adds no heap values.

## Open questions

- `print` is not defined by any RFC in force. The run test needs a definition of `print` from a kernel RFC.
- Whether the language should also accept a second extension later. This RFC says no. A later RFC must remove or justify any second suffix.
- Whether the name collides with existing software or trademarks has not been checked.


## Owner ruling (2026-11-20)

The one-sentence rule in RFC 0004 section 2 does not treat a full stop inside a file name or extension, such as `.gl` or `main.gl`, as a sentence break. The RFC 0011 message `source file does not end in .gl` is valid as written. The message checker in `compiler/stage0/src/message.ts` must accept it, with a test. This settles the conflict between RFC 0004 and RFC 0011 (issues 54 and 59).
