# RFC 0011: The language name

Class: language
Slug: name-v2

## Summary

The language is called **Glyph**. Source files end in `.gl`. The compiler command is `glyphc`. This RFC adds no grammar, no types and no runtime behaviour. It fixes the name in the spec title, the one source file extension the toolchain needs, and the one diagnostic code that rule uses.

## Motivation

The constitution leaves the name to the agents. The repository already calls the language Glyph in `README.md`, `docs/SPEC.md`, the compiler command and the site. Changing it would mean renaming all of that before any kernel code exists.

The check job and the publisher need one fixed suffix to recognise language sources. The check runs on the file name before the file is read, so it works even when the content is not valid Glyph. That is why the rule is a file-name rule, even though its code sits in the lexical block.

## Design

Normative.

1. The name of the language is `Glyph`. The spec title is `Glyph`. The word "codename" is removed from `README.md` by the first implementing PR that creates `spec/`. This RFC does not edit that file.
2. A source file uses the extension `.gl`. The extension is lower case. A path is a source file when its last suffix is exactly `.gl` and at least one character precedes it in the file name (the part after the last `/`). Matching is case-sensitive. `main.gl`, `dir/prog.gl` and `a.b.gl` are source files. `main.glyph`, `prog.txt`, `PROG.GL`, `main.gl.bak`, `.gl`, `dir/` and the empty string are not.
3. The compiler executable is `glyphc`. Its subcommands are `check`, `run` and `build`. This RFC does not define what they do; later RFCs do.
4. Names in this RFC are case-sensitive. `Glyph` is the only spelling of the name in the spec.
5. When `glyphc check`, `glyphc run` or `glyphc build` is given a path that is not a source file, it does not read the file. It writes exactly one diagnostic record, as defined by RFC 0004 section 2, to stderr, and exits with status 1. Nothing is written to stdout. The record is:
   - `code`: `E0010`
   - `severity`: `error`
   - `message`: `source file does not end in .gl`
   - `span`: `{"file": <path as given>, "start": 0, "end": 0, "line": 1, "column": 1}`. The file is not read, so the span is the start of the file.
   - no `fix`. Renaming the file is the author's choice, not a mechanical edit.
6. The message in rule 5 is valid under RFC 0004 section 2. A full stop inside a file name, such as the one in `.gl`, is not a sentence break. The message checker in `compiler/stage0/src/message.ts` must accept this message, as the owner ruling of 2026-11-20 requires.
7. The code `E0010` has the meaning "the path given is not a source file". It is entered in `spec/errors.json` with the message in rule 5. Codes are never reused.

## Alternatives

- **Keep "Glyph" as a codename and pick a new name later.** Rejected. It postpones a decision that costs nothing now and leaves the extension question open.
- **Pick a new name.** Rejected. Every existing file and tool would need changing. Collision with other projects was not checked, because the session has no network access. Renaming stays cheap until a release exists.
- **No file extension rule.** Rejected. The publisher and check job need one suffix to find sources.
- **Accept `.glyph` as well as `.gl`.** Rejected. A second suffix is a second way to name the same thing. Any example that uses `.glyph` is a conflict to be fixed in that RFC.
- **Use a diagnostic code from a `GLY` prefix.** Rejected. RFC 0004 fixes the `E` plus four digits format and has no other prefix.

## Cost

Counted with `sbx python3 -m tools.check.tokens`:

- **Core spec:** the name sentence "Glyph. Source files end in .gl (case-sensitive). Compiler: glyphc check|run|build." counts 22 tokens. The `E0010` entry is counted by the merge bot when `spec/errors.json` is checked.
- **Spec card:** adds the lines `Glyph` and `Source: *.gl, compiler glyphc`, counted 10 tokens. Nothing is removed.
- **Removes:** nothing.
- **Diagnostics:** one new code, `E0010`, in the lexical block. It is the only code this RFC adds.
- **Grammar:** no production is added, so grammar coverage is unchanged.

## Test plan

- **run:** `conformance/name/run-title.test`. A kernel program `main.gl` prints `Glyph` with `print`, as the kernel RFC in force defines it.
- **compile-error (node tests, in `compiler/stage0/src/`):**
  - `cli.test.ts`: `prog.txt`, `PROG.GL`, `main.glyph` and a missing `missing.txt` each give exactly the record in Design rule 5 for `check`, `run` and `build`. Each exits 1, writes nothing to stdout, and does not attempt to read the file. A `.gl` path does not give `E0010`.
  - `source-file.test.ts`: the examples in Design rule 2 are classified as listed.
  - `e0010.test.ts`: the `E0010` entry exists exactly once in `spec/errors.json`, its code is in the range E0001 to E0099, and its message passes `checkMessage` from `message.ts` with no problems.
  - `message.test.ts`: `source file does not end in .gl` passes `checkMessage` with no problems. A message with a full stop followed by a space, such as `Read it. Then stop`, is still reported.

The conformance runner gives every input the name `main.gl`, so no conformance test can present a path that is not a source file. The file-name compile-error cases are therefore the node tests above.

## Open questions

- A conformance compile-error test for `E0010` can be added once the conformance runner accepts an input file name. This RFC does not require it.
- Whether the language should accept a second extension later. This RFC says no. A later RFC must justify any second suffix.
- The name has not been checked against existing software or trademarks. That needs a network check outside this session.
