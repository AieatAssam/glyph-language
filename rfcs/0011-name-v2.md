# RFC draft: The language name

Class: language
Slug: name-v2
Author: designer-min

## Summary

The language is called **Glyph**. Source files end in `.gl`. The compiler command is `glyphc`, as already used in `bin/glyphc`. This RFC adds no grammar, no types and no runtime behaviour. It fixes the name in the spec title, the one source file extension the toolchain needs, and the one diagnostic code that rule uses.

## Motivation

The repository already calls the language Glyph in `README.md`, `docs/SPEC.md`, the compiler command and the site. Every other choice would mean renaming all of that before any kernel code exists. The cheapest name is the one already in use.

The check job and the publisher need one fixed suffix to recognise language sources, so the file extension is fixed here.

The source-file check runs on the file name before the file is read, so it works even when the content is not valid Glyph. That is why it is a file-name rule, even though its code sits in the lexical block.

## Design

Normative.

1. The name of the language is `Glyph`. The spec title is `Glyph`. Names in this RFC are case-sensitive; `Glyph` is the only spelling of the name in the spec.
2. A source file uses the extension `.gl`. The extension is lower case. A path is a source file when the part after its last `/` ends in exactly `.gl` and has at least one character before `.gl`. So `main.gl`, `dir/prog.gl` and `a.b.gl` are source files. `main.glyph`, `prog.txt`, `PROG.GL`, `main.gl.bak`, `.gl`, `dir/` and the empty string are not.
3. The compiler executable is `glyphc`. Its subcommands are `check`, `run` and `build`. This RFC names them and does not define them; later RFCs do.
4. When `glyphc check`, `glyphc run` or `glyphc build` is given a path that is not a source file, it does not read the file. It writes exactly one diagnostic record, as defined by RFC 0004 section 2, to standard error, and exits with status 1. Nothing is written to standard output.
   - `code`: `E0010`
   - `severity`: `error`
   - `message`: `source file does not end in .gl`
   - `span`: `{"file": <path as given>, "start": 0, "end": 0, "line": 1, "column": 1}`. The file is not read, so the span is the start of the file.
   - no `fix`. Renaming the file is the author's choice, not a mechanical edit.
5. The message in item 4 is valid under RFC 0004 section 2. A full stop followed by a letter, as in `.gl`, is part of a name and is not a sentence break.
6. The code `E0010` has the entry in `spec/errors.json`: `message` `source file does not end in .gl`, and `meaning` `the path given is not a source file`. Codes are never reused.

## Alternatives

- **Keep "Glyph" as a codename and pick a new name later.** Rejected. It postpones a decision that costs nothing now and leaves the extension question open.
- **Pick a new name.** Rejected. Every existing file and tool would need changing. Collision with other projects was not checked, because this session has no network access. If a collision is found later, a new RFC can rename the language. Renaming is cheap until a release exists.
- **No file extension rule.** Rejected. The publisher and check job need one suffix to find sources.
- **Accept `.glyph` as well as `.gl`.** Rejected. A second suffix is a second way to name the same thing, which breaks principle 1.
- **Use a diagnostic code from the `GLY` prefix.** Rejected. RFC 0004 fixes the `E` plus four digits format and has no other prefix.

## Cost

Counted with `tools/check/tokens.py`:

- **Adds to the core spec:** the name and the `.gl` rule, 28 tokens. The `E0010` catalogue meaning and message, 19 tokens. Item 4 is spec text of the rule, counted in the 28.
- **Removes:** nothing.
- **Spec card:** adds `Glyph` and `Source: *.gl, compiler glyphc`, 10 tokens.
- **Diagnostics:** one new code, `E0010`, in the lexical block. It is the only code this RFC adds.
- **Grammar:** no production is added, so grammar coverage is unchanged.

## Test plan

- **run:** `conformance/name/run-title.test`. A program `main.gl` prints `Glyph` with `print`, as the kernel RFC defines it.
- **compile-error, file names:** node tests in `compiler/stage0/src/`. These cannot be conformance tests, because the conformance runner gives every source the name `main.gl`. See Open questions.
  - `cli.test.ts`: for `check`, `run` and `build`, the paths `prog.txt`, `PROG.GL`, `main.glyph` and `missing.txt` each write the record in Design item 4 and return 1, and do not read the file. The path `main.gl` does not give `E0010`.
  - `source-file.test.ts`: every example in Design item 2 gives the stated answer.
  - `e0010.test.ts`: the `E0010` entry exists exactly once in `spec/errors.json`, and its code is in the lexical block `E0001` to `E0099`.

No grammar production is added, so the coverage script has nothing new to match.

## Memory allocation

Not applicable. This RFC adds no heap values.

## Open questions

- **File-name conformance tests.** The conformance runner writes every source to `main.gl` and has no meta key that names another input. So the two file-name cases in the test plan are node tests. A key that names the input file would let them be conformance tests; the architect decides whether to add it.
- **RFC 0005 address example.** Its `main.glyph::add` should read `main.gl::add` to agree with this RFC. This RFC does not edit RFC 0005.
- Whether the language should also accept a second extension later. This RFC says no. A later RFC must remove or justify any second suffix.
- The name has not been checked against existing software or trademarks. That needs a network check outside this session.
