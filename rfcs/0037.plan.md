# Plan: RFC 0037 Ordering on Text with `<` (text-order)

RFC 0037 is accepted. It lets `<` take two `Text` operands and compare them byte by byte as unsigned bytes, with a proper prefix less than the longer text (OR1 to OR3). `<=`, `>` and `>=` stay `Int`-only (OR4). It amends RFC 0020 E4 (OR6) and replaces RFC 0035 TX7 (OR7).

Subtask 1 needs only the toolkit and can be built now. Subtasks 2 to 6 need the kernel checker and codegen that `rfcs/0020.plan.md` has not yet delivered, and subtask 4 needs an architect decision (see Conflicts).

## Conflicts and decisions

- **PR 356 and the file name (resolved in this revision).** PR 356 creates `compiler/stage0/src/kernel/rt-text.ts` with `addTextRuntime`. This plan used the same path for `addTextOrder`, so the two PRs would conflict. This revision renames the new file to `compiler/stage0/src/kernel/rt-text-order.ts`, and subtasks 1 and 3 use that name. This plan does not touch `rt-text.ts`.
- **PR 356 conformance test `cmp-text.test` (must change before subtask 2 lands).** PR 356's conformance test `cmp-text.test` expects E0200 for `<` on `Text`. Subtask 2 of this plan makes that false, because `<` on two `Text` operands is `Bool` (OR1, OR2). Existing conformance tests cannot be edited, so PR 356 must change that test to use `<=` first, which stays E0200 under OR4. This plan does not edit that test. The contents of `cmp-text.test` could not be confirmed, because PR 356 is not in this checkout. This note rests on the earlier review and the diff text. If PR 356 has not made that change when subtask 2 is ready to merge, subtask 2 breaks the gate and must wait.
- **TX9 rejects the test programs (blocks subtask 4 and everything that runs the `ord-` run tests).** RFC 0035 TX9 (accepted) says a `Text` expression may appear only as a `let` or `var` initialiser or assigned value, as a `print` argument, as an operand of `==` or `!=`, or as the first argument of `text_len` or `text_byte`. Anywhere else is rejected with the T3 diagnostic. RFC 0037 does not amend TX9, but its test programs put `Text` in the operand of `<` inside an `if` condition, for example `if "a" < "b" { print(1) }`. Under TX9 as written, that is rejected. RFC 0037 OR1 and TX9 contradict each other, so this is an architect decision (the task rule: two accepted RFCs that contradict each other go to the architect). Decision the architect must make: add "an operand of `<`" to TX9, in the same wording as `==` and `!=`. Until then, subtask 4 is blocked. Subtasks 1, 2 and 3 are not blocked, because they test the expression rule without a placement check.
- **`==` and `!=` on Text in RFC 0020 subtask 10.** The test list for `types-expr.test.ts` in `rfcs/0020.plan.md` subtask 10 expects `"a" == "b"` to give E0200. RFC 0035 TX6 (accepted) gives `==` and `!=` `Text` operands. TX6 wins. The 0020 subtask 10 implementer should follow TX6, and subtask 2 here must not repeat that expectation. Do not edit RFC 0020's test text. Report it in the PR body.
- **Test for `==` in 0020 batch B.** `err-text-op` in `rfcs/0020.plan.md` subtask 24 (and RFC 0020 test plan row `err-text-op`) expects E0200 for `print("a" == "b")`. The same TX6 conflict applies. Leave that to the 0020 batch author. It is not changed by this plan.
- **Error code for mixed operands (issue #31).** RFC 0037 OR3 and OR4 use E0200, which RFC 0020 uses for every type mismatch. `spec/errors.json` holds E0001, E0005, E0006, E0010, E0100 and E0500. It does not hold E0200, and this plan adds no code. RFC 0020 subtask 10 adds E0200. If E0200 is missing when you reach subtask 2, stop and report it. If issue #31 settles on another code, OR3 and OR4 change with it, and so do the expected codes in subtask 5.
- **Test directory.** RFC 0037 puts its tests in `conformance/text/`, as RFC 0026, 0028, 0030, 0033 and 0035 do. RFC 0020's plan uses `conformance/kernel/`. Follow RFC 0037: write to `conformance/text/`. The directory is new in this checkout. Do not move RFC 0020 tests.
- **Gate and failing run tests.** The gate runs every conformance test. A PR that adds a `run` test before the code that passes it fails the gate. So the conformance tests are added in the same PR as the last code change they need (subtask 5). Node tests in subtasks 1 to 4 are written first, as the working style says.
- **Helper reuse.** Two helpers compare `Text` bytes, and they live in different files:
  - `text_lt` (this plan, OR1) lives in `compiler/stage0/src/kernel/rt-text-order.ts`, added by subtask 1.
  - `text_eq` (RFC 0035 TX6) is planned by PR 356 in `compiler/stage0/src/kernel/rt-text.ts`, the file PR 356 creates. It is not in this checkout, so this plan does not depend on it.
  Each helper stays in its own file. If both land, they may share one byte-loop later. Do not merge them in this plan, and do not edit `rt-text.ts`.

## Subtasks

Write each subtask's node tests first. Each subtask stays under 400 changed lines and touches one stage. No dependency is added. Node tests live in `compiler/stage0/src/kernel/*.test.ts`, so the gate's `node --test 'compiler/stage0/**/*.test.ts'` runs them. Conformance tests go in `conformance/text/`.

- [ ] 1. Add `compiler/stage0/src/kernel/rt-text-order.ts`: `addTextOrder(m: ModuleBuilder)` defining `text_lt(ap: i32, al: i32, bp: i32, bl: i32): i32`. It returns 1 when the first text is less than the second, else 0 (OR1). It loops from index 0 up to `min(al, bl)`, loads each byte with `i32Load8U`, and compares with `i32LtU` (unsigned, so `0x80` is above `0x7F`). At the first difference it returns that comparison. If the common prefix is equal, it returns `al < bl` as a signed compare, so a proper prefix is less and equal texts are not. It allocates nothing, traps nothing and calls no counter, because it is not a source loop, so no `tick` (OR2). Test `rt-text-order.test.ts`: a harness per case stores both texts with `addData`, calls `text_lt`, and prints the result with `print_int` from `rt-print.ts`. The cases are: `""` vs `"a"` gives 1; `"a"` vs `""` gives 0; `"a"` vs `"a"` gives 0; `"ab"` vs `"abc"` gives 1; `"abc"` vs `"ab"` gives 0; `"Z"` vs `"a"` gives 1; `"z"` vs `"é"` (bytes `C3 A9`) gives 1; `"é"` vs `"z"` gives 0; the single bytes `7F` vs `80` give 1, and `80` vs `7F` give 0. Depends on the toolkit (`ModuleBuilder`, `addData`, `exportMemory`) and on `rt-print.ts` (RFC 0020 subtask 3, already checked). This subtask can be done now. Target under 200 lines.

- [ ] 2. Edit the expression type rules in `compiler/stage0/src/kernel/types-expr.ts`. A `<` whose two operands are both `Text` has type `Bool` (OR1, OR2). `Text` with any other type on either side of `<` is E0200 at the operand, so `"a" < 1` is E0200 (OR3). `<=`, `>` and `>=` with a `Text` operand are E0200 at that operand (OR4). `==` and `!=` are unchanged (OR5; RFC 0035 TX6 already gives them `Text`). This subtask does not check placement; that is subtask 4. Add no catalogue entry: E0200 is added by RFC 0020 subtask 10 (see Conflicts). Test `types-text-order.test.ts`: call the expression checker directly on expressions parsed from the RFC 0020 parser (`parse-expr.ts`, subtask 6 of 0020, already checked). Cases: `"a" < "b"` types `Bool`; `"a" < 1` gives E0200 at `1`; `1 < "a"` gives E0200 at `1`; `"a" <= "b"`, `"a" > "b"` and `"a" >= "b"` each give E0200 at the first operand. Include one `Int` case per operator so the `Int`-only rule still passes. Depends on RFC 0020 subtasks 8 to 10, and on PR 356 having changed `cmp-text.test` to `<=` (see Conflicts). Target under 200 lines.

- [ ] 3. Add the `Text` case of `<` to `compiler/stage0/src/kernel/cg-expr.ts`. Evaluate the left operand (pointer and length), then the right (pointer and length), left to right, then call `text_lt` from `rt-text-order.ts` (subtask 1) (OR2, RFC 0020 E10). The result is an `i32` `Bool`. The `Int` case is unchanged. Test `cg-text-order.test.ts`: a harness function evaluates `"a" < "b"` to 1, `"b" < "a"` to 0, `"" < "a"` to 1, and `"a" < "a"` to 0, and the results print through `print_int`. Build twice from the same source and compare bytes (determinism). Depends on subtask 1 and RFC 0020 subtask 14. Target under 200 lines.

- [ ] 4. BLOCKED on an architect decision about RFC 0035 TX9 (see Conflicts). When it is decided, add the decided wording to the placement check in `types-expr.ts`, so that a `Text` expression may be an operand of `<`, in the same way as an operand of `==` or `!=`. Test `types-text-placement.test.ts`: `if "a" < "b" { }` passes placement; `let x = "a" < "b"` (a `Bool` `let` with a `Text`-operand comparison) passes placement; `f("a" < "b")` for an `Int` parameter gives E0200 at the argument, not at a placement error; `"a" < "b" + 1` is rejected at the `+` or at `1` as an `Int` mismatch. If the architect rejects the change, this subtask is closed without a change, and subtask 5 changes to run tests with the operands in `let` (`let a = "a"` then `if a < "b"`) only if the architect allows `Text` variables in `<`. If the first unticked subtask is this one and no decision is recorded, stop and report that.

- [ ] 5. Add the conformance tests in `conformance/text/`. Run tests (`run` kind, with `expect-stdout` and `expect-exit`): `ord-lt.test` (`if "a" < "b" { print(1) }`, `if "ab" < "abc" { print(2) }`, `if "" < "a" { print(3) }` expect `1`, `2`, `3`); `ord-bytes.test` (`if "Z" < "a" { print(4) }` expects `4`, and `if "z" < "é" { print(5) }` expects `5`); `ord-equal.test` (`if "a" < "a" { print(6) }` expects empty stdout).
