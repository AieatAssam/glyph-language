# Plan: RFC 0112 Diagnostic style (diagnostic-style-v9)

RFC 0112 is accepted (frontmatter). It amends `spec/core/diagnostic.md` (Record, Order, Codes, Tests and Runtime traps), the `# Card: diagnostics` section of `spec/card.md`, and the entry shape of `spec/errors.json`. It adds `glyphc explain CODE`. It does not change the trap line (RFC 0109 TR1). This plan writes no code. It was checked against this session's scratch copy on 2026-11-27.

## State in this checkout

- `compiler/stage0/src/diagnostic.ts`: `Diagnostic` has `severity`, `message` and `span` with `file`, `line` and `column`. `toJsonLine` writes those keys and `fix` when present. `sortRecords`, `firstLexicalOnly` and `isLexical` already implement RFC 0112 D5 and RFC 0104 rule 13. Reuse them; change only the types.
- `spec/errors.json` has six entries: E0001, E0005, E0006, E0010, E0100, E0500. Each has `code`, `message`, `meaning` in that order, and each already meets D6. E0003 is absent.
- `compiler/stage0/src/catalogue-check.ts` is a pure check of emitted codes against a catalogue. Reuse it for the catalogue test.
- `bin/glyphc` (protected) reads `compiler/ACTIVE`. For `stage0` it runs `node compiler/stage0/src/main.ts`. So stage0 code runs from the repository's files, and `explain` must not depend on the current directory.
- `compiler/stage0/src/cli.ts` answers `glyphc: no front end yet` (exit 2) for `check`, `run` and `build`. Its test asserts that text.
- `tools/check/conformance.py` (protected), `compile-error` branch, lines 267 to 276: actual records are kept when `severity` is missing or `error`; `_matches` checks `code`, then `span` by subset, then `fix` only when the expected object has one. Extra keys in an actual record pass. The `CODE LINE` form compares `span.line`. No file under `conformance/` uses `compile-error` yet (checked by grep).

## Conflicts and decisions

1. **The runner cannot enforce RFC 0112 D8 exactly.** D8 says the runner compares `code`, `span` and `fix` exactly. `_subset` and `_matches` in `tools/check/conformance.py` accept extra keys, so a record with `severity`, `message`, `file`, `line` or `column` still matches. Implementers may not change `tools/`. Decision: subtask 6 enforces the exact key sets in a node test, and the PR body says the runner does not. The architect decides whether `tools/check/conformance.py` should compare exactly, or whether RFC 0112 should name the node test as the enforcement.
2. **The `CODE LINE` expectation form stops working.** After D1 no record has `span.line`, so `_matches` can never pass a `CODE LINE` expectation. No test uses that form yet. Decision: every new test uses the JSON form. The architect retires the `CODE LINE` branch in `tools/` when convenient.
3. **Who adds E0003.** RFC 0112's Test plan says the implementing PR adds E0003, as RFC 0104's table requires. `rfcs/0109.plan.md` (Diagnostics convention) says RFC 0104 plan subtask 10 adds it with `code` and `meaning` only. That convention violates D6, which requires `message`. Decision: subtask 4 of this plan adds E0003 with `message` and `meaning`, taking the words from RFC 0104's table. RFC 0104 plan subtask 10 must find the entry present and must not add a second one, because `checkCatalogue` reports a repeated code. If RFC 0104's table gives no `message`, the implementer writes one that meets D6 and says so in the PR body. The architect corrects the convention line in `rfcs/0109.plan.md`.
4. **RFC 0004 is not named.** RFC 0112 changes the record shape that RFC 0004 sections 2 and 3 define (`diagnostic.ts` cites them), but its `Amends` line names only `spec/core/diagnostic.md`, `spec/card.md` and `spec/errors.json`. The constitution requires a new RFC to name the RFC it amends. Decision: implement RFC 0112 as accepted. The architect confirms that RFC 0112 supersedes RFC 0004's record sections.
5. **Owner ruling of 2026-11-20 (RFC 0112 open question 1).** This plan could not find the ruling's text under `governance/` either. Decision: the E0010 wording is its catalogue entry, `source file does not end in .gl`, and nothing changes it. Subtask 3 checks that `compiler/stage0/src/message.ts` reads the catalogue and keeps no second copy, and that it writes no human text to stderr.
6. **Where `explain` gets the catalogue.** D7 says the catalogue is built into the binary. stage0 runs from source files, so there is no build step to embed it. Decision: subtask 5 commits `compiler/stage0/src/catalogue-data.ts` as a copy of `spec/errors.json`, and a node test asserts that the copy equals the file. Ceiling: the copy can drift, and only the test catches it. Upgrade path: a generator run from the build, once `tools/` allows it. The file is marked `ponytail:`.
7. **Rows that stay red, and why.** Conformance rows in subtask 1 need the CLI and front end. `diag/v9-fix-present`, `diag/v9-no-fix` and `diag/v9-order` need `glyphc check` to run the front end: that needs RFC 0104 B1 and RFC 0109 subtask 20. `diag/v9-no-fix` also needs the E0003 keyword emitter (RFC 0104 subtask 10). `diag/v9-clean` is a run test and needs code generation (RFC 0109 subtasks 13 and 20). Each implementing PR reports which of its rows are still red, with the subtask that unblocks them.
8. **`explain` does not need the front end.** It can land before RFC 0104 B1. Subtask 5 keeps the `cli.test.ts` stub assertion for `check`, `build` and `run`, and adds `explain` beside it.
