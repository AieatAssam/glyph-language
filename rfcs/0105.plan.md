# Plan: RFC 0105 Kernel integers, booleans, bindings, functions, conditionals, loops, text output (kernel-v46)

RFC 0105 replaces RFC 0085 (kernel-v44) and builds on `lexical-syntax-v6` (RFC 0104, accepted in front matter). It defines the `put`, `fail`, `ex` and `ret` forms, the F7 fail-mark rule, the E0200 to E0403 checks, the trap line `trap: <kind>` with exit 1 (TR1), and the kernel card (K1). This plan was written on 2026-11-27 from the RFC text and the files of this checkout. Nothing was built or run. Each test named here is a new file; no existing conformance test is edited.

Revised after review of plan PR 582. Changes: Conflicts 1 (print-one is already red in this checkout), Conflicts 4 (the code-to-subtask table; E0003 removed from this plan), Conflicts 5 (E0500 moved to the checker, as RFC 0104's table says), Conflicts 6 (expected records are JSON with span and fix), and subtasks 5, 7, 8, 9, 10 and 13 to 16 where the code table changed. Second revision (review point on `MAX_STEPS`): subtask 3 now also changes `types.test.ts`, the two test names in `rt-count.test.ts` and a comment in `rt-count.ts`; see Conflicts 2.

Subtasks 1 to 4 need only the runtime and can start now. Subtasks 5 to 19 depend on the lexer and parser of `lexical-syntax-v6`, which I did not check line by line (Conflicts 3). Subtask 8 and subtask 19 must not land before `retire-print-one` is accepted (Conflicts 1).

## Conflicts and decisions

1. **`print-one.test` is already red, and `retire-print-one` is still needed.** RFC 0105 says `print-one.test` passes today and fails under it. That is wrong for this checkout: `cli.ts` exits 2 for `run`, so the test fails now. RFC 0105 therefore breaks no passing test here. The RFC's "Alters tests" line and G-c need correcting by its author; this plan does not amend the RFC. The block on subtasks 8 and 19 is a governance rule, not a test result: the test's `rfc: 0020` and its `print` syntax stay until `retire-print-one` is accepted, and no PR may edit the test (Never). Decision: subtasks 1 to 7, 9 to 18 and 20 to 21 do not change `print` and may land. Subtasks 8 and 19 wait for the orchestrator to accept `retire-print-one`. Architect: open and accept `retire-print-one` before the parser reaches `put`.
2. **Trap line and exit status already match TR1.** `rt-trap.ts` writes the kind line and calls `proc_exit(1)`. So subtask 1 is a check and an extension, not a rewrite. Decision: keep the existing layout and extend it. Known gap: `MAX_STEPS = 1000000000` in `types.ts` line 30 does not match TR3 (10000000). Subtask 3 fixes it. The same change must touch four places, and the PR body names each one: (a) `types.ts` line 30, the constant; (b) `types.test.ts` lines 32 and 33, the existing node test that asserts 1000000000 under the name 'MAX_STEPS is 1000000000 (TR3)'. Without this edit that test goes red. It is a node test, not a conformance test, so the no-edit rule does not apply; (c) `rt-count.test.ts` lines 52 and 58, whose test names say 1000000000 (the loops already use the constant, so only the names change); (d) the comment at `rt-count.ts` line 7.
3. **Lexer and grammar are assumed to follow `lexical-syntax-v6`.** The RFC gives the grammar by reference. I did not verify that `compiler/stage0/src/lexer/` and `spec/grammar.peg` already match RFC 0104. Decision: subtask 5 first checks the lexer against RFC 0104's tests. If they differ, stop and report it. Do not edit the lexer to match RFC 0105 alone. Architect: confirm RFC 0104 has a conformance set and a grammar that subtask 5 can check.
4. **Error codes enter the catalogue with their first emitter, and this plan adds only the codes in its table.** Constitution: no code outside `spec/errors.json`. Each code below is added by exactly one plan, in the PR that first emits it, with the meaning and span from RFC 0105's Diagnostics table. Never change an entry once it is in.

5. **E0500 is a checker code.** RFC 0104's table says E0500 is "Reported by the checker". So the literal range check (T1, E0500) is in the checker, not the lexer. Decision: subtask 9 emits E0500 and adds its tests (`kc-int-max`, `kc-int-min`). Subtask 5 checks only the keyword list.
6. **Expected records are JSON, with span and fix where the RFC gives them.** `spec/core/diagnostic.md` says a compile-error test states its records as JSON, and that the runner compares `code`, `span` and `fix`. The `CODE LINE` form in `tools/check/conformance.py` compares only the code and the line, so it cannot check the span column or a fix. Decision: every compile-error test uses JSON records. A record gives `code`, `span` with `start`, `end`, `line` and `column` (byte offsets, 1-based line and column), and `fix` with `span` and `replacement` where RFC 0105 gives a fix. Omit `file` and `message`. The `_expected` and `_matches` functions compare only the keys given, so a key left out is not checked. The subtask computes byte offsets by hand from the source and lists them in its PR body. Until the front end exists, these records cannot be checked: `glyphc` answers exit 2, so every compile-error test is red in this checkout. The PR body must say so.
7. **Test location.** New tests go in `conformance/kernel/`, named as RFC 0105's Test plan names them (for example `put-one`, `trap-div`). Node tests go in `compiler/stage0/src/kernel/*.test.ts` or next to the stage they test.
8. **Gate caps.** Each subtask stays under 400 changed lines. Subtask 20 (the spec and card) may need to split if the core spec measures over 12000 tokens. Measure with `sbx python3 -m tools.check.tokens` before opening the PR.
9. **Syntax used in every test.** Programs are in canonical layout: one line, no separator, no comments. Use `put` without parentheses and `n Int` parameters.
10. **Example evaluation runs in-process.** `check`, `build` and `run` each evaluate examples. Each example is compiled as a Bool function through the same codegen as `main`, then run with the compiler's runtime at depth 0 with a fresh loop counter. If no runtime path exists for this in `compiler/stage0/src/`, subtask 16 stops and reports it.

## Subtasks

Write each subtask's tests first, as new files. Then write the smallest code that passes them. Keep each subtask to one stage where possible.

### Runtime (no parser needed)

- [ ] 1. Trap line check and extension (TR1, E1, E2). In `rt-trap.ts` and `types.ts`, confirm that the trap line is exactly `trap: <kind>` with LF and exit 1, and that the four kinds match TR1 (`overflow`, `divide-by-zero`, `stack-exhausted`, `step-exhausted`). Tests first: `rt-trap-kernel.test.ts` (new) checks each kind's stderr line and exit status, and that nothing else is written to stderr. Target under 150 lines.
- [ ] 2. Integer arithmetic (E1, E2, T1). In `arith.ts`, check `+ - *` overflow, unary `-` on the minimum, `/` and `%` truncating toward zero, `%` taking the sign of the left operand, `MIN/-1` trapping `overflow`, `MIN%-1` giving `0`, and a zero divisor trapping `divide-by-zero`. Tests first in `arith.test.ts` (extend with new cases; do not change existing ones). Target under 200 lines.
- [ ] 3. Depth and step counters (TR2, TR3). In `rt-count.ts`, the depth check traps `stack-exhausted` when depth would be 10001, with `main` at depth 1 and examples at depth 0. The per-frame loop counter traps `step-exhausted` before an addition would exceed 10000000. Change `MAX_STEPS` from 1000000000 to 10000000 in `types.ts` line 30. In the same PR, make the three other edits the constant needs, because they assert or name the old value: (a) `types.test.ts` lines 32 and 33: the assertion becomes `10000000` and the test name becomes 'MAX_STEPS is 10000000 (TR3)'; (b) `rt-count.test.ts` lines 52 and 58: the two test names change from 1000000000 to 10000000, and the loops stay on the constant; (c) the comment at `rt-count.ts` line 7. The PR body names all four files (types.ts, types.test.ts, rt-count.test.ts, rt-count.ts) and says why each changed. Tests first: the edited assertion in `types.test.ts` fails before the constant is changed, and the depth and step tests in `rt-count.test.ts` are extended with the TR2 and TR3 cases. Target under 150 lines.
- [ ] 4. Output format (P2). In `rt-print.ts`, `put` of an `Int` writes decimal with a leading `-` when negative, then LF. `put` of text writes the bytes, then LF. Tests first in `rt-print.test.ts`: `0`, `-7`, `9223372036854775807` and the minimum `-9223372036854775808`. Target under 150 lines.

### Lexer and parser (lexer and grammar must match `lexical-syntax-v6`, Conflicts 3)

- [ ] 5. Lexer check for kernel words (lexical G3). Confirm that `put`, `fail`, `let`, `var`, `wh`, `ret`, `if`, `else`, `ex`, `io`, `true`, `false`, `not`, `and`, `or` are keywords as RFC 0104 rule 7 lists them. `Int` and `Bool` are identifiers (RFC 0104 rule 6) and are checked by the type rules, not here. Add tests in `lexer/kernel-words.test.ts` (new) only for the kernel cases. Do not add lexer rules beyond RFC 0104. E0500 is not checked here (Conflicts 5). Target under 150 lines.
- [ ] 6. Expression parser (precedence, G6, E0100). Extend `parse-expr.ts` to the precedence table in RFC 0105 (`or`, `and`, comparisons without chaining, `+ -`, `* / %`, unary `- not`, call, literal, name, parenthesis). Binary operators are left-associative. A chained comparison is E0100. Tests first in `parse-expr.test.ts` (new cases). Target under 250 lines.
- [ ] 7. Declaration parser (L1, L3, F1, EX1, G3). Parse `NAME [ "(" NAME T, ... ")" ] [ R ] [ "io" ] [ "fail" ] block { "ex" expr }`, with no parentheses for a declaration without parameters. `fn main io{}` is E0100 at `main`. `ex` after a non-declaration is E0100 at `ex`. A keyword as a declaration name is E0003 at the keyword (`kc-fn-put`), and E0003 must already be in `spec/errors.json` (Conflicts 4). Tests first in `parse.test.ts` (new cases). Target under 300 lines.
- [ ] 8. Statement parser (L2, P1, C1, C2, G3). Parse `let`, `var`, assignment, a call statement, `put` with exactly one expression, `if` with block-only `else`, `wh`, and `ret` with or without an expression as a block's last item. `put 1 2` is E0100 at `2`. `put(1,2)` is E0100 at `,`. A statement never starts with an operator, `(` or a literal. A keyword as a binding name is E0003 at the keyword (`kc-reserved-put`, `kc-reserved-fail`), with the same E0003 check as subtask 7. Tests first in `parse.test.ts`. **Waits for `retire-print-one` (Conflicts 1).** Target under 300 lines.

### Checker (one diagnostic family per subtask; each adds its codes to `spec/errors.json` as Conflicts 4 says)

- [ ] 9. Types of literals and operators (T1, T2, T3, T5, T6, E3, E5, E8, E9, E0500). Check `Bool` and `Int` operand types, `==` and `!=` on two `Int` or two `Bool`, `and` `or` `not` on `Bool`, the `if` and `wh` condition being `Bool`, text only as the whole argument of `put` (E0200 elsewhere), a void call used as a value (E0200), a type or function name used as a value (E0301). Emit E0500 for an integer literal above 9223372036854775807, including after unary `-` (T1). Failed expressions take a recovery type `?` with no further diagnostic. Add E0200 and E0301 to `spec/errors.json`. Tests first: one compile-error test per row of RFC 0105's compile-error table in this area (`kc-text-let`, `kc-text-cmp`, `kc-put-paren`, `kc-put-bool`, `kc-type`, `kc-bool-op`, `kc-void-value`, `kc-unknown`, `kc-type-value`, `kc-fn-value`, `kc-int-max`, `kc-int-min`). Target under 350 lines.
- [ ] 10. Bindings and scope (B1 to B5, F6). `let` immutable, `var` mutable, assignment only to `var` (E0303 otherwise), unknown name E0301 (already added in subtask 9), use before declaration E0301, parameters declared as `let` at the body's start, duplicate or reserved names E0300, function names unique (E0300). Add E0300 and E0303 to `spec/errors.json`. This subtask does not add E0003 (Conflicts 4). Tests: `kc-dup`, `kc-dup-param`, `kc-dup-param-2`, `kc-reserved-int`, `kc-use-before`, `kc-assign-let`, `kc-assign-param`, `kc-assign-type` (E0200, B2). Target under 350 lines.
- [ ] 11. Calls and arity (E6, E7, F5). Argument count and types must match the parameters (E0200 at the argument, or at the callee name for a count error). Evaluation is left to right. Recursion is allowed. Add no new codes. Test: `kc-arity`. Target under 250 lines.
- [ ] 12. Return analysis (F3, F4, C2). A block returns if its last item is `ret`, or an `if` with `else` whose two blocks both return. A `wh` never returns. A result clause whose body does not return is E0201 at the closing `}`. `ret e` with a mismatch or a value in a no-result function is E0200 at `e`. Bare `ret` in a result function is E0200 at `ret`. Add E0201 to `spec/errors.json`. Tests: `kc-missing-ret`, `kc-if-else-partial`, `kc-wh-return`, `kc-ret-value`, `kc-ret-bare`. Target under 250 lines.
- [ ] 13. Effects and entry point (F2, M1, P1 effect). A function without `io` may not call an `io` function or `put` (E0400 at the callee name, or at `put`). `main` must be unique (E0300 for a second, which needs subtask 10), have no parameters or result (E0200 at `main`), and exist (E0302 at the end-of-file token). Add E0302 and E0400 to `spec/errors.json`. Tests: `kc-no-main`, `kc-main-sig`, `kc-dup-main`, `kc-effect`, `kc-effect-call`. Target under 300 lines.
- [ ] 14. Examples check (EX1, EX2, C0). `ex e` must be `Bool` (E0200 at `e`), call no `io` function (E0400 at the callee name, reusing subtask 13's code), and cannot contain `put` (E0100 there). The examples check runs only when no other error is reported (C0). Tests: `kc-example-type`, `kc-effect-example`. Target under 250 lines.
- [ ] 15. Fail mark (F7, E0403). A body is trapping if it has a binary `+ - * / %`, a unary `-`, a `wh`, or a call to a function declared in the file (`put` does not count), outside its examples. The `fail` token must be present if and only if the body is trapping. A wrong mark is E0403 at the function name. The fix is a zero-length insert of ` fail` at the `{`, or a delete of the space and `fail`. Add E0403 to `spec/errors.json`. Tests: `kc-fail-missing`, `kc-fail-extra`, `kc-fail-main`. Target under 300 lines.
- [ ] 16. Example evaluation (EX3, E0202, TR1 at check time). Compile each example as a Bool function through the same codegen and run it (Conflicts 10); `false` or a trap is E0202 from `ex` to the end of `e`. Add E0202 to `spec/errors.json`. Tests: `kc-example`, `kc-example-trap`, `kc-example-budget`, `kc-example-stack`. **Depends on subtask 17.** Target under 300 lines.
