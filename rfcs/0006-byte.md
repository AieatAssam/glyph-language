# RFC draft: Byte value type

Class: language
Slug: byte
Status: draft
Author: designer-min

## Summary

This RFC adds one value type, `Byte`, an unsigned 8-bit integer from 0 to 255. It adds two built-in functions: `byte(n: Int) -> Byte`, which checks the range and traps when it fails, and `int(b: Byte) -> Int`, which never fails. A `Byte` has no literal form and no arithmetic. It can be bound, passed, returned, compared for equality and order, and converted back to `Int`. It cannot be printed. This RFC covers only the bytes part of readiness item `integers-booleans-bytes`. `Int` and `Bool` come from the kernel RFC and are not redefined here.

## Motivation

The self-hosting readiness checklist (`docs/SPEC.md`, the checklist section) lists bytes as a required item. Later items need it. Text indexing and building, growable byte buffers, and the agents' own Wasm encoder all work on bytes, and none of them can be specified without a byte type.

No benchmark finding and no open user issue supports this RFC yet. The only grounding is the readiness checklist. It is listed here so that a reader does not assume more evidence than there is.

The purpose clause asks for few errors and few tokens. The smallest byte type is one that uses the `Int` rules where they apply, adds no new syntax, and makes every conversion visible in the source.

## Design

Normative. "Must" and "is" are binding on implementers.

### Type

- `Byte` is an unsigned 8-bit integer. Its values are exactly the integers 0 through 255.
- A `Byte` value is held as an `i32` on the WebAssembly stack or in a local, with the high 24 bits always zero. No heap is involved.
- `Byte` may be used anywhere a type is written: parameters, return types, `let` and `var` annotations.
- Local `let` and `var` may omit the type, as in the kernel.
- No implicit conversion exists between `Byte` and `Int`, or between `Byte` and `Bool`.

### Built-in functions

- `byte(n: Int) -> Byte`. If `n` is between 0 and 255 inclusive, the result is `n`. Otherwise the program traps with `byte out of range` (see Traps below).
- `int(b: Byte) -> Int`. The result is the same number as `Int`. It never traps.

Both names are built-in. A program that declares a function called `byte` or `int` is an error, E0108, as with `print`. Neither function has the `!io` marker.

### Literals

There is no `Byte` literal. A `Byte` value comes only from a call to `byte`. An integer literal such as `65` is an `Int`, so `byte(65)` is how a program writes that byte.

### Operators

- `==` and `!=` work on two `Byte` operands.
- `<`, `<=`, `>`, `>=` work on two `Byte` operands. The order is the numeric order from 0 to 255.
- Both operands of any of these must be `Byte`. Mixing `Byte` and `Int` is E0102.
- `+`, `-`, `*`, `/`, `%`, unary `-`, `and`, `or`, `not` are not defined on `Byte`. Using one is E0102. A program that needs arithmetic writes `int(b) + 1` and converts back with `byte(...)` if it needs a `Byte`.
- Operands are evaluated left to right, as in the kernel.

### Printing

`print` does not accept `Byte`. The kernel's two signatures for `print` stay as they are. To print a byte, the program writes `print(int(b))`.

### Traps

The byte range trap uses the same form as the kernel's traps: the message `trap: byte out of range` goes to stderr and the program exits with status 3.

### Examples

An example may use `byte` and `int`, because they are pure. For example:

```
example int(byte(65)) == 65
```

### Stable addresses

`Byte` and the two built-in functions have the fixed addresses `type:Byte`, `builtin:byte` and `builtin:int`. These are the addresses the tools use to refer to them.

## Alternatives

- **A `Byte` literal such as `'A'` or `b'A'`.** Rejected for now. It adds a lexical form and a new token. `byte(65)` covers the same need with no new syntax. Revisit it if text literals need it.
- **Compile-time range check when the argument is an integer literal, so that `byte(300)` is a compile error.** Rejected for this RFC. It adds a second rule and a new diagnostic code for a case that the runtime trap already handles. It can be added later as a separate RFC.
- **Wrapping conversion, where `byte(256)` gives 0.** Rejected. Wrapping hides the bugs the purpose clause wants caught. It also breaks the kernel rule that out-of-range results trap.
- **Make `Byte` an alias of `Int`.** Rejected. It breaks the no-implicit-conversion rule and makes the type of a value unclear in signatures.
- **Arithmetic on `Byte`.** Rejected. Each operator would need a defined overflow rule for 8 bits. `int(b) + 1` uses rules that already exist.

## Cost

Core spec: about 320 tokens. This covers the type, the two built-ins, the operator rules and the trap.

Removes: nothing. This RFC adds no operator, keyword or lexical form. It reuses the `Int` comparison rules and the kernel trap format.

Card: `spec/card.md` gains `Byte` in the value-types line, the two built-in names in the built-in list, and one row in the trap table. About 35 tokens. It omits the stable-address line and the example.

## Test plan

Conformance tests live in `conformance/bytes/`.

Run tests:

- `bytes/convert.test`: `byte(0)`, `byte(255)`, and `int(byte(200))` printed as `200`.
- `bytes/compare.test`: `==`, `!=`, `<` and `>=` on two `Byte` values.
- `bytes/bind-fn.test`: a `Byte` parameter, a `var` of type `Byte`, and a function returning `Byte`.
- `bytes/example.test`: a program whose `example int(byte(65)) == 65` holds builds and prints nothing extra.
- `bytes/trap-range.test`: `byte(256)` traps; exit status 3; stderr `trap: byte out of range`.

Compile-error tests:

- `bytes/err-arith.test`: `byte(1) + byte(2)` gives E0102.
- `bytes/err-print.test`: `print(byte(1))` gives E0102.
- `bytes/err-mix.test`: `byte(1) == 1` gives E0102.
- `bytes/err-declare.test`: `fn byte(n: Int) -> Byte` gives E0108.

No new diagnostic code is added. Every code used here is already in the kernel RFC.

Each grammar production that this RFC touches is covered: the type name, the call form, and the operators on the new type.

## Open questions

1. Should a `Byte` literal be added later for text work? This RFC says no for now. The text RFC should decide it, since text is where most byte literals would appear.
2. This RFC depends on the kernel RFC. The kernel RFC is currently `rejected`. If a revised kernel is accepted, this RFC will be restated against it, and its `Int` references will follow the accepted rules.
3. Should the trap be `byte out of range`, or should it name the value that was out of range? A fixed message keeps the trap format simple. The kernel's other traps also use fixed messages.
