# RFC draft: Text operations

## Summary

Give the `Text` type its first operations: a byte length, a byte at an index, a byte slice, concatenation, equality and the `<` order. `Text` values stay immutable, always valid UTF-8, and built only from literals and these operations. Literals, escapes and token rules are unchanged from RFC 0014. Code-point handling, number formatting and mutable builders are left to the standard library and to RFC 0025.

## Motivation

Readiness checklist item `text` (`docs/SPEC.md`, section 9) asks for "indexing, slicing, comparison, and building". No benchmark finding covers this item yet, so the case rests on the checklist and on the user issues below.

- RFC 0018 T3 says a `Text` value "has no operation in the kernel besides being bound, assigned and printed". Stage 1 needs to compare and slice source text, so the checklist item is not met until that rule changes.
- Issue #37 and issue #40 show that the team has not agreed on the escape set. RFC 0014 (accepted) gives `\n`, `\"` and `\\` and reports any other escape as E0005. This draft keeps that set and does not add `\t` or `\0`. Issue #40 is answered for escapes by reusing E0005 rather than adding a code.
- Issue #64 asks whether traps belong in signatures. The operations here trap, so the table in Design lists the trap. Principle 3 of the constitution is the reason the table names it.
- Issue #52 shows that `>`, `>=` and `<=` are not accepted (RFC 0018 G8). The order on `Text` therefore uses only `<`, as E4 does for `Int`.

This draft replaces the rejected RFC 0007. Three things differ from that draft, and each follows the accepted baseline: the trap exits with status 1 and writes `trap: <kind>` (RFC 0020 TR1), not 101; the escape set is RFC 0014's, so `\t` and `\0` are gone; and the operations are named `text_*` so that `len` keeps one meaning, the array `len` of RFC 0025.

## Design

### Values and literals

TX1. A `Text` value is a finite sequence of bytes that is valid UTF-8. Its length is at most the heap limit of RFC 0025 A24. No operation makes a `Text` from arbitrary bytes. That conversion belongs to a later RFC.

TX2. A text literal is written as RFC 0014 rule 10 defines it. Its escapes are `\n`, `\"` and `\\`. Any other backslash sequence is E0005 (RFC 0014). A tab in a literal is E0001 (RFC 0014 rule 2). This RFC adds no escape.

TX3. A literal is stored in static data. Evaluating a literal allocates nothing.

### Operations

TX4. Four built-in functions. Each has one signature. No name is overloaded.

| Function | Type | Effects | Behaviour |
| --- | --- | --- | --- |
| `text_len(t)` | `(Text) -> Int` | none | The number of bytes in `t`. |
| `text_byte(t, i)` | `(Text, Int) -> Byte` | traps `index-out-of-bounds` | The byte at index `i`, counting from 0. The run traps unless `0 <= i < text_len(t)`. |
| `text_slice(t, from, to)` | `(Text, Int, Int) -> Text` | allocates; traps `index-out-of-bounds` | A new text of the bytes from `from` up to but not including `to`. The run traps unless `0 <= from <= to <= text_len(t)`. |
| `text_cat(a, b)` | `(Text, Text) -> Text` | allocates | A new text: the bytes of `a` followed by the bytes of `b`. |

TX5. Arguments are evaluated left to right (RFC 0020 E10). Then the checks in TX4 run. A failed check traps; nothing else happens first.

TX6. `==` and `!=` accept two `Text` operands and compare bytes. `<` accepts two `Text` operands and compares bytes lexicographically: a proper prefix is less than the longer text. Mixing `Text` with another type is E0200, as E3 and E4 already require for `Int` and `Bool`. `>`, `>=` and `<=` are not accepted for `Text` (RFC 0018 G8).

TX7. Indexing and slicing count bytes. There is no code-point or grapheme operation. Code-point iteration is a standard-library function.

### Traps

TX8. `index-out-of-bounds` is one new trap kind. It is added to the trap list of RFC 0020 TR1. When it fires, the program writes `trap: index-out-of-bounds` to standard error, keeps the output written before it, and exits with status 1 through WASI `proc_exit`. The kind is catalogued in `spec/errors.json` by the first PR that emits it. `out-of-memory` (RFC 0025 A24) applies to `text_cat` and `text_slice`.

### Memory

TX9. `text_slice` and `text_cat` take their space from the bump allocator (RFC 0025 A23). Nothing is freed individually. A slice is a copy, not a view.

### Where Text may appear

TX10. RFC 0018 T3 is amended. A `Text` expression may appear wherever a `Text` value is allowed, which is: the initialiser of a `let` or `var`, the right side of an assignment to a `Text` `var`, the argument of `print`, an operand of `==`, `!=` or `<`, and an argument of one of the four functions in TX4. The rule that a `Text` value may not be used as a condition, or in other places the grammar does not allow, is unchanged.

TX11. RFC 0018 T6 is unchanged. A `Text` parameter or result is still E0100. Passing text between functions waits for the memory decision in RFC 0025.

## Alternatives

- **Code-point indexing.** Rejected. `text_byte` would cost O(n), and `text_len` would mean something different from the byte count. Code-point iteration fits the standard library.
- **`text_byte` returning an option.** Preferable to a trap, but it needs variant types, which are not yet in the language. Revisit with the records-variants item.
- **Clamping `text_slice`.** Rejected. It hides off-by-one errors, and the kernel already treats bad indices as traps.
- **Slice as a view.** Rejected for now. A view needs lifetime rules that RFC 0025 does not yet give.
- **`+` for concatenation.** Rejected. `+` is an `Int` operator in RFC 0018, and giving it a second meaning is the overloading the constitution forbids. `text_cat` is the only way to concatenate.
- **Adding `\t` or `\0`.** Not in this draft. Tabs are forbidden in source (RFC 0014 rule 2), and RFC 0014 chose not to add a tab escape. The question is open; see Open questions.
- **A `text` builder.** Rejected here. A builder is a growable byte buffer and belongs to RFC 0025.

## Cost

Adds: four built-in functions (TX4), the `Text` rule for `==`, `!=` and `<` (TX6), the `Text` rule that replaces T3 (TX10), and one trap kind (TX8). Estimate: about 260 tokens to the core spec, measured against RFC 0018 and RFC 0020. The tokeniser has not run, because `spec/` is not in this checkout.

Removes: the sentence in T3 that gives `Text` no operations, and the sentence in E3 that gives `Text` no equality. Nothing else is removed.

Spec card: about 90 tokens. One line lists the four functions with their signatures. One line gives `==`, `!=` and `<` on `Text` and says that the other orderings are not accepted. The trap line gains `index-out-of-bounds`. The card omits the copy rule and the allocator details.

## Test plan

Run tests:

- `text/len-cat.test`: `print(text_len(text_cat("ab", "cde")))` prints `5`.
- `text/slice.test`: `print(text_slice("hello", 1, 3))` prints `el`, and `print(text_slice("hi", 0, 0))` prints an empty line.
- `text/compare.test`: `if "a" < "b" { print("1") }`, `if "ab" < "abc" { print("2") }`, `if "" < "a" { print("3") }`, and `if "a" == "a" { print("4") }` print the four numbers. Each `if` is written separately so that `print` needs only `Text` and `Int`.
- `text/escapes.test`: `\n`, `\"` and `\\` each give a literal whose `text_len` is 1 for the escape, checked with `text_len`.
- `text/byte.test`: `text_byte("hello", 1)` gives the byte 101. The test converts it to `Int` with the `Byte`-to-`Int` conversion of RFC 0024. If that conversion is not accepted, this test is dropped and the byte behaviour is covered by RFC 0025.
- `text/index-trap.test`: `print("before")` then `text_byte("x", 1)` prints `before`, writes `trap: index-out-of-bounds` to standard error and exits with status 1.
- `text/slice-trap.test`: `text_slice("x", 2, 1)` traps the same way.

Compile-error tests:

- `text/bad-escape.test` (E0005): `"\t"` and `"\q"`, one per file.
- `text/eq-mismatch.test` (E0200): `"a" == 1`.
- `text/order-gt.test` (E0100): `"a" > "b"`, which the grammar does not accept.
- `text/slice-type.test` (E0200): `text_slice("a", "0", 1)`.
- `text/param.test` (E0100): `fn f(t: Text) { }`, to check that TX11 stays in force.

## Open questions

1. Tab output. Issue #37 is the open question about a `\t` escape. This draft adds none. If the team wants tabs in output, the decision belongs in the escape rules of RFC 0014, not here.
2. Traps in signatures. Issue #64 asks whether traps belong in signatures. If principle 3 requires that, the effects column of TX4 changes, and the same rule applies to RFC 0025's `get` and `set`.
3. Text parameters and results. TX11 keeps them out until the memory decision is made.
4. Slices as copies. A view would avoid the copy, but it needs lifetime rules.
