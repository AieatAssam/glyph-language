# Plan: RFC 0004 Diagnostic style

Subtasks 1 to 8 need nothing outside RFC 0004. Subtask 9 is partly done (see its line). Subtasks 10 and 11 stay blocked until the lexer and checker from RFCs 0003 and 0005 exist. Do not start a blocked subtask; if the first unticked line is blocked, stop and report that.

## Conflicts to settle first

- Runner format. Resolved. `tools/check/conformance.py` now reads JSON records for `compile-error`, compares `code`, `span` and `fix` where the expected object gives them, and uses byte-offset `fix` spans. `glyphc check` must write JSON Lines to stderr with no `--json` flag. Still open: the runner has no `check` kind, so `diag/catalogue` and `diag/retired` stay node tests (subtask 10).
- Test kinds. RFC 0004 uses a `check` kind for `diag/catalogue` and `diag/retired`. `TEST_KINDS` in the runner is `run, compile-error, trap, fmt, fix`.
- Trap wording and exit status. Resolved in favour of RFC 0004 §5: `trap: divide-by-zero` and exit 1. `compiler/stage0/src/kernel/arith.ts` and its tests already use this. RFC 0005 (rejected) says `trap: divide by zero` and exit 3; that is not used.
- Code blocks. RFC 0005 puts effect and duplicate-name errors (E0105, E0108) inside the syntax block, where RFC 0004 §4 would put effects in E0400 and names in E0300. This RFC does not fix it; whoever revives RFC 0005 must re-block its codes.
- Lexer codes versus RFC 0004 examples. The lexer emits E0001, E0005 and E0006 only. It gives a leading zero (`007`) E0006, not E0001, and no code emits a `fix` field yet. RFC 0004's test plan says `007` gives E0001 with a fix. Only the architect can choose between the RFC example and the lexer's code, because RFC 0014 owns the lexical codes.
- Keyword as name. RFC 0004's test plan says `let let = 1` gives E0003. No code emits E0003 yet, and the keyword is a valid token to the lexer, so the error belongs to the parser or checker.
- Missing tree. Resolved. `compiler/stage0/src/` and `spec/` exist in this checkout. Spec core is `spec/core/diagnostic.md` (already holds the record shape, order, block table and traps).

## Subtasks

- [x] 1. Create `spec/errors.json`: an array of entries `{code, message, meaning, retired?}` with the six blocks from RFC 0004 §4 as a comment-free table in the spec text, and no codes yet. This is the only file that will hold codes, so keep it one array.
- [x] 2. Add `compiler/stage0/src/diagnostic.ts`: the record type with fields in RFC 0004 §2 order (`code`, `severity`, `message`, `span {file, start, end, line, column}`, optional `fix {span, replacement}`), and `toJsonLine(record)` that writes one object and no trailing comma. Tests in `diagnostic.test.ts`: field order, `fix` key absent when not given, `replacement` may be empty, one line per record. Target: under 200 lines.
- [x] 3. Add the ordering helper in `diagnostic.ts`: sort by `span.start`, then `code`, stable and deterministic. Add `firstLexicalOnly(records)`, which keeps only the first record whose code is in E0001 to E0099. Tests: unsorted input, equal starts, a lexical error followed by a syntax error.
- [x] 4. Add `compiler/stage0/src/span.ts`: from a UTF-8 buffer and a byte offset, return 1-based `line` and 1-based byte `column`. A line ends at LF. Tests: multibyte text before the offset, offset at line start, end of file, CRLF before LF. Open question in the RFC (bytes vs scalar values) is settled as bytes here, as the RFC chooses.
- [x] 5. Upgrade path: pass source text as a separate template argument. Tests: one passing and one failing case for each rule.
- [x] 6. Add `compiler/stage0/src/catalogue-check.ts`: given the parsed `spec/errors.json` and a list of emitted codes, report any code that is missing, retired, or repeated. Node tests with fixture catalogues only. Depends on subtask 1.
