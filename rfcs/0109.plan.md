# Plan: RFC 0109 Kernel: integers, booleans, bindings, functions, conditionals, loops, text output (kernel-v47)

RFC 0109 is accepted (frontmatter). It replaces RFC 0105 (kernel-v46), amends RFC 0104 (lexical-syntax-v6) by removing the `fail` mark from `decl` and rule G10, and supersedes the kernel design of `rfcs/0085.plan.md`. This plan follows RFC 0109 and writes no code. It was checked against this session's scratch copy on 2026-11-27.

Verified with the protected counter (`sbx python3 -m tools.check.tokens --text`): the RFC's sample program costs 36 tokens without `fail` and 38 with it, as the RFC's Cost table says.

Subtasks 1 to 4 need only the lexer and parser that RFC 0104 defines. They need no checker. Subtasks 5 to 12 need the checker, which does not exist. Subtask 13 needs subtasks 1 to 12, because the checker must pass a program before codegen runs. Subtasks 13 to 19 need the code generator, which does not exist. Subtasks 20 onward need the CLI wiring (blocker B1 in `rfcs/0104.plan.md`).

## Conflicts and decisions

1. **Retirement of `kernel/print-one` is not clearly allowed (blocks subtask 22; subtask 20 keeps `print-one` green).** RFC 0109 Test plan says the implementing PR retires `print-one`. The constitution allows deleting a test only when its `rfc:` line names a superseded RFC. `print-one` names RFC 0020, and RFC 0109 does not say RFC 0020 is superseded (grep of RFC 0105 and RFC 0109 finds no 0020). Decision: option (b) from the review. Subtask 20 keeps `print-one` passing through the old skeleton path (`parser/parse.ts`, `kernel/parse-expr.ts`), and says so in its PR body. The old path is selected only for the exact `print-one` source text, and that branch is marked `ponytail:` naming subtask 22 as its removal point. Subtask 22 still waits for the architect to confirm the retirement, or to open an RFC that names RFC 0020 as superseded, as `rfcs/0085.plan.md` Conflicts 1 asked. Option (a), moving retirement ahead of subtask 20, is not chosen: the architect's confirmation is not in the repo, and this plan will not record a confirmation it does not have. When retirement is confirmed, subtask 22 deletes `print-one` and the old-path branch in the same PR.
2. **RFC 0109 L2 omits `ret` from the statement starts.** L2 lists `let`, `var`, `put`, `if`, `wh` or a name. But `ret` is a statement (Card, C2, F4, and the `ret` rule in RFC 0104 G2). Decision: `ret` also starts a statement. Architect to fix the wording of L2 in the next RFC that amends it.
3. **`fail` stays a keyword.** RFC 0104 rule 7 keeps it, and RFC 0109 open question 1 leaves the choice to the lexical owner. Decision: keep it, so `lex/kw-fail` and RFC 0104's keyword count stand. In a declaration `fail` is then E0100 at the keyword, by RFC 0104 G8 and G10 as amended.
4. **Overlap with `rfcs/0104.plan.md`.** Subtask 2 here is RFC 0104 plan subtask 7 with the `fail` alternative removed. RFC 0104 plan subtask 7's node test `f(n Int)Int fail{ret n+1}` changes: this plan's subtask 2 rewrites that node test, and the PR body says so. RFC 0104 plan subtask 13 writes the run tests of RFC 0104's table; those programs use `fail` and must be written without it, as RFC 0109 Test plan requires. The architect should note this in `rfcs/0104.plan.md`. This plan does not write them.
5. **Overlap with `rfcs/0085.plan.md` (superseded).** None of its subtasks run. Its decisions on example evaluation (Conflicts 5: one-function wasm module run in Node's `WebAssembly`) and on stable addresses (Conflicts 6: stored in the checker's symbol table only) are adopted here. Its `fail` check, `kc-fail-order`, E0403 and F7 do not apply.
6. **Parser emits E0003, not the checker.** `put`, `fail` as names (and `let put=1`) are E0003 by RFC 0104 G3. RFC 0104 plan subtask 10 owns that, and owns the rows `kc-reserved-put`, `kc-reserved-fail` and `kc-fn-put` (`put Int{ret 1}main io{}`, E0003 at `put`). This plan does not add an E0003 emitter. Subtasks 5, 8 and 9 use the parser's output and do not re-check keywords.
7. **Text literal in the parser.** T3 restricts a text literal to the whole argument of `put`. Decision: the parser accepts a `TEXT` token as a primary everywhere (so it can recover), and the checker reports E0200 at the literal (subtask 6). The parser reports E0100 only for `put` with more than one argument (P1).
8. **Step budget constant.** `rfcs/0086.plan.md` reports `types.ts` line 30 as `MAX_STEPS = 1000000000`. RFC 0109 TR3 says 10000000 per call frame. Decision: codegen uses the RFC value and subtask 16 changes the constant, with a test. Check the line before editing.
9. **Trap kinds.** TR1 defines four kinds: `overflow`, `divide-by-zero`, `stack-exhausted`, `step-exhausted`. Subtask 13 checks `types.ts` against these four. If `types.ts` has a different list, the RFC list wins and the PR body says what changed.
10. **Canonical layout of the test programs.** Each program in RFC 0109's test plan is in canonical layout (RFC 0104 rule 4). The gap check (RFC 0104 plan subtask 3) must accept them. A test that fails only because of its layout is a bug in the test, and is fixed before the feature is judged.

## Diagnostics convention

Each emitter adds its code to `spec/errors.json` in the PR that first emits it, with `code` and `meaning` only (RFC 0104 plan B4). The `meaning` is a noun phrase of at most ten words (RFC 0050 section 4). Entries to add, with the subtask that adds each:

- E0200 type mismatch (subtask 6), E0201 result clause, body does not return (subtask 10), E0202 example false or traps (subtask 19), E0300 duplicate or reserved name (subtask 5), E0301 unknown name or type or function as value (subtask 6), E0302 no `main` (subtask 5), E0303 assignment to `let` or parameter (subtask 8), E0400 effect error (subtask 11).
- E0500 exists. E0003 is added by RFC 0104 plan subtask 10.

## Subtasks

Write each subtask's tests first, as new files. Each changes fewer than 400 lines and touches one stage where it can. A subtask that touches two stages says why in its PR body. Node tests go in `compiler/stage0/src/**/*.test.ts`. Conformance tests go in `conformance/kernel/` with names `kernel/<name>` from RFC 0109's Test plan and `rfc: 0109` in the meta block. Each row of the RFC's test tables is written by exactly one subtask, here or in `rfcs/0104.plan.md` where Conflicts 6 names it. The first such subtask is the one whose feature makes the program run or fail for the stated reason. Each row below names its subtask. Byte spans use JSON `expect-errors`. Never edit an existing conformance test.
