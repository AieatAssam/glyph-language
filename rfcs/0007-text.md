# RFC draft: Text

## Summary

Add one built-in type, `text`: an immutable sequence of bytes that is always valid UTF-8. It has literals, a byte length, indexing to a byte, slicing, concatenation, and comparison. Nothing else. Code-point and grapheme handling, number formatting, and mutable builders are left to later RFCs and the standard library.

## Motivation

Checklist item 2 of the self-hosting readiness list (spec section 9) reads: "Text with indexing, slicing, comparison, and building." Stage 1 cannot start without it: the lexer, parser and diagnostic printer all consume source text, and the differential oracle compares `--dump` output, which is text.

No benchmark finding or user issue is open for this item yet (the assignment lists none). The motivation is the checklist and the stage 1 plan, not a measured failure. If a finding later shows that models mis-index text (for example by assuming code points), this RFC should be revised.

## Design

### Type and values

1. `text` is a built-in type. A value of type `text` is a finite sequence of bytes, `len` in 0 to 2^31 - 1 bytes.
2. Every `text` value is valid UTF-8. The language has no operation that produces `text` from arbitrary bytes. Byte-to-text conversion belongs to the arrays-buffers RFC, which must validate and fail with a diagnostic-level error.
3. `text` values are immutable. No operation changes a value in place.

### Literals

4. A string literal is a double-quoted token. The token rules (line structure, what a closing quote is) come from RFC 0002. This RFC adds only the escape set:
   - `\n` (0x0A), `\t` (0x09), `\r` (0x0D), `\\`, `\"`, `\0` (0x00).
   - `\u{H...}`, one to six hex digits, naming a Unicode scalar value that is not a surrogate and is at most 0x10FFFF. Encoded as UTF-8.
5. Any other backslash sequence is a compile error. A literal that contains a raw byte sequence that is not valid UTF-8 is a compile error.
6. A literal has type `text` and is stored in the module's data segment. Evaluating a literal allocates nothing.

### Operations

All operations are built in. None is overloaded for other types.

| Form | Type | Effects | Behaviour |
| --- | --- | --- | --- |
| `len(t)` | `text -> int` | pure | Number of bytes in `t`. |
| `t[i]` | `(text, int) -> byte` | `trap` | The byte at index `i`, counting from 0. If `i < 0` or `i >= len(t)`, the program traps (see rule 9). |
| `slice(t, from, to)` | `(text, int, int) -> text` | `alloc`, `trap` | A new text of the bytes `from` up to but not including `to`. Traps unless `0 <= from <= to <= len(t)`. |
| `concat(a, b)` | `(text, text) -> text` | `alloc` | A new text of `a` followed by `b`. |
| `==`, `!=` | `(text, text) -> bool` | pure | Byte equality. |
| `<`, `<=`, `>`, `>=` | `(text, text) -> bool` | pure | Lexicographic order on bytes. A prefix is less than the longer text. |

8. Indexing is by byte, not by code point or grapheme. `len` is a byte count. Code point iteration is a standard library function, not a language operation.
9. A trap stops the program with exit code 101 and writes one line, `trap: <code>`, to standard error, where `<code>` is a stable diagnostic-style identifier named in `spec/errors.json` (for example `index-out-of-range` and `slice-out-of-range`). The result is defined on every run, so no program has undefined behaviour here.
10. Effects appear in the signature. The effect names `alloc` and `trap` are those of RFC 0003; if RFC 0003 names them differently, this RFC follows its names.

### Memory

11. Text values are heap values. `concat` and `slice` allocate from the bump allocator in the current arena, as the designer guidance requires. Literals and all values built from them stay valid for the lifetime of the arena that holds them. Nothing is freed individually.
12. No reference counting. No general free list.

### Compile-time checks

13. Operands of the operations above must have the stated types. Passing a `byte` or `int` where `text` is required, or the reverse, is a compile error. There are no implicit conversions.
14. `==` between `text` and any other type is a compile error.

### Errors (new codes)

Each new code is numbered from the next free number in `spec/errors.json` at merge time and is never reused.

- Literal contains invalid UTF-8.
- Unknown escape sequence in a literal.
- Malformed or out-of-range `\u{...}`.
- Operand type mismatch for a text operation.
- Runtime traps `index-out-of-range` and `slice-out-of-range` (rule 9). These are catalogued as diagnostics so that the trap line can be checked against `spec/errors.json`.

## Alternatives

- **Code-point indexing.** Rejected. It makes `t[i]` cost O(n), and it gives two meanings to `len` depending on the operation. Iteration by code point is a stdlib function, so the one-way rule holds.
- **Grapheme handling.** Rejected. It needs large Unicode tables, which breaks the small-spec and small-compiler goals.
- **`get(t, i) -> option`.** Preferable to a trap, but `option` needs tagged unions (records-variants). Revisit when that item lands.
- **Clamping `slice`.** Total and defined, but it hides off-by-one errors. Errors are data, so a silent clamp is worse than a trap.
- **Mutable text or a `text` builder.** Rejected here. A builder is a growable byte buffer and belongs to the arrays-buffers RFC. Until then, building is repeated `concat`.
- **String interpolation or a `format` function.** Rejected. It adds a second way to build text. Number-to-text conversion is a stdlib function.

## Cost

Adds: the `text` type, the string literal escape set, six operations, and the comparison rule for `text`. Roughly 350 tokens to the core spec and roughly 120 tokens to `spec/card.md`.

Removes: nothing. It replaces nothing.

The `text` section of the card should list the operation table and the byte-indexing rule. The escape set goes in the core spec only.

Dependencies: the `int`, `bool` and `byte` types (integers-booleans-bytes), the effect syntax and trap model (RFC 0003), and the literal token rules (RFC 0002). This RFC should not be implemented before those are accepted. Until `spec/` exists, the diagnostic codes cannot be checked against `spec/errors.json`.

## Test plan

Run tests:

- `text-len-concat.toy`: `len(concat("ab", "cde"))` prints `5`. Needs `int` printing from RFC 0003.
- `text-index-slice.toy`: `"hello"[1]` and `slice("hello", 1, 3)` produce the expected bytes and text.
- `text-compare.toy`: `"a" < "b"`, `"ab" < "abc"`, `"" < "a"`, and `"é" > "z"`, using UTF-8 byte order.
- `text-escapes.toy`: each escape in rule 4 produces the expected bytes, checked by `len`.
- `text-index-trap.toy`: `"x"[1]` exits with code 101 and writes `trap: index-out-of-range` to stderr.
- `text-slice-trap.toy`: `slice("x", 2, 1)` exits with code 101 and writes `trap: slice-out-of-range` to stderr.

Compile-error tests:

- `text-bad-escape.toy`: `"\q"` gives the unknown-escape diagnostic.
- `text-bad-utf8.toy`: a literal with an invalid UTF-8 byte gives the invalid-UTF-8 diagnostic.
- `text-type-mismatch.toy`: `concat("a", 1)` gives the operand-type diagnostic.
- `text-index-type.toy`: `"a"[true]` gives the operand-type diagnostic.

Each construct in the grammar and each new code gets at least one test, as the constitution requires.

## Open questions

1. Should traps become a `fails` result once the failure model is settled? If so, indexing and `slice` change signature, and this RFC is revised with it.
2. Is `\0` needed, or can `\u{0}` cover it? Keeping both is a small redundancy. Removing `\0` saves a few tokens and one way to write the same byte.
3. Should `slice` be a view rather than a copy? A view needs lifetime rules that do not exist yet, so this draft copies.
