# Plan: RFC 0093 (integers-booleans-bytes-codes)

RFC 0093 adds nine entries to `spec/errors.json` and changes one sentence of RFC 0085. It changes no rule, grammar production, conformance test or compiler code. This plan writes no code. This PR is plan-only: it implements no subtask, and both subtasks stay unticked until a later implementer session does them. Both subtasks are small text edits, each well under 400 lines.

## Current state in this checkout

- `spec/errors.json` has six entries: E0001, E0005, E0006, E0010, E0100 and E0500. Each is one object per line with the fields `code`, `message` and `meaning`, in code order.
- `rfcs/0085-kernel-v44.md` line 183 is the sentence that C3 changes. It says that E0201, E0202, E0300 to E0303 and E0400 "have RFC 0049's meanings", and ends with "None is in `spec/errors.json` yet; the first PR that emits each adds it."
- The meanings in C1 are not yet checked against their sources in this plan. Subtask 1 checks each one against the rule it cites before writing it. This revision did not re-check them.
- `rfcs/0085.plan.md` and `rfcs/0086.plan.md` exist. Neither is changed here.

## Conflicts and decisions

1. **Status.** The frontmatter says `accepted` and the body says `Status: draft`. This plan follows the frontmatter, as `rfcs/0085.plan.md` does.
2. **The codes are permanent once merged.** Under "Never edit the spec's error codes once a code is in `spec/errors.json`", a wrong meaning cannot be fixed later. Subtask 1 checks each meaning against the rule it cites before it is written.
3. **Duplicate add steps in RFC 0085's plan.** `rfcs/0085.plan.md` subtasks 9 and 18 (lines 44 and 56) each say to add a code to `spec/errors.json`, and other subtasks in that plan may do the same. Once subtask 1 below merges, those codes are already present. Adding them again would duplicate JSON keys. This plan does not edit `rfcs/0085.plan.md`. Those subtasks should skip the add step and only check that the code is present. The architect or the next RFC 0085 plan session should make that change and check every subtask that names a code.
4. **The sentence in RFC 0085 line 183.** C3 says to change one sentence. The same sentence also says the codes are not yet in `spec/errors.json`, and that is false after this RFC merges. Subtask 2 replaces the source and removes that clause. This keeps the edit to one sentence, as C3 requires. If the architect wants the clause kept, that is a change to subtask 2 only.
5. **The core spec cap.** RFC 0093 says it cannot tell whether the catalogue counts toward the 12,000-token cap. This plan does not decide that. Subtask 1 records rule 9 of `tools.check.run` before and after the change and reports both numbers in the PR body.
6. **Tests.** RFC 0093 adds no test. Its test plan names tests from RFC 0085 and RFC 0086 (`let-var`, `kc-*`, `bytes-err-value`). None of them is in `conformance/` in this checkout, and their RFCs are not accepted. They belong to the RFC 0085 and RFC 0086 plans. This plan writes none.
