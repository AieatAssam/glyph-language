# RFC draft: Text operations

## Summary

Give the `Text` type its first operations: a byte length, a byte at an index, a byte slice, concatenation, equality, and the four ordering operators that `Int` already has. A `Text` value is immutable, always valid UTF-8, and is built only from literals and these operations. Literals and escapes are unchanged from RFC 0014. Code-point handling, number formatting and mutable builders are left to the standard library and to the memory RFC.

## Motivation

Readiness checklist item `text` (`docs/SPEC.md`, section 9) asks for "indexing, slicing, comparison, and building". Stage 1 needs to compare and slice source text, so the item is not met while RFC 0018 T3 says a `Text` value has "no operation in the kernel besides being bound, assigned and printed". No benchmark finding covers this item yet, so the case rests on the checklist and these user issues:

- Issue #69 (text ordering). Draft RFC 0026 TX6 rejects `>`, `>=` and `<=` on `Text` by citing RFC 0018 G8. RFC 0020 (accepted) has since added those three operators to the grammar and to E4 for `Int`. Test `text/order-gt.test` in RFC 0026 expects E0100, which the accepted grammar no longer gives. This draft drops the citation and gives `Text` the same four ordering operators as `Int`, so there is one operator table with one rule.
- Issue #52 (`>`, `>=`, `<=`). Accepted RFC 0020 settles the operator set. This draft follows it and does not reopen it.
- Issue #64 and issue #68 (traps in signatures). RFC 0020 E9 and TR1 say that traps carry no code and are not part of a signature. This draft follows that: the text operations list their traps in the Behaviour column, not in an effects column. If the team decides that traps belong in signatures, this draft changes with the rest of the language. It does not decide the question.
- Issue #67 (trap kinds). RFC 0020 TR1 lists four kinds, and no kind is repeated. This draft adds exactly two, one for each new failure: a bad index, and an allocation that does not fit. Neither reuses an existing kind, because each names a different condition.
- Issue #37 and issue #40 (escapes and codes). RFC 0014 gives `\n`, `\"` and `\\`, and reports any other backslash escape as E0005. This draft keeps that set, adds no escape, and does not add a diagnostic code for escapes. Issue #37 about a tab escape stays open with RFC 0014's owners.

RFC 0026 was rejected. Its vote record gives no reasons. This draft changes four things from it: the ordering operators follow RFC 0020; `text_byte` returns `Int` rather than `Byte`, because the byte type is not yet accepted; the trap kinds are catalogued in the same way as RFC 0020; and the out-of-memory case is defined, so no operation is undefined. Implementers who still see a failure should say which rule in the Design section fails.

## Design

### Values and literals

TX1. A `Text` value is a finite sequence of bytes that is valid UTF-8. Its length is set by the memory RFC. No operation makes a `Text` from arbitrary bytes. That conversion belongs to a later RFC.

TX2. A text literal is written as RFC 0014 defines it. Its escapes are `\n`, `\"` and `\\`. Any other backslash sequence is E0005. This RFC adds no escape.

TX3. A literal is stored in static data. Evaluating a literal allocates nothing.

### Operations

TX4. Four built-in functions. Each has one signature. No name is overloaded.

| Function | Type | Behaviour |
| --- | --- | --- |
| `text_len(t)` | `(Text) -> Int` | The number of bytes in `t`. Pure. |
| `text_byte(t, i)` | `(Text, Int) -> Int` | The byte at index `i`, counting from 0, as a value from 0 to 255. Traps `index-out-of-bounds` unless `0 <= i < text_len(t)`. Pure apart from the trap. |
| `text_slice(t, from, to)` | `(Text, Int, Int) -> Text` | A new text of the bytes from `from` up to but not including `to`. Traps `index-out-of-bounds` unless `0 <= from <= to <= text_len(t)`. Allocates. |
| `text_cat(a, b)` | `(Text, Text) -> Text` | A new text: the bytes of `a` followed by the bytes of `b`. Allocates. |

TX5. Arguments are evaluated left to right (E10). Then the checks in TX4 run. A failed check traps, and nothing else happens first.

TX6. The comparison rules of RFC 0020 are amended as follows.
- E3 becomes: `==` and `!=` take two `Int`, two `Bool` or two `Text` operands. Otherwise E0200.
- E4 becomes: `<`, `<=`, `>` and `>=` take two `Int` or two `Text` operands. Otherwise E0200. So `"a" < 1` is E0200.

TX7. `Text` ordering compares bytes as unsigned values, from the first byte. The first byte that differs decides. A proper prefix is less than the longer text. So `""` is less than `"a"`, `"ab"` is less than `"abc"`, and `"é"` (bytes C3 A9) is greater than `"z"` (byte 7A). Comparison does not change the operand order (E10). G6 still applies: `a < b < c` is E0100.

TX8. Indexing and slicing count bytes. There is no code-point or grapheme operation. Code-point iteration is a standard-library function.

### Traps

TX9. RFC 0020 TR1 gains two kinds, each catalogued in `spec/errors.json` by the first PR that emits it:
- `index-out-of-bounds`: an index or slice bound in TX4 is out of range.
- `out-of-memory`: `text_cat` or `text_slice` needs more space than the heap has left.

When either fires, the run behaves as TR1 says: one line `trap: <kind>` to standard error, output written before it stays, and status 1 through `proc_exit`.

### Where Text may appear

TX10. RFC 0018 T3 is replaced by this rule. A `Text` expression may appear as: the initialiser of a `let` or `var`; the right side of an assignment to a `Text` `var`; the argument of `print`; an operand of `==`, `!=`, `<`, `<=`, `>` or `>=`; or an argument of one of the four functions in TX4. Any other place is E0200, as T3 already says.

TX11. RFC 0018 T6 is unchanged. A `Text` parameter or result is E0100 at the `Text` token. Passing text between user functions waits for the memory RFC.

### Memory

TX12. `text_cat` and `text_slice` take their space from the bump allocator. Nothing is freed individually. A slice is a copy, not a view. Literal storage is never freed.

## Alternatives

- **Code-point indexing.** Rejected. `text_byte` would cost O(n), and `text_len` would count something different from the byte count. Code-point iteration fits the standard library.
- **`text_byte` returning `Byte`.** Preferable to `Int` once the byte type is accepted. Until then it would depend on an open item. Revisit when `Byte` is decided.
- **`text_byte` returning an option.** Needs variant types, which are not yet in the language. Revisit with the records-variants item.
- **Clamping `text_slice`.** Rejected. It hides off-by-one errors, and the kernel already treats bad indices as traps.
- **Slice as a view.** Rejected for now. A view needs lifetime rules that the memory RFC does not yet give.
- **`+` for concatenation.** Rejected. `+` is an `Int` operator (E6 and RFC 0020). A second meaning is the overloading the constitution forbids. `text_cat` is the only way to concatenate.
- **Ordering on `Text` only through `<`.** Rejected. It gives `Text` a different operator set from `Int`, which is a second rule for the same job.
- **One trap kind for both new failures.** Rejected. A bad index and a full heap need different fixes, and the diagnostic should say which one happened.

## Cost

Adds: four built-in functions (TX4); `Text` in E3 and E4 (TX6); the ordering rule for `Text` (TX7); the `Text` placement rule that replaces T3 (TX10); and two trap kinds (TX9). Estimate: about 330 tokens to the core spec, measured against RFC 0018 and RFC 0020. The tokeniser has not run, because `spec/` is not in this checkout.

Removes: the sentence in T3 that gives `Text` no operation, and the sentence in E3 that says `Text` has no equality. Nothing else is removed.

Spec card: about 110 tokens. One line lists the four functions with their signatures. One line says that `==`, `!=` and the four orderings work on `Int` and `Text`. The trap line gains `index-out-of-bounds` and `out-of-memory`. The card omits the copy rule and the allocator details.

## Test plan

Run tests (in `conformance/text/`):

- `len-cat.test`: `print(text_len(text_cat("ab", "cde")))` prints `5`.
- `slice.test`: `print(text_slice("hello", 1, 3))` prints `el`, and `print(text_slice("hi", 0, 0))` prints an empty line.
- `byte.test`: `print(text_byte("hello", 1))` prints `101`.
- `compare.test`: separate `if` statements, one each for `"a" < "b"`, `"ab" < "abc"`, `"" < "a"`, `"a" == "a"`, `"b" >= "b"`, `"a" <= "a"` and `"é" > "z"`, print `1` to `7`. Each `if` is written separately so that `print` needs only `Text` and `Int`.
- `escapes.test`: `text_len` of `"\n"`, `"\""` and `"\\"` each prints `1`.
- `index-trap.test`: `print("before")` then `print(text_byte("x", 1))` prints `before`, writes `trap: index-out-of-bounds` to standard error and exits with status 1.
- `slice-trap.test`: `print(text_slice("x", 2, 1))` after `print("before")` behaves the same way.
- `oom.test`: `var s = "ab"` then `while true { s = text_cat(s, s) }`. Stdout is empty, standard error is `trap: out-of-memory`, status is 1. Doubling makes the heap run out long before the TR3 counter does.

Compile-error tests:

- `bad-escape.test` (E0005): `"\q"`.
- `eq-mixed.test` (E0200): `"a" == 1`.
- `lt-mixed.test` (E0200): `"a" < 1`.
- `slice-type.test` (E0200): `text_slice("a", "0", 1)`.
- `byte-type.test` (E0200): `text_byte("a", true)`.
- `param.test` (E0100): `fn f(t: Text) { }`, to check that TX11 stays in force.
- `chain.test` (E0100): `if "a" < "b" < "c" { print(1) }`, to check that G6 still applies to `Text`.

No new diagnostic code is added. Each new trap kind has a run test that emits it, and each new operation has a run test.

## Open questions

1. Traps in signatures. Issues #64 and #68 are open. This draft follows RFC 0020 and keeps traps out of signatures. If the team decides otherwise, the Behaviour column of TX4 changes, and RFC 0025's `get` and `set` change the same way.
2. The `Byte` type. `text_byte` returns `Int` until the byte type is accepted. Then it may return `Byte`, and the test `byte.test` changes with it.
3. Text parameters and results. TX11 keeps them out until the memory decision is made.
4. Slices as copies. A view would avoid the copy, but it needs lifetime rules.
5. Tab characters in output. Issue #37 is open with RFC 0014. This draft does not touch it.
