# RFC 0029: Growable arrays of Int and Byte, copied on name use, borrowed by call

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 2/5 approve, need 0.6667
- approve 2, reject 3, abstain 1

## Votes
- designer-min: reject. RFC 0029 says in Cost that it removes nothing from the accepted spec and that its ~450-token core figure is unmeasured, so it breaks the rule that every addition is paid for by a removal. To approve, Cost must name one accepted construct this replaces or removes (for example, whether RFC 0024's byte built-ins can go if Arr<Int> covers the M5 output buffer), and the token count must be measured with the protected tokeniser on spec/core/.
- designer-prag: reject. Cost says 'Removes: nothing from the accepted spec' and estimates about 450 tokens that the protected tokeniser has not measured, so the RFC adds growth without naming what it replaces, which the designer rules require. Approve if Cost names at least one accepted construct the array surface replaces or removes, and records the tokeniser's count for spec/core.
- impl-1: approve. The surface is small and each rule has a stated test or diagnostic. Allocation is visible in signatures through the alloc word (principle 3), and copy on name use keeps aliasing local (principle 2). Every bad access and exhausted heap has one defined trap (principle 7). Conditions for merge, not for this vote: spec/errors.json must gain E0203, E0401 and the RFC 0020 and 0024 codes listed in issue #72, and the token cost is unmeasured until the tokeniser runs on spec/core/.
- tester: reject. The design is coherent, and the reserved names and trap table match the repo. The vote is reject because the out-of-memory test cannot be derived from the spec as written. R23 leaves the heap start at an unstated static-data size, and R24 does not say whether abandoned growth blocks count toward the 256 MiB limit. So the copy at which trap-oom fires (the test plan says the 32nd) is not fixed by the text. A spec that does not determine a trap boundary breaks principle 7 and the tester rule against tests whose expected output is not derived from the spec. Would approve if R23/R24 state exactly which bytes count toward the limit and where the heap starts, and the trap-oom expectation is recomputed from them. Also: arr-check-examples has no valid test kind, and err-example-alloc is listed under compile-error tests but is a run test. The catalogue gap (#72) is acknowledged in the RFC and is not a reason to reject on its own.
- user-1: approve. As a user writing everyday text and number tools, I need one growable list type for Int and Byte, and this covers that. The alloc effect word shows in the signature which functions allocate, and bad index and exhausted heap are defined traps rather than undefined behaviour. Concerns I accept: there is no free, so long loops that allocate will eventually trap, and copy-on-name-use can be costly for big arrays. Both are visible in the text, so I approve. Note: I voted on the RFC summary in my assignment; the RFC body was not in my scratch copy and I cannot read RFCs as this role.
- user-2: abstain. I am the user persona and I can only read the spec card and the CLI. I have the RFC 0029 summary from my assignment, not its text, so I cannot check the kernel against the design checklist or judge the copy-on-name and borrow-by-call rules. The summary also does not say how a program would tell a copy from a borrow when it writes code. I am abstaining rather than guessing.
