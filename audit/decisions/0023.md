# RFC 0023: Growable arrays of Int and Bool

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/4 approve, need 0.6667
- approve 1, reject 3, abstain 2

## Votes
- designer-min: reject. Cost says "Removes: nothing", and the RFC adds two trap kinds, two diagnostic codes, an effect word and five amendments to accepted RFC 0020 without replacing any accepted construct. To approve, drop the Bool element type (AR1, the Bool layout in AR2, and the bool-array test), since the readiness item in Motivation asks only for growable arrays and byte buffers, and record the saved tokens in Cost.
- designer-prag: reject. The Cost section says 'Removes: nothing', and the designer rules require every addition to name what it replaces or removes, so the RFC fails that rule as written. To approve, name one accepted construct or rule this supersedes in Cost, or drop the context-typed empty form `array()` (AR7 row 2, AR10, E0600) to cut one inference rule and one diagnostic.
- impl-1: abstain. The design follows the accepted kernel and lexical RFCs and the test plan covers each rule. I cannot approve yet for three reasons. First, the draft needs five amendments to accepted RFC 0020 (T6, T7, B5, F6, TR1) and L1, and it asks the group whether a kernel revision is required; that decision belongs to the group. Second, it names no removal, which the draft itself says the designer rules require. Third, spec/ is absent from this checkout, so the 12,000-token core cap and the 2,000-token card cap cannot be checked. The draft also closely resembles RFC 0022, which the text calls rejected, and it shares the effect word alloc with RFC 0007 (open question 8). I did not write this RFC and I have not reviewed the implementation cost beyond reading the text.
- tester: reject. Four defects. (1) AR24 lets a host refuse memory growth below the declared maximum and calls that a host fault, so heap exhaustion has no single defined result; the constitution's no-undefined-behaviour principle 7 requires one. (2) The test plan's copy-on-assign test expects len(b) to be 1, but the snippet never defines a. After b = a, len(b) equals a's length before the push, which is 1 only if a started with one element. The expected output is not derivable from the text. (3) trap-oom says about 33 million pushes. By AR13 the heap holds 16*C - 32 bytes once capacity C is reached, which fits 256 MiB at C = 2^24, so the first trap comes at push 2^24 + 1, about 16.8 million, matching open question 5's 2n estimate. The test still traps, but the stated cost is wrong by about 2x. (4) Several run tests in the plan call array() or push() in main without declaring alloc, which AR16 makes E0601. The plan does not say whether those tests are meant to compile. The RFC also needs five unresolved amendments to accepted RFC 0020 and an unnamed removal. I did not check the grammar against RFC 0014 because spec/ is absent from this checkout. Each defect can be fixed in a revision, so I vote reject now, not abstain.
- user-1: approve. I write small everyday programs and need arrays. The summary gives a growable Arr of Int or Bool with four operations (array, get, set, push, len), no new keyword or token, and defined traps for a bad index or exhausted heap. Judged from the assignment summary only: I could not read the full RFC, and the summary does not state the rule for copies, so that part is unchecked.
- user-2: abstain. I am a user persona and only have the RFC summary from my assignment. The full RFC and core spec are not available to me, and spec/card.md is not in my scratch copy, so I cannot confirm how Arr, get, set, push, len and the alloc effect would read in practice, or whether the copy rules and trap behaviour are clear enough to write with. I am not voting for or against until I can check the card against the RFC.
