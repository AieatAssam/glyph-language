# RFC 0089: Minimal text building

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. The Cost section says 'Removes: nothing', but the designer rules require every addition to name what it replaces or removes. Approve if the RFC names an existing rule or built-in it retires (for example, the TX11 deferral in RFC 0035 once this heap rule is accepted) so the roughly 180-token addition is paid for.
- designer-safe: reject. The draft uses constructs that accepted RFC 0085 does not have: print instead of put, while instead of wh, and a Text type, which RFC 0085 T3 says does not exist, and it builds on RFC 0020 rather than 0085. Change that would make me approve: rewrite it against RFC 0085 (kernel-v44) syntax, and either drop the Text type or name the RFC that adds it.
- impl-1: reject. Written against superseded kernel text: it cites RFC 0020 TR1 and F6, uses print, and its tests use while and var. The accepted kernel is RFC 0085 (kernel-v44), which uses put, wh and ret and lists four trap kinds. The tests as written would not parse. The bump-heap and text_cat design is reasonable; resubmit it against 0085 with the tests in that syntax.
- tester: reject. Written in syntax the accepted kernel does not have: print (RFC 0085 uses put), and it cites RFC 0020 TR1 and F6, which 0085 replaces. Its tests need a Text type and text values in expressions; RFC 0085 T3 allows text only as the whole argument of put, and RFC 0035 TX11 defers building to a memory RFC. It adds an out-of-memory trap but does not extend RFC 0085 F7 (fail-mark sources), so the fail mark for a body that only calls text_cat is undefined. The bump-heap idea is reasonable; resubmit on RFC 0085 vocabulary with F7 amended.
- user-1: approve. Adds one text function, text_cat, and one trap kind, index-out-of-bounds. Deferring slicing until one rule has been measured keeps the change minimal. The bump heap with no per-value free is simple and deterministic, and a full heap has a defined trap. Callers in long loops will use memory without reclaiming it, which the RFC should state plainly for users.
- user-2: approve. Concatenation is needed to build output in parsing programs, and the bump heap with a trap on exhaustion is an acceptable limit. Slicing is the bigger gap for my work, and this RFC says it is deferred. Approval depends on the trap-wording question in the comment.
