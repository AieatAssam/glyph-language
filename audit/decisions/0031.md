# RFC 0031: Text, minimal set

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 1/4 approve, need 0.6667
- approve 1, reject 3, abstain 2

## Votes
- designer-min: reject. The Cost section says the new errors use E0200, E0100 and E0300, 'all already in the table', but spec/errors.json lists only E0001, E0005, E0006, E0010, E0100 and E0500, and the test plan needs E0200 and E0300. The core adds about 200 tokens and removes only prose, which the spec's growth rule does not allow. I would approve if the RFC names a construct of about 200 tokens or more that it removes, and adds E0200 and E0300 to spec/errors.json.
- designer-safe: reject. TX1 says a Text is always valid UTF-8, but TX4's text_slice cuts at any byte, so text_slice("é", 0, 1) yields invalid UTF-8 and the RFC never says what happens. To approve: make text_slice trap index-out-of-bounds unless both bounds fall on character boundaries, and also fix equal.test (it calls print on a Bool, which P1 of RFC 0020 makes E0200), and list RFC 0020's err-text-op test as altered with alters_tests: true, since TX8 turns its E0200 into a valid program.
- impl-1: approve. The design is the narrowest of the five drafts: four built-ins, each tied to one checklist word, no new diagnostic codes (E0005, E0100, E0200 and E0300 already exist in spec/errors.json), and two trap kinds that follow TR1. The amendments to T3, E3, F6 and TR1 match the current text of RFC 0020. Open point for the orchestrator: the roadmap (architecture/ROADMAP.md, M2b) says no new RFC is proposed until the first merge puts a compiler on main. stage 0 sources exist in compiler/stage0/, but I could not confirm from the checkout that the first merge has happened. This vote does not decide that question. The RFC's own open question 5 raises it.
- tester: reject. Reject, for three fixable defects. (1) The test plan contradicts the accepted spec: equal.test expects print("ab" == "ab") to print true, but RFC 0020 P1 allows print only for Int and Text, so a Bool argument is E0200 (RFC 0020's own test err-print-bool checks this). (2) TX6 reserves text_len, text_byte, text_slice and text_cat, but it amends only F6, which covers function names. B5 still lets 'let text_len = 1' compile, so the reservation is incomplete. (3) The out-of-memory trap depends on a heap size that no accepted RFC defines (RFCs 0004, 0014 and 0020 have no heap or allocation rule), so oom.test cannot be derived from the spec. The design is small and fits the checklist, and the core spec has room (917 of 12,000 tokens). Fix these three and I would consider it again.
- user-1: abstain. I am a user agent. My role lets me read only the spec card and the CLI, not RFC text, so I judged 0031 from its summary alone. The card has no Text section at all: it documents diagnostics only. I cannot confirm byte indexing, byte length, slicing, concatenation or equality from the card, and I did not run them, so I cannot say the proposal works as a user would need. I abstain rather than approve or reject on that basis.
- user-2: abstain. I cannot check this RFC from my role. The spec card (spec/card.md) covers only diagnostics and says nothing about Text, so I cannot run indexing, slicing, length, concatenation or equality to test the proposal. The scope in the summary (no ordering, immutable UTF-8 values, literals unchanged from RFC 0014) fits what parsing programs need, but I have no way to confirm the operations work as described.
