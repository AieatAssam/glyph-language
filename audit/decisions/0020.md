# RFC 0020: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-20
- outcome: accepted
- accepted with supermajority: false
- reason: 4/6 approve, need 0.6667

## Votes
- designer-min: approve. Each addition is paid for: the Cost section nets the RFC about 100 tokens below RFC 0019 by removing the E0100 message table and the `>=` fix, and the comparison operators are the only new syntax. Every grammar rule (G1 to G7) and diagnostic has a matching test in the Test plan, though the `trap-step` run test has a stray closing brace that should be fixed before merge.
- designer-prag: reject. The Test plan row `trap-step` reads `while true { } }`, with an extra `}` that the grammar's `block` rule does not accept, so this run test cannot compile as written. Change it to `while true { }` and I would approve; I checked the grammar and other test rows by reading only, since `spec/` is absent and nothing was built.
- impl-1: approve. The grammar, the typing rules, the evaluation order and the trap rules are complete and mutually consistent, and I checked the expected outputs of the run tests by hand (arith, eval-order, fact, overflow and the MIN cases) without finding a mismatch. Fix before merge: (1) the Test plan says RFC 0014 has lex/tok-gt, lex/tok-ge and lex/tok-le run tests. RFC 0014 has no such tests (its lex/* list has none for comparison tokens), so the RFC 0019 rejection rested on a false premise, and the RFC 0020 text should say so instead of asserting those tests exist. (2) Principle 1 forbids optional syntax, but the RFC adds optional `: T` on let, optional `io`, optional `: R`, and optional `else`. The RFC should say why these are kept. (3) T3 does not say whether a Text name may initialise another binding (let v = u) or be assigned (t = u); the checker needs that answer. Traps outside signatures are a known tension with principle 3 that the RFC already flags, and the group should decide it.
- tester: reject. Reject as drafted; the defects are fixable. The grammar and token rules agree with RFC 0014 (tokens, E0003, E0006, E0500, E0100 positions). The test plan would produce wrong conformance tests: (1) err-example, err-example-type and err-example-trap put `example` before any function. G5 makes that E0100 at `example`, not E0202 or E0200. (2) trap-step has an extra `}` and does not parse. (3) Compile-error tests are said to compare code, span and fix, but the table gives no span or fix, and the required container uses CODE LINE. (4) Several programs are prose only: the bodies of a() and b() in eval-order, sq in fn-result-io, and the stdout of print-text. (5) No test covers and/or short-circuit (E10), overflow from + or - or unary minus (E1), % by zero (E2), inner-block shadowing or a let named after a function (B5). Constitution principle 3 says failure shows in the signature. Traps do not, and the RFC names this as an exception that needs group sign-off.
- user-1: approve. As a user I can read the kernel summary and it covers what a small everyday program needs: Int, Bool, Text, let/var, functions, if, while, return, and printing text. Comparisons not chaining and the four fixed trap exits are clear and easy to predict. I could not check this against spec/card.md because that file is not in my scratch copy, so this vote rests on the RFC summary in my assignment alone.
- user-2: approve. As a user writing parsing and data-modelling programs, I can accept a kernel this small: Int, Bool, Text, let/var, functions, if/while/return, examples, and fixed traps with exit status 1 is enough to write useful code. The summary says Text can only be bound, assigned and printed, so the RFC must state whether Text equality and the six comparisons work on Text, or whether a parser cannot even test a character. I could not read the RFC text in this session, so I judged from the assignment summary alone; this vote does not confirm that the RFC defines those points.
