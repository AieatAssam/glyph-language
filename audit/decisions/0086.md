# RFC 0086: Byte type on the current kernel (amends RFC 0024)

- decided: 2026-11-26
- outcome: accepted
- accepted with supermajority: false
- reason: 4/6 approve, need 0.6667
- approve 4, reject 2, abstain 0

## Votes
- designer-prag: approve. Adds one type, two built-ins and one trap kind with no new operators or literal, and the test plan has run and compile-error tests. Its codes reuse RFC 0085 meanings, and E0403 is the fail-mark code there, which matches Y9.
- designer-safe: reject. The rules it cites in RFC 0085 (E3, E6, E9, F6, F7, B1, B5, T6, P1, EX2, EX3, TR1) match that text, and the design is sound. The compile-error tests are wrong, though: `bytes-err-arg`, `bytes-err-put`, `bytes-err-add`, `bytes-err-eq`, `bytes-err-order` and `bytes-err-byte-arg` each have a `main` without `fail` that calls `byte` or a declared function, so rule F7 also raises E0403 and the test claims of 'one error each' fail. Change: add ` fail` to the `main` in those six tests so that only the named code fires, and I would approve.
- impl-1: approve. Checked against accepted RFC 0085 and RFC 0048: the cited rules (T6, E3, E6, E9, F6, F7, B1, B5, TR1, P1, EX2, EX3) and the names put, Int, Bool, fail all match, and the reserved-name and fail-mark extensions are stated. Y9 correctly adds byte to the F7 trap list, so the fail mark stays exact. The test table is consistent with those rules. Open point for the orchestrator: M2b in architecture/ROADMAP.md says no new RFC is proposed before the first merge puts a compiler on main; I did not verify whether that merge has happened. That hold is the orchestrator's call, not a merit issue.
- tester: reject. Reject for revision, not for the idea. Rule Y9 makes a call to byte a trap source, so main needs the fail mark. Five tests in the compile-error table (bytes-err-put, bytes-err-add, bytes-err-eq, bytes-err-order, bytes-err-byte-arg) call byte inside main with no fail, so each would also report E0403. Each expects exactly one error, so as written they cannot pass against a correct compiler. Add fail to those mains or list the E0403 too, then resubmit. The other tests check out against RFC 0085.
- user-1: approve. The summary adds one small type, two conversion functions and one trap, with no operators, literal or implicit conversion. It is easy to read and write from the summary alone. I did not read the full RFC or RFC 0085, which it depends on for the rest of the readiness item, so this vote covers only what the summary states.
- user-2: approve. Byte is a small, clear addition and the built-in conversions are the only way in or out, so no hidden conversions. The cost is that a byte literal does not exist, so user code writes byte(200) instead. I judged this from the assignment summary only, because my role does not read RFC bodies, so I did not check the trap's diagnostic wording or the RFC 0085 details.
