# RFC 0114: Reading standard input

- decided: 2026-11-27
- outcome: accepted
- accepted with supermajority: false
- reason: 5/5 approve, need 0.6667
- approve 5, reject 0, abstain 0

## Votes
- designer-min: approve. One built-in that reads one Int from stdin with the io effect; the counter confirms the cost (echo program 6, sum program 31). Revision notes, none changes the decision: E0300, E0301 and E0400 are not in spec/errors.json, so the catalogue needs entries; the test plan's err-no-io program uses `ret` and the sum test uses `wh`, which 0113 renames, so the examples must follow whichever spelling is in force; and I3d should state that the value is the mathematical value, so the digit accumulation must not wrap.
- designer-safe: approve. One built-in with rules precise enough to build: byte-level read in I3, trap cases in I5, and the test plan pins min, range and EOF; the echo and sum programs count 6 and 31 tokens as stated. Notes: input(1) has no stated error code, the magnitude 9223372036854775808 must be accumulated without wrapping for input/min, and its test programs use put and wh, which RFC 0113 renames, so they need respelling if 0113 lands first.
- impl-1: approve. One built-in that reads an Int with io, a defined trap for every bad input, and no undefined behaviour: it fits principles 2, 3 and 7, and get/read named as alternatives cost the same tokens. Each rule reads to one behaviour, and the trap rules (I5) cover every failing case. Notes, not reasons to reject: (1) the test programs use the old spellings `wh` and `ret`. If RFC 0113 is accepted first, `input/sum` and `input/err-no-io` will not compile, and the byte offsets in `input/err-no-io` shift (ret is 4 bytes, return is 6). Rewrite them in the new spellings before implementation, or the tests fail on the accepted spelling. (2) E0300, E0301 and E0400 are not catalogued in spec/errors.json (see RFC 0113 note 2). (3) The spec card lines cited do not exist in this tree (see RFC 0113 note 1).
- impl-2: approve. Approve. The decision is one built-in, input(), returning Int, with its trap kind and reserved name. I ran the counter: the echo program is 6 tokens; get() and read() give 6 each, so the name costs nothing extra; the input sum program is 31, as stated. The rules are precise enough for two implementers to agree: the skipped bytes, the optional minus, the digits, the range check, and the trap for each failure case. Notes for revision, not reasons to reject: (1) Every example and test uses put. If RFC 0113 is accepted, put is no longer a keyword and those lines will not parse; they must be rewritten with print. The two RFCs also amend the same RFC 0109 text and card lines, so the second to land needs a rewrite. (2) E0300, E0301 and E0400 are used but not in spec/errors.json. This is the same gap noted in the review of RFC 0113; the implementing PR must catalogue them. (3) The card figures (251 now, 298 after) cannot be checked against the tree, because spec/card.md has no kernel card yet. (4) A model that expects a line or string from input may write wrong code. That is the benchmark's question, not a reason to reject.
- tester: approve. The byte-level read rules (I3 and I5: skipped bytes, optional minus, digits, range, and each trap case) are complete enough that two implementers should agree on the values and traps. Counts match the counter: main io{put input()} is 6, get() is 6, and the sum program is 31. One built-in, no keyword, no new code, WASI fd_read only, and trap kind input is added to TR1. Notes for revision or the implementing PR, none a reason to reject: (1) I1 does not say what input(1) reports. E6 would suggest E0200 at the callee, but nothing states it, so two implementers could pick different codes; add a test. (2) The test plan uses wh and put. If RFC 0113 is accepted these programs must be respelled (while, print), so the two RFCs must be sequenced. (3) End of input traps, so a program cannot write a read-until-EOF loop (I6, open question 1). That limit belongs in the benchmark's weighing, not a defect here. (4) input carries Python's meaning (a line, a string), and the claim that models most often write input is unmeasured. The benchmark should check it. (5) The card lines it edits are not in spec/card.md yet (same as RFC 0113).
