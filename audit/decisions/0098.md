# RFC 0098: Close readiness item integers-booleans-bytes on RFCs 0085 and 0086

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-prag: reject. RFC 0085's header says it needs prerequisite `retire-print-one`, which is 'not yet opened', and its body says 'Status: draft', so C1's 'accepted and in force' is not met. Approve if C1 names `retire-print-one` as a gate and issue #509 (the status conflict) is resolved first.
- designer-safe: reject. C1 says the item is met once RFC 0085 and 0086 are accepted, but the Motivation says it cannot be called met until the C4 card lines land, and the Test plan says the named tests must exist before it is marked met; the card has no kernel section and conformance/ has no bytes tests yet. One change would make me approve: rewrite C1 so the item is met only when the C4 card lines are in spec/card.md and the Test plan tests exist.
- impl-1: approve. Adds no language construct. Its C2, C3 and C4 match RFC 0086 Y4, Y12 and the card lines of RFC 0085 K1 and RFC 0086 Card. Its trap list matches RFC 0085 TR1. Caveat: it rests on RFC 0085, whose front matter says accepted but whose body says draft with open gates (issue #509). The RFC's own open question 1 keeps the item open if #509 changes that status, so approval is conditional on that.
- tester: reject. Reject as written. The design is sound: no new construct, and C2 (no == or != on Byte) and C3 (no addresses for built-ins or Byte) follow RFC 0086. The item is not ready to be declared met. (1) The Summary says the RFC 'declares the item met' now. Motivation, C4 and the Test plan say the item cannot be called met until the card lines and the named tests exist. (2) Neither exists: spec/card.md has no kernel or byte lines, and conformance/ holds only print-one.test and v4-lf-only.test, so bytes-convert and bytes-err-arg are absent. (3) It does not cite accepted RFC 0093, which catalogues E0200, E0201, E0202, E0300 to E0303, E0400 and E0403. spec/errors.json has six entries, so the catalogue rule fails without 0093. (4) It says four earlier drafts were rejected and names three; RFC 0093 names RFC 0088 as the fourth. (5) C1 rests on RFC 0085 being in force, but 0085's body says draft with gates G-b and G-c open, which the RFC's own Open question 1 admits. A revision that fixes (1), (3) and (4), and says plainly that the item stays open until C4 and the named tests land, is worth approving.
- user-1: abstain. As a user I read only spec/card.md, and it shows no integers, booleans, bytes or types at all, so I cannot check from my side whether the item is met. I have not read RFCs 0085 or 0086 and cannot confirm that their text covers overflow and the other points. I abstain rather than approve something I cannot see.
- user-2: reject. As a user I can judge RFC 0098 only from spec/card.md, which has no entry for Int, Bool or Byte, and says nothing about overflow. The RFC itself lists card and test checks as still needed, so the readiness item is not yet met for a user. Closing it now would record it as done too early. I did not read the RFC 0085 or 0086 text, which I am not allowed to see.
