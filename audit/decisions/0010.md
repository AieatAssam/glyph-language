## Votes
- designer-min: reject. The Cost section says 'Removes: nothing', but the designer rules require every addition to name what it replaces or removes. Change to approve: remove the `pop` built-in and its `pop from empty array` trap, since no example or stated stage-0 or self-hosting need uses `pop`.
- designer-prag: reject. Cost states that it removes nothing, and designer rules require every addition to name what it replaces or removes, so the RFC breaks a stated rule and says so itself. Approve if Cost names at least one existing construct this replaces or removes, or if the RFC is deferred until spec/ exists and the tokeniser has measured the core against the 12,000-token cap.
- impl-1: reject. Reject as written. The rules and tests depend on constructs that no accepted RFC defines: var, while, return and if from RFC 0005 (rejected), and Int and Bool from RFC 0009 (not decided). Rules 4 to 19 cite E0100, E0102 and E0104 as existing codes, but no accepted RFC or spec/errors.json defines them in this checkout. Rule 11 uses max(), which the language does not define. The test plan says what each test must observe (for example a[2] is 3) but not how the value is seen, since print for Int is a kernel feature and is not accepted. A resubmission should name its prerequisites, define the codes it uses, and say how tests observe values, for example with examples. The copy, borrow and bump-allocator design is otherwise coherent, and I would review a resubmission on that basis.
- tester: abstain. The array rules are internally consistent and most tests can be derived from the text. Two points are not settled. First, the RFC depends on kernel terms that exist only in RFC 0005, which is rejected: E0102, E0104, print, the trap mechanism and exit status 3. Second, the trap-oom test is described as about 33 million pushes, but that figure is not derived from the 256 MiB limit and the doubling growth rule with a no-free bump allocator, so the expected behaviour is unchecked. I cannot approve a test count I could not derive, and I have no design objection that justifies a reject. Abstaining until the kernel dependency is settled and the OOM test's expected behaviour is derived.
- user-1: abstain. I only have the summary in my assignment, not the RFC text. The summary is narrow and defines a trap for each failure case, which is a good sign. But I cannot check the !alloc rules, value semantics or the bump allocator details, and a no-free heap matters for long-running programs. I abstain until I can read the full text.
- user-2: abstain. I can only see the summary in the assignment, not the full RFC text, and spec/card.md is missing from my scratch copy, so I cannot judge the array semantics or the bump allocator against anything a user can read. It also depends on Int and Bool from RFC 0009, so its vote should follow 0009's outcome.
