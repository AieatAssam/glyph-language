# RFC 0094: Growable Int arrays with no sharing

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 1/6 approve, need 0.6667
- approve 1, reject 5, abstain 0

## Votes
- designer-min: reject. Cost says "What it removes: nothing" and leaves the 12,000-token cap to a later RFC, so the additions are not paid for. To approve: name the existing construct or spec section this replaces or trims, with the core and card counts measured by the tokeniser, and add a run test for rule 12 (a returned local moves its block), which no test covers.
- designer-prag: reject. No benchmark finding or open issue shows a need for arrays: the only diagnostic row is UNKNOWN (540) and the RFC itself says so. To approve, the author must cite a finding or user issue that needs `[Int]` now, and add the heap-exhaustion run test (rule 15), which the test plan lists only as an open question, since the constitution requires every construct to be tested. The `arr(Int)` form, which takes a type name as an argument, is also a special case that works against principle 1.
- impl-1: reject. It contradicts the lexical RFC it builds on. RFC 0014 (rule 10 and Rejected alternatives) removes the tokens '[', ']', '->' and bare '!', and says the result type is written with ':'. RFC 0094 needs '[' and ']' for [Int] and a[i], and writes '-> Int !alloc', so it needs '->' and '!' as well. Its header says 'Amends: nothing', which is false. Kernel RFC 0085 writes results as ': Int' and effects as the keyword 'io'. The fix would be an amendment to RFC 0014 that names it, with '!alloc' rewritten as a keyword, and a resubmission. Its other rules are not reviewed in depth here.
- tester: reject. Four blocking problems. (1) Lexing: lexical-syntax-v4 (RFC 0048, which RFC 0085 depends on) makes `[`, `]` and `!` E0001 (its rule 11), and it has no `->` token. The RFC's own syntax uses `[Int]`, `a[i]`, `!alloc` and `-> Int`, so the productions it adds cannot parse under the accepted lexical rules. (2) Base: it builds on RFC 0014 and RFC 0020. RFC 0085 (kernel-v44) replaces the RFC 0020 kernel, and the item's kernel is 0085. The RFC says it amends nothing, yet it adds two trap kinds to TR1 and productions to the kernel. TR1 in RFC 0085 is a closed list of four kinds, so this is an amendment and must name RFC 0085. (3) Principle 7: heap exhaustion traps only when growth would exceed the module's maximum memory, and the RFC leaves that maximum open (its Open question 2). Whether a program traps then depends on the implementation, which the constitution forbids. (4) Tests: the test plan writes `print`, which RFC 0085 replaced with `put`. It tags `arr-index-trap` as kind run, but that test expects a trap on standard error, which is kind trap, and the container has no standard-error block. Nothing tests a positive parameter view, returning an array (rule 12), or a positive `!alloc` function, though the RFC adds productions for each. The codes E0700 to E0703 are also not catalogued. I would reconsider on a revision that uses the RFC 0085 base and lexical-syntax-v4 tokens, fixes the heap maximum, and corrects the test kinds and the `put` form.
- user-1: reject. The four new codes, E0700 to E0703, lie outside every range spec/card.md lists (E0001-E0599 are the only ranges given), so a user reading the card cannot tell what they mean or where they belong. The RFC should place them in a range the card names, or extend the card's range list in the same change. Resubmission with that fixed is welcome.
- user-2: approve. A data-modelling or parsing program needs a growable list, and this gives one with defined traps for out-of-range index and heap exhaustion. The no-sharing rule keeps the meaning of a call readable from its text. Two concerns, neither blocking: the card lists code ranges only up to E0599, so E0700-E0703 sit in a range the card does not describe; and storage is never freed, so a long parse may hit a trap that a user cannot avoid except by splitting the work. I could only judge the summary, not the full text.
