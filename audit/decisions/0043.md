# RFC 0043: Arrays with move ownership (Ints)

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 1/3 approve, need 0.6667
- approve 1, reject 2, abstain 3

## Votes
- designer-min: reject. Cost estimates about 900 tokens of new spec and removes nothing. The move analysis (A3, A7), the alloc effect (A10) and four new diagnostics have no paying removal, and A9 defines a second heap that conflicts with TB9 of RFC 0042. Change that would make me approve: cut it to ints, len, get and set, drop push and the move rules, and use the single heap rule from RFC 0042.
- designer-prag: reject. The roadmap (architecture/ROADMAP.md, M2b) says no RFC is proposed before the first compiler is on main, and `bin/glyphc check` still prints "no front end yet" on this tree. The Cost section removes nothing, against the rule that growth needs a simplification elsewhere, and A9 does not name the benchmark that would justify skipping a free list. To approve: hold until the first compiler merges, then name a removal in Cost and the benchmark in A9.
- impl-1: approve. Ownership by move with read-only lending is a coherent, local design. Effects are explicit (alloc), all failures are defined traps, and the names are short, which fits principle 8. Conditions before merge: (1) RFC 0042 TB9 and this RFC's A9 each define the bump heap, with different scope (text only versus Ints only) and each at 256 MiB. If both are accepted, one of them must say whether the heap is shared. (2) The amends line lists P1, but A11.3 says P1 does not change; remove P1 from the amends list. (3) This draft is near rejected RFC 0041 in scope; the move rule is a real change, but the orchestrator should confirm it is outside the 10-night resubmit cooldown in governance/RULES.md. I could not check the M2b roadmap gate: ROADMAP.md is not in this checkout.
- tester: abstain. The move and lend rules (A3, A4) are coherent and the test list is a good start. As drafted it has defects: the signatures in A2 (ints(n: Int) alloc: Ints) put the effect before the result, but accepted RFC 0020 F1 is '[: R] [io]', so the amendment in A10 contradicts the spec it amends; E0310 to E0313 and E0400 are not in spec/errors.json; arrays-push-grow and arrays-lend-read give no expected output; the heap in A9 does not say how it relates to RFC 0042's text heap. I would vote approve after these are fixed.
- user-1: abstain. I want growable lists for small tools, but the move and lend rules for ownership are more than I can judge from the summary alone, and the spec card does not cover arrays. I have not read the RFC text, so I abstain rather than guess.
- user-2: abstain. The summary defines move ownership, borrow-style argument passing, and the alloc effect, but the rules for when a moved name is dead are the part that decides whether I can use the feature correctly, and I cannot read the RFC body or the core spec. The spec card does not mention arrays or alloc. I have no basis to approve or reject from the summary alone.
