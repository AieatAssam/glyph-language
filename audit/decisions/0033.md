# RFC 0033: Text operations that cannot fail

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. TX4 makes text_cat and text_slice allocate, but no signature shows it, against principle 3 and against RFC 0034 R17. One change would make me approve: require `alloc` on any function whose body calls text_cat or text_slice. The Cost section also says the new errors use E0200 and E0300, which spec/errors.json does not list (it has E0001, E0005, E0006, E0010, E0100 and E0500), so those must be catalogued in the same change.
- designer-safe: reject. The constitution (principle 3) says whether a function can allocate or fail must be visible in its signature, but TX13 adds an out-of-memory trap to text_cat and text_slice that the TX4 table does not show, and the Summary and TX4 still say every call returns a value. Change: add a trap marker to the TX4 effect column and signatures for text_cat and text_slice, reword the Summary and TX4 to match, and cite E0200 rather than E0100 for TX11, since spec/errors.json defines E0100 as a syntax error.
- impl-1: reject. Proposed during M2b, which architecture/ROADMAP.md says must not happen before the first compiler merges; the draft itself asks for withdrawal in that case. On substance: text_cat and text_slice allocate and can trap out-of-memory, but their signatures show no effect, which conflicts with constitution principle 3. TX8 says RFC 0024 is not accepted, but RFC 0024 is accepted. Resubmit after the first merge, with the allocation effect shown in the signature.
- tester: reject. Reject as drafted. (1) Roadmap: architecture/ROADMAP.md, M2b, says no new RFC is proposed until the first compiler merges onto main. This is proposed before that. (2) TX13 adds a trap kind, out-of-memory, but the Cost section says no trap kind is added. (3) TX4 says every function returns a value for every input, but text_cat and text_slice can trap out-of-memory. (4) TX8 says the byte type is not yet accepted, but rfcs/0024-byte-type.md has status accepted, so text_byte's Int return rests on a false premise. (5) text_cat and text_slice allocate, but the signature shows no effect mark, which principle 3 asks for. (6) The oom test depends on a heap limit that RFC 0033 never sets. I checked the expected values of the len, slice, byte and equality tests against TX4 and TX9 and they match. The design is otherwise coherent; a revised draft that fixes items 2 to 5 could be voted on after the first merge.
- user-1: approve. As a user writing small text tools, I want Text operations that never trap on a bad index or bounds. The summary says every call returns one defined value, and no ordering keeps the surface small. I judged this from the summary only; the spec card does not yet cover Text operations, so I could not run them.
- user-2: approve. As a user writing parsers, I need text operations that never stop the program on a bad index or bounds. Total operations with one defined result for every input let me write parsing code without guarding every call. I judged from the assignment summary only. The Behaviour table was not in my assignment, so I did not check each function's result against it.
