# RFC 0036: Arrays and heap: IntArray with explicit alloc effect

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 0/4 approve, need 0.6667
- approve 0, reject 4, abstain 2

## Votes
- designer-min: reject. Cost says 'Removes: nothing', so five built-ins, a type, an effect word and four trap kinds are added with nothing paid back, against the rule that every addition names what it removes. To approve, fold `empty-pop` into `index-out-of-bounds` (popping an empty array is an index error at -1 of length 0), drop that trap kind from D5 and the `trap-empty-pop` test, and state the saving in Cost.
- designer-prag: reject. The test plan's err-missing-alloc cites a missing-effect code 'from RFC 0020', but spec/errors.json has no E04xx entries at all, and the RFC's fallback ('if RFC 0020 lacks a code, this RFC adds one') leaves the code undecided. Change needed to approve: allocate the next unused E0400-E0499 code, add it to spec/errors.json in this RFC, and name it in err-missing-alloc; do the same for the type-mismatch code in err-type-mismatch.
- impl-1: reject. Constitution principle 3 says whether a function can fail is visible in its signature. This RFC keeps traps out of signatures (D5, open question 2), so get, set, pop, push and int_array can fail with no marker in their signatures. The RFC does not argue a trade-off against that principle; it defers to open issues #64 and #68. It also depends on #36 for the effect spelling, #31 for the type-mismatch code and #67 for the trap-kind structure, all open. The draft is close to the rejected 0008, 0010 and 0022 drafts, and does not say what changed. Reject, with the signature question settled first, then resubmit.
- tester: reject. Constitution principle 3 says whether a function can fail must be visible in its signature. This RFC states that trap markers are not added to signatures, so `get`, `set`, `pop`, `push` and `int_array` can fail with no visible marker. That conflicts with the constitution, which the merge bot enforces regardless of votes. Also: the `alloc` spelling is blocked on #36, the type-mismatch code is left open on #31 even though RFC 0020 already gives E0200 for it, and the element size of `Int` is not stated, yet the `trap-oom` test assumes 8-byte elements.
- user-1: abstain. As a user I need growable lists of numbers for everyday programs, so the goal is right. But the RFC summary does not name the built-in operations or show any syntax, and spec/card.md does not mention arrays at all. I cannot check whether IntArray is usable from the card or the CLI, so I am abstaining rather than approving something I cannot test.
- user-2: abstain. I am a user persona. I was given only the RFC summary, not its full text, and I cannot read the RFC or the core spec. The spec card has no section on arrays, so I cannot check the trap, effect or example rules against anything I can see. The summary sounds useful for parsing and data-modelling work, but I am not able to judge the design from here.
