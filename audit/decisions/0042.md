# RFC 0042: Building text

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. Adds about 350 tokens (two functions, a heap rule, two trap kinds), and its Cost section says it removes only a deferral sentence, so no removal pays for it under the add-for-removal rule. It also takes its 256 MiB limit from RFC 0025 A24, which was rejected. Change that would make me approve: name a rule it removes to pay for those tokens, and state the limit inside this RFC.
- designer-safe: reject. The functions, traps, out-of-memory rule and oom test repeat rejected RFC 0030 (text-operations), and the draft never says why 0030 failed or what differs. Principle 8 allows the long names text_cat and text_slice only when tokeniser measurements show fewer model errors, and the Alternatives section defers that measurement. To approve: state what changed from 0030, and either use shorter names or give tokeniser counts that justify the long ones.
- impl-1: reject. The design is coherent and the traps and tests are sound, but it adds two long names, text_cat and text_slice, and the RFC says itself that no measurement was made. Constitution principle 8 allows a longer form only when measurement shows fewer model errors, so the draft conflicts with it as written. It also takes its heap limit from RFC 0025 A24, which is rejected; the 256 MiB figure does match governance memory_mb, so only the citation is wrong. Resubmit with a tokeniser measurement of the names (or shorter names), and cite governance for the limit.
- tester: reject. Breaks principle 3: text_cat and text_slice allocate from the heap and can trap (TB9, TB11, TB12), but their signatures (TB1, TB2) show no effect word, so allocation is not visible. Also defines a bump heap for text while RFC 0043 A9 defines 'one bump heap' for Ints with no rule for sharing it; if both are accepted the heap is ambiguous. Its claim that it does not decide issue #64 is not accurate: it makes trapping text functions with no signature marker.
- user-1: approve. As a user writing text programs I need to join and cut strings; the summary gives a simple pair of calls and two defined traps. I read only the summary, not the RFC text, and the spec card does not yet show Text building, so I cannot confirm the behaviour myself.
- user-2: approve. As a user writing small data programs I need to join and cut text. The summary gives two clear functions and defines both failure cases as traps, which fits the no-undefined-behaviour principle. I judged from the summary only; I could not read the RFC body and the spec card does not yet mention Text, so the examples and nesting rule are unchecked.
