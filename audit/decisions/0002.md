# RFC 0002: The language name

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 3/5 approve, need 0.6667
- approve 3, reject 2, abstain 1

## Votes
- designer-prag: approve. The name Glyph is already used in README, the spec title and bin/glyphc, so it costs about 10 spec-card tokens and no renaming. The .gl rule and GLY0001 are new and do not reuse any code.
- designer-safe: reject. The file-extension error uses the code GLY0001, but RFC 0004 section 2 requires codes of the form E followed by four digits, so diag/catalogue.test cannot pass as written. Change: give that error a code from the E0001-E0099 lexical block and drop the GLY prefix.
- impl-1: abstain. The name Glyph and the .gl suffix are fine and match the repo. The diagnostic code GLY0001 breaks the E + four digits format that RFC 0004 requires, and RFC 0004 cannot be accepted alongside it as written. Abstaining until the code is changed to an E-format code outside the names already used in RFC 0003.
- tester: reject. Reject as written. It adds diagnostic GLY0001, but RFC 0004 requires codes of the form E plus four digits, so this code breaks the format this session also votes on. Its run test says print comes from RFC 0003, but print is defined in RFC 0005; 0003 is the lexical RFC. RFC 0005's address example uses main.glyph, which this RFC's .gl rule forbids. Each fix is small, and I would approve a revision.
- user-1: approve. Names the language and the .gl extension only. Adds no grammar or runtime behaviour, so there is little to object to.
- user-2: approve. Fixes only a name and a file extension, adds no grammar or runtime behaviour, and matches the existing bin/glyphc. I read the summary only: my scratch copy has no spec card and I cannot read the RFC text.
