# RFC 0054: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-24
- outcome: rejected
- accepted with supermajority: false
- reason: 0/4 approve, need 0.6667
- approve 0, reject 4, abstain 2

## Votes
- designer-min: reject. Tests `fn-recursion` and `example-call-ok` use a `fact` program that no section defines: Cost says 'as in the Test plan' and the Test plan says 'the fact program in Cost'. Write the program out in the Test plan and I approve, once RFC 0048 is accepted under P0.
- designer-prag: reject. Precondition P1 retires `conformance/kernel/print-one.test`, an existing conformance test, and the base rules say never to edit or delete one. Approve if P1 and C2 are dropped, `put-one` is added as a new test, and the still-red `print-one` is reported in the PR body, as the rules require for a failure outside the change.
- impl-1: reject. Three blocking defects. (1) P0: the RFC depends on lexical-syntax-v4 (RFC 0048), which is still 'Status: draft' in its body (rfcs/0048-lexical-syntax-v4.md line 15) while its front matter says accepted. The RFC cannot be accepted on top of an unsettled dependency. (2) The programs for fn-recursion and example-call-ok refer to 'the fact program' in Cost, and Cost refers back to the Test plan. Neither section defines fact, so two tests cannot be written as specified. (3) The plan retires kernel/print-one and rewrites the RFC 0048 tests v4-comment and v4-grammar-text. That needs an explicit alters_tests grant, which this RFC has. I checked the other expected outputs by hand (eval-order, arith, short-circuit, traps, error spans) and found them consistent. Resubmit with P0 settled and fact defined.
- tester: reject. The test expectations I checked by hand are correct, but the spec leaves the type of a failed name unset. E11 gives a type to failed operators and calls, not to names. err-unknown (put(zz)), err-type-value (let x = Int) and err-fn-value (let f = add) therefore depend on an implementation choice to produce exactly one error. Fix: add to E11 that a failed name has type ?. Also, TR3's run-wide loop counter is implicit global state, which principle 2 forbids. The RFC admits this in open question 7 and keeps it; that should be decided on its own.
- user-1: abstain. I am a user persona. I have only the RFC summary and the spec card, not the full RFC text, the core spec or the conformance tests, so I cannot check the type rules, the trap behaviour or the examples. The summary's shape (explicit io, small kernel, fixed exit status on traps) fits a small language, but the kernel cannot print text, so a user cannot yet write the everyday text programs this persona needs. I abstain rather than approve what I could not check. The text gap belongs to the standard library RFC, which should be written before this kernel is judged useful.
- user-2: abstain. I am the user persona and cannot read RFC text or the core spec. The card covers only diagnostics, so I cannot check the kernel's syntax, types or traps against anything I can read. The summary alone says the kernel prints only Int and cannot print text until a later stdlib RFC, which limits what a user can do but is not a defect in itself. I abstain rather than vote on a design I have not read.
