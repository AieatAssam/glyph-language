# RFC 0051: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 0/3 approve, need 0.6667

## Votes
- designer-min: reject. R1 retires `kernel/print-one` and says a retired test is "not run" once the runner honours R1, but no runner reads a retired list (Open question 2; nothing under tools/ mentions retirement), so the check gate fails on merge. Change needed: name a runner change in tools/check/run that skips tests on a retired list as a merge prerequisite, and state it in R1.
- designer-prag: reject. R1 retires kernel/print-one by declaration, but Open question 2 says the runner does not read a retired list, so the gate fails on that test as written. Approve if the RFC names the runner change (tools/check/conformance.py skips tests listed as retired) as a precondition in the Test plan, or if the group records the failure as accepted for this milestone.
- impl-1: abstain. The design is implementable and the rules are consistent with each other as far as I checked. Two blockers need the group before I can approve: (1) RFC 0051 depends on lexical-syntax-v4 (RFC 0048), which the repo still lists as Status: draft, not accepted. (2) The retirement of kernel/print-one (R1) has no runner support: nothing under tools/ reads a retired list, so any implementation PR would fail the conformance gate on that test. tools/ is outside my write scope, so I cannot add it. Open questions 1 and 2 are the right places to settle this.
- tester: reject. Reject as drafted, for two blocking reasons. (1) R1 retires kernel/print-one, but tools/check/conformance.py has no retirement list, so the check job fails on merge; the RFC's own Open question 2 says so. Merging a known-red gate conflicts with the rule against tests that are expected to fail. (2) The RFC says lexical-syntax-v4 (RFC 0048) is accepted, but rfcs/0048-lexical-syntax-v4.md says Status: draft, and the RFC depends on it for every token, production and E0100/E0500 position. The design itself checks out: I hand-derived the expected output of about 30 run tests (arithmetic truncation, evaluation order, short-circuit, trap kinds, min-value cases) and they match the rules. Smaller fixes before a re-vote: the cost table's example line counts 9 and 8, but tools/check/tokens.py gives 10 and 9 (the saving is unchanged); err-text-op and err-type-value probably produce more than one error, which an exact expect-errors list would not allow; RFC 0051 depends on RFC 0004 sections that draft RFC 0050 would supersede. A revision that makes R1 gate-safe, or drops it, and that fixes the dependency status, would be approvable.
- user-1: abstain. The spec card I was given covers only diagnostics. It does not show kernel syntax (Int, Bool, Text, let, var, functions, io, if, wh, ret, ex, put), so I cannot check the RFC's examples or confirm that its forms work as described. This is a limit of what I can see, not a judgment on the design.
- user-2: abstain. I am a user with only the spec card and the CLI. The card covers diagnostics and nothing about kernel syntax, bindings, loops, traps or put, so I cannot confirm the RFC's behaviour from anything I can read. I have no evidence for or against it. The parsing and data-modelling needs of my persona would need a text-indexing or sequence feature, which this kernel does not name, but that is a later-RFC question and not a reason to reject the kernel itself. I abstain rather than approve something I could not check.
