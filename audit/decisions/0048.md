## Votes
- designer-min: approve. Removes NEWLINE, the parenthesis-depth rules, and binding annotations, and adds only `;` as a separator, which G1 to G12 make unambiguous. Open question 3 (existing RFC 0014 tests that would fail) must be settled before acceptance.
- designer-safe: reject. Open question 7 keeps `007` in direct conflict with the accepted RFC 0004 test `diag/fix-present` (E0001 with a fix), and open question 4 moves E0003 for `let let` away from RFC 0004's `diag/record-shape` and RFC 0014's `lex/ident-keyword`; the leading-zero conflict has been carried unresolved since RFC 0014. Approve if a new RFC that names RFC 0004 or RFC 0014 as amended fixes the code and span, and lists the existing tests it retires (open question 3), since the base rules forbid editing or deleting them.
- impl-1: approve. The grammar and token rules are complete enough to build the lexer and parser from the text alone, and each E0100 position is stated. The counter claims match tools/check/tokens.py. Approval does not settle two open points the RFC flags: leading zero is E0006 here but E0001 in the RFC 0004 test, and the RFC 0014 lex tests it cites are not in this checkout (conformance/ has only kernel/print-one.test).
- tester: reject. Two spec-vs-spec disagreements are left open, and the RFC cannot merge cleanly without a decision on them. (1) Rule 8 makes a leading zero E0006, but open question 7 says RFC 0004's diag/fix-present expects E0001 with a fix for 007. (2) G3 and the v4-err-keyword-let test put E0003 at the second let, but open question 4 says RFC 0014's lex/ident-keyword and RFC 0004's diag/record-shape put it at the first let. The RFC names both conflicts but does not resolve them. It also gives no way to retire the existing tests it breaks (lex/punct-semicolon, lex/ws-crlf, lex/kw-while, lex/kw-return, lex/kw-example), while the base rules forbid editing or deleting them. Checked: spec/errors.json has E0001, E0005, E0006, E0010, E0100 and E0500 with the meanings the RFC uses, and the counter in tools/check/tokens.py charges the costs the RFC states. In this checkout, conformance/ holds only kernel/print-one.test, so I could not confirm the lex and diag tests the RFC cites. Layout is also left unspecified, which principle 1 does not allow. Reject until open questions 4 and 7 are settled and a retirement rule for the broken tests is written.
- user-1: approve. As a user I only have the summary, not the full grammar, so this is a judgement on the summary. Line ends as whitespace and a single ';' separator are easy to write without tracking line breaks. The error codes fit the card's ranges (E0001 lexical, E0100 syntax). One thing to pin down before the grammar is final: the summary says '->' is rejected at the '-' with E0100, so it should say what to write instead, because a user will type '->' first.
- user-2: approve. From the summary alone: line ends are whitespace, `;` is the one statement separator, and `let`/`var` take no annotation. For a user writing short programs this means fewer decisions per line and no newline-sensitive errors. The `->` split into `-` then `>` with E0100 at the `-` gives a clear, span-exact diagnostic. I did not read the full grammar text, so I cannot check the production list or the conformance coverage.
