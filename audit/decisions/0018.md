# RFC 0018: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/3 approve, need 0.6667

## Votes
- designer-min: abstain. The design is minimal: E4 drops >, >= and <= and keeps only < with written forms, which I support. I abstain because the text I was given stops mid-sentence in the test plan at kernel/fn-void.test, the Coverage section and open questions it cites are missing, and no compile-error test is visible, which the RFC checklist requires. I would approve if the full test plan lists at least one compile-error test and the core and card token counts are measured.
- designer-prag: reject. E4 rewrites `a > b` as `b < a` and `a <= b` as `not (b < a)`, so the right operand is evaluated first, while E11 makes the order observable when operands call `io` functions; the written forms therefore do not mean what the programmer wrote. Approve if the E4 forms are restricted to the order-preserving `a >= b` as `not (a < b)`, and E0100 at `>` and `<=` says the programmer must reorder the calls by hand.
- impl-1: approve. Implementable as written: the grammar is small, each rule that decides a token's position is in it, and the visible test plan maps to the codes in the tables. Two problems to fix in a revision, neither a blocker. (1) EX3 says an example that runs long is delayed only up to the TR3 limit, and Alternatives says TR2 already bounds call work. Both are false for branching recursion such as f(n) calling f(n-1) twice: depth is bounded by TR2, but total calls are not, so check can run without a practical end. Either count calls toward TR3 or state the gap in EX3. (2) The draft text I was given ends in the middle of the test plan (after kernel/fn-void.test), so the Coverage section it says closes the plan is not visible to me. The spec size and token caps could not be checked: this checkout has no spec/ directory and no compiler.
- tester: reject. Reject as drafted. RFC 0018 rule G8 makes the tokens `>`, `>=` and `<=` E0100 in every position. Accepted RFC 0014 (test plan, lex/tok-gt, lex/tok-ge, lex/tok-le) requires those three tokens as run tests with the token in a valid kernel position. Under 0018 those programs fail to compile, so the tests cannot pass. RFC 0018 rewrites only cmp-ops and does not mention these three. Fix: name the three tests and say how each changes (rewrite as E0100 compile-error tests, or amend RFC 0014 first). Also, the draft text I was given ends mid-sentence in the test plan at kernel/fn-void.test, so the Coverage section and the later tests could not be checked. Principle 3 asks that failure be visible in the signature; traps (overflow, divide-by-zero, exhaustion) are not, and the RFC does not discuss that trade-off. I would approve once the lex/tok conflict is resolved and the rest of the test plan is supplied. The checkout has no spec/ directory, so the 12,000-token and 2,000-token limits were not measured.
- user-1: abstain. I am the user persona and cannot read the RFC or its grammar, and spec/card.md is missing from my scratch copy, so I cannot test the kernel against the programs I would write. The summary is coherent: three types, bindings, functions, if/while/return, and defined traps. One limit matters for everyday programs: Text can only be bound, assigned and printed, so I cannot join or format text in the kernel. That is a stated scope choice, not a defect, but I want the stdlib RFC to cover it before I approve.
