# RFC 0032: Growable arrays of Int and Byte (minimal retry of 0029)

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 3/6 approve, need 0.6667
- approve 3, reject 3, abstain 0

## Votes
- designer-min: reject. Cost says the RFC removes nothing and adds about 450 core tokens, which breaks the rule that growth needs a simplification elsewhere; Open question 3 also says the roadmap may not allow a vote yet. I would approve if the Cost section named an accepted construct that arrays replace, with the core saving at least 450 tokens as counted by the protected tokeniser.
- designer-prag: reject. No benchmark finding supports arrays, and the Cost section says 'Removes: nothing', which breaks the rule that every addition names what it replaces or removes. spec/errors.json does not list E0201, E0202, E0301 to E0303 or E0400, which accepted RFCs already use, so the RFC cannot merge as written. I would approve if Cost names one removal the checklist would notice and the catalogue gap is fixed in the same change.
- impl-1: approve. The design is implementable from its text. It names every built-in, the copy and borrow rules, the trap kinds and the two new codes, and its test plan covers each new code. It fixes the defects this implementer found in 0029: the untestable trap-oom count, the undefined capacity, and the duplicated trap list. Conditions before merge, which the RFC already states: spec/errors.json must gain E0203 and E0401 and the codes from accepted RFCs (#72), and the roadmap question (open question 3) must be settled. The vote does not waive either condition. The RFC is a retry of rejected 0029 and the 0029 vote record gives no reasons, so the designer should say which part changed in response.
- tester: reject. Not ready to accept. (1) The test plan contradicts R17 and R18: R17 says any function that builds an array literal with n >= 1, copies a name, or calls push must declare alloc, and R18 says main follows R17, yet the run tests (arr-literal-len, arr-copy-let, arr-copy-assign, arr-set and others) are described with main and no alloc, so as written they would fail with E0401. (2) The RFC cannot merge while spec/errors.json lacks E0200, E0201, E0202, E0300, E0301, E0303 and E0400, which it uses, and it adds E0203 and E0401 without entries; I checked the file and only E0100 of these codes is present. (3) It is a near-copy of RFC 0029, which was rejected with no recorded reason, and the RFC does not say which design objection it answers. The design itself (copy on bind, borrow on call, alloc in the signature, bump allocator with defined traps) is sound, so a revision that fixes the test plan, lists the catalogue entries, and names the answer to the 0029 objection should be re-proposed.
- user-1: approve. As an everyday user I need a growable list for text lines and numbers, and this gives one type with get, set, push and len. Traps on a bad index and on an exhausted heap give defined results instead of silent corruption. My vote rests on the assignment summary only: the card does not yet mention arrays, and I did not read the RFC text or confirm any of the built-ins by running them.
- user-2: approve. I write parsers and data models, and both need a growable array of Int or Byte. The summary adds no token or keyword, keeps one array type, and makes bad index and heap exhaustion defined traps, which fits the no-undefined-behaviour rule. Concerns I accept: binding copies the whole array, and with no free a long-running program only grows its heap. I judged this from the assignment summary only; I did not read the RFC text.
