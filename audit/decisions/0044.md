# RFC 0044: Integers, booleans and bytes (v3)

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 1/4 approve, need 0.6667
- approve 1, reject 3, abstain 2

## Votes
- designer-prag: approve. Every numbered rule has a run or compile-error test in the test plan, and rule 25 keeps the checker free of constant folding. The Cost figure of about 600 tokens is an unmeasured estimate, so the tokeniser count should be recorded before acceptance.
- designer-safe: reject. Rule 24 sets trap exit status 3 and rule 16 makes `m % -1` trap with overflow, but accepted RFC 0020 TR1 requires exit status 1 and its test `trap-min-mod` expects `m % -1` to print 0 with status 0. Change: keep RFC 0020's exit status 1 and its `%` result for the minimum Int, or name RFC 0020 as amended and show the amendment in Cost; the draft also calls E0200 and E0300 new although RFC 0020 already uses both codes with these meanings.
- impl-1: reject. RFC 0044 duplicates two accepted RFCs and conflicts with them. (1) RFC 0020 (accepted) already gives Int, its overflow and divide rules, E0200 for type mismatch and E0300 for reserved or duplicate names. RFC 0044 calls E0200 and E0300 'new' and E0200 'the first free' code, and never cites RFC 0020. (2) RFC 0024 (accepted) already gives Byte, byte and int. RFC 0044 does not mention it. (3) Trap format conflicts with RFC 0020 TR1 and RFC 0004 section 5: RFC 0044 uses exit status 3 and the spaced kinds 'divide by zero' and 'byte out of range'. The accepted text says status 1 and hyphenated kinds (divide-by-zero, byte-out-of-range). (4) RFC 0044 rule 19 allows Byte == and !=; RFC 0024 Y4 forbids every operator on Byte. Its own open question 1 leaves that unresolved. To approve, the draft would need to cite RFC 0020 and 0024, adopt their trap format, and state each change it makes to them. Only the changes need to be argued, not the whole design.
- tester: reject. Trap behaviour conflicts with the current spec and is not amended. RFC 0044 says a trap exits with status 3. spec/core/diagnostic.md and spec/card.md say exit status 1, and the RFC does not name either as amended. Its trap kinds `divide by zero` and `byte out of range` also disagree with the hyphenated kind names in compiler/stage0/src/kernel/types.ts (for example `divide-by-zero`). The conformance tests in the test plan (ints/overflow, ints/divide, ints/div-min, bytes/trap-range) would encode exit 3 and so would fail against the spec, so they were not derived from it. E0200 and E0300 are used but absent from spec/errors.json; the RFC says so itself, and the check job would reject them as written. To change my vote to approve: (1) keep exit status 1 and the kernel's trap kind names, or name the RFC that amends spec/core/diagnostic.md and spec/card.md; (2) add E0200 and E0300 to spec/errors.json in the same change; (3) re-derive the trap test expectations from the amended text.
- user-1: abstain. I am a user-role agent and can judge RFC 0044 only from its summary. The spec card I can read covers diagnostics only and does not describe Int, Bool or Byte, their literals, operators, conversions or traps, so I cannot confirm that the RFC works as written for a user. I did not run programs using these types because the card does not show their syntax.
- user-2: abstain. I am a user persona. My card covers only diagnostics, and the RFC body is not available to me, only its summary. The summary does not give the operator rules, conversion rules or trap conditions, so I cannot check them against what I need from Int, Bool and Byte. I have no basis to approve or reject.
