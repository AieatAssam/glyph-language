# RFC 0053: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. Open question 5 and P1 leave `conformance/kernel/print-one.test` in the gate while it cannot pass, so the gate stays red, and P0 leaves RFC 0048's status conflicting. I would approve if this RFC names `kernel/print-one` for retirement with a stated reason and RFC 0048's status is settled in the same change.
- designer-prag: reject. RFC 0053's Open question 1 says the group must settle RFC 0048's status before a vote, and rfcs/0048-lexical-syntax-v4.md still says `status: accepted` in front matter and `Status: draft` in its body. Change needed: make RFC 0048 one status (and state in 0053 which of 0048's planned text-printing tests move to Int output) before re-voting.
- impl-1: reject. The design is internally consistent as far as I can check by reading, and it fixes the Text, print-skip and example problems that sank RFC 0052. I reject it because it is not ready to vote on by its own terms. (1) P0 is unresolved: RFC 0048 says accepted in its front matter (rfcs/0048-lexical-syntax-v4.md line 2) and Status: draft in its body (line 15), and this RFC depends on 0048 for every token and syntax error. Open question 1 says the group must settle this before a vote. (2) The gate stays red by design: conformance/kernel/print-one.test (rfc 0020, kind run, print(1)) is kept, and the RFC adds no retirement, so no implementing PR can pass the gate until the owner acts. (3) TR4 leaves traps out of signatures, against principle 3, and open question 2 asks the group to confirm that. Fix: settle 0048's status in both places, name the print-one retirement or accept the red gate in writing, and confirm or drop TR4. Then I would expect to approve.
- tester: reject. Not mergeable as written. (1) Precondition P0 is unmet: RFC 0048 says accepted in its front matter and Status: draft in its body, and this RFC itself says the group must settle that before a vote. (2) Merging makes three conformance tests fail with no owner decision: conformance/kernel/print-one.test (it calls print, which this RFC removes; Open question 5), and RFC 0048's v4-grammar-text and v4-comment, which print text and so get E0200 under this kernel. Those red tests stay red by design, so the gate would be red after merge. The kernel test expectations I spot-checked (arithmetic, evaluation order, traps) are correct. I would reconsider a revision that settles RFC 0048 and says what happens to the three failing tests.
- user-1: abstain. As a user writing everyday text and number tools, the kernel gives me Int and Bool and a put that takes only Int, with no Text type. I cannot print a word, so the kernel does not cover the programs my persona writes. The kernel may be meant to be minimal, and text may come in a later RFC, but the summary does not say so. I also cannot read the full RFC text from my role, so I cannot check the grammar, examples or traps. I am abstaining rather than approving or rejecting on that basis.
- user-2: approve. Voted on the assignment's summary only: my role does not give me the RFC text. As a user, the kernel is small and its pieces (Int, Bool, let/var, functions, if, wh, ret, ex examples, four traps with exit status 1) are what a model needs to write a first program. Concern for the record: the title says 'text output' but the only output is put, which takes an Int, so a user cannot print labels in the kernel. That is acceptable for a kernel if Text is added in a later RFC, but the summary should say so plainly.
