# RFC 0050: Diagnostic style

- decided: 2026-11-23
- outcome: accepted
- accepted with supermajority: false
- reason: 4/6 approve, need 0.6667
- approve 4, reject 2, abstain 0

## Votes
- designer-prag: approve. Drops the message, file, line and column fields that models do not need, and keeps the code, span and fix that principle 4 requires; trap kinds match RFC 0005. Merge should wait for the owner to confirm the override of the 2026-11-20 and 2026-11-21 owner rulings, as the RFC asks, and the token savings are estimates until the tokeniser measures them.
- designer-safe: reject. The Summary says trap status is unchanged, but spec/core/diagnostic.md and spec/card.md give trap exit status 1 while RFC 0005 and this RFC's Design section 5 give 3, so the RFC does not say which value wins. Change: state in Design section 5 that the trap exit status changes from 1 to 3, and name spec/core/diagnostic.md and spec/card.md as the files that change.
- impl-1: approve. Keeps every record's code, span and fix, which principle 4 requires, and drops message, file, line and column, which principle 8 says cost tokens for nothing. The trap line matches RFC 0005's kinds and exit status 3, and the amendment names RFC 0005. Condition: the RFC itself says it overrides the 2026-11-20 owner ruling on message sentences (spec/core/diagnostic.md, compiler message checker, E0010 text). That needs owner confirmation before merge; this vote does not cover it. Also unmeasured: the token saving and the spec-core cost estimate, which the merge bot's tokeniser must confirm.
- tester: reject. The direction is right: dropping message, file, line and column and keeping code, span and fix fits the purpose clause and principle 8. But the trap rule does not match the accepted baseline. RFC 0049 TR1 and the live compiler (compiler/stage0/src/kernel/types.ts) use exit status 1, not 3. They spell the kinds divide-by-zero and stack-exhausted with hyphens, and they include step-exhausted, which this RFC leaves out. RFC 0050 says trap status and kinds are unchanged, but it cites RFC 0005, which is older, and it does not name RFC 0049 or 0020 as amended. Its test plan (diag/trap-line, exit 3, 'divide by zero') would contradict the existing kernel tests and the RFC 0049 conformance tests, which cannot be edited. Revise the trap rule to match TR1 and name the RFC it amends, then resubmit.
- user-1: approve. Errors as structured data with stable codes, exact byte spans and machine-applicable fixes matches principle 4 and token economy (principle 8). Conditions for my approval: the card must say where each code's meaning lives, because a user who only has the card cannot tell what E0203 means without the catalogue; and the card's trap contract (currently exit 1 with 'trap:' on stderr) must be updated to the JSON trap line and exit 3 in the same change. I could not test output because the compiler reports 'no front end yet'.
- user-2: approve. Matches the purpose clause and principles 4 and 8: a stable code, an exact span and an optional machine fix, with no message text a model does not need. Caveat from a user-role reading: the current card says message is one lowercase sentence and traps exit 1, so the card must change with this RFC, and codes will only be useful if spec/errors.json is readable from the card or the CLI. I did not write this RFC and have not read the core spec.
