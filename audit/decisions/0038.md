# RFC 0038: Arrays and buffers: IntArray with bump-allocated handles

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The Cost section says 'Removes: nothing' and adds about 700 tokens (a type, six built-ins, the alloc effect, four trap kinds, E0402), and it states that it proposes no simplification, which breaks the rule that growth needs a removal. To approve, name a removal that pays for the addition (for example, drop `set` and `pop` with tests arr-set and arr-pop, or another cut of similar size) and replace the estimate with the tokeniser's measured figure.
- designer-prag: reject. Cost says it removes nothing, but the designer rule requires every addition to name what it replaces or removes, and the planning rule says growth needs a simplification elsewhere. Approve once Cost names removals worth about 700 core tokens, or the owner waives the rule in writing.
- impl-1: reject. The design is coherent, but the draft cannot pass the diagnostic catalogue check as written. It adds E0402 and uses E0300, E0301 and E0400, and none of these is in spec/errors.json, which the constitution requires for every code. The draft says E0402 is new and does not add it to the catalogue. The draft is also large (about 700 core tokens, with no cut proposed) and says it amends RFC 0020 by name only, which is unclear when it changes T6, F7, B5, F6 and TR1. The draft could come back as a revision that catalogues the codes, names each amended rule in full, and sets out the M2b gate result.
- tester: reject. The design is coherent, but the text has defects that block approval. (1) D3 push uses cap(a) in its growth steps, but no cap built-in appears in the D2 table, so the surface language never defines it and an implementer cannot write push from the text. Add cap to D2 or drop the reference. (2) E0402 is new and is not in spec/errors.json. The constitution requires every diagnostic code to be catalogued, and the RFC does not commit to adding the entry. Note that errors.json also lacks E0200, E0300, E0301 and E0400, which this RFC reuses, so the catalogue gap needs one fix for all of them. (3) The test plan hard-codes the spelling alloc while the RFC says the spelling depends on open issue #36. The tests cannot be final until #36 is settled, and the RFC should say so in the test plan. (4) Fixed capacity of 256 MiB with no free means a loop that creates many short-lived arrays traps out-of-memory even when live data is tiny. The RFC says no such program exists yet, but one is easy to write, so the free-list benchmark condition is already met in principle. (5) ROADMAP M2b applies here as it does to RFC 0037. No conformance test uses len, get, set, push, pop, IntArray or int_array, so the reserved names do not break existing tests.
- user-1: approve. Everyday programs need a growable list, and IntArray covers the common case with six built-ins. Every failure is a defined trap, which is what I need to debug a script. The bump heap never frees memory, so long-running programs will hit exhaustion sooner; I would like the spec to say how that trap looks to the user. I judged this from the assignment summary only, not the full RFC text.
- user-2: abstain. The summary says there are six built-in functions and that every failure is a defined trap, but it does not list them or the trap kinds, and the card does not cover arrays. I cannot judge the handle and allocation design from the summary alone, so I am abstaining rather than guessing. The idea of a growable Int array is useful for the parsing and data-modelling programs I write.
