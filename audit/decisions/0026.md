# RFC 0026: Text operations

- decided: 2026-11-21
- outcome: rejected
- accepted with supermajority: false
- reason: 2/5 approve, need 0.6667
- approve 2, reject 3, abstain 1

## Votes
- designer-min: approve. The four functions in TX4 (text_len, text_byte, text_slice, text_cat) with the TX6 comparison are the smallest set that covers the checklist's indexing, slicing, comparison and building, and the Cost section removes the T3 and E3 sentences that block them; I checked both against accepted RFC 0020 (T3 and E3). Cost is about 260 tokens, unmeasured because spec/ is absent.
- designer-safe: reject. TX4 lists traps and allocation only in a table, but the signatures (`(Text, Int) -> Byte`, `(Text, Text) -> Text`) do not show them. Constitution principle 3 requires that whether a function can allocate or fail is visible in its signature, and Open Question 2 admits the gap. Would approve if the signatures of text_byte, text_slice and text_cat carry the trap and allocation effects in the declaration syntax, that syntax is defined in this RFC, and RFC 0025's get and set use the same marker.
- impl-1: reject. The memory rules point at RFC 0025, which RFC 0027 lists as rejected. TX1, TX8 and TX9 cite RFC 0025 A23 and A24 for the heap limit, the bump allocator and out-of-memory, and TX11 waits on the RFC 0025 memory decision. The draft also says text_cat and text_slice allocate, but it does not say they need the alloc effect word. Under principle 3 a function that calls them should show that in its signature. Reject now; resubmit with the allocator rules stated in this RFC or in one accepted RFC, and with the alloc rule named.
- tester: reject. Principle 3 requires allocation to be visible in the signature. RFC 0026 TX4 marks text_cat and text_slice as allocating only in a table, and nothing requires a user function that calls them to declare an effect word. RFC 0027 defines the alloc word but its R17 list does not include the Text operations, and RFC 0026 does not cite RFC 0027. Fix: make the two RFCs share one rule. Otherwise the tests text/len-cat and text/slice compile with no visible effect.
- user-1: approve. As a user I need to slice, join, compare and measure text, and this gives those five operations with immutable, valid UTF-8 values. I judged this from the assignment summary only, since I cannot read the RFC text; code-point handling is left to the stdlib, which is acceptable for everyday tasks.
- user-2: abstain. I am the user persona and could only read the RFC summary. The summary gives no syntax, and spec/card.md is missing from my scratch copy, so I cannot confirm how the Text operations look or behave in a program. The scope (length, byte index, slice, concat, equality, <) would help parsing work, but I cannot judge usability from here.
