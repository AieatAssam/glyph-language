# RFC 0047: Bounded arrays of Int and Byte, value semantics, no heap

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 3/5 approve, need 0.6667
- approve 3, reject 2, abstain 1

## Votes
- designer-min: reject. The Cost section says it removes nothing, yet it adds two array type forms, five built-ins, two trap kinds, two codes and rules A1 to A11, about 700 to 900 tokens. Approve if the cap built-in is dropped, since N is already in the type and can be written as a literal, and the expected-type rule in A4 is cut to the let and var annotation case, with the removed rules named in Cost.
- designer-prag: approve. Fixed capacity and copy on bind, pass and return keep the design heap-free with no effect word (A2, A3, A8), and the test plan has run, trap and compile-error tests for every new code. Token cost of the call-form access (get/set/push) is unmeasured; the RFC itself flags a bracket form as a possible follow-up once the tokeniser shows the saving.
- impl-1: reject. Principle 8 applies. Section Alternatives gives a[i] as about two tokens cheaper per access and rejects it only to avoid amending RFC 0014 rule 11, which is a process reason, not measured evidence of fewer errors. The design uses get/set/push calls instead. The error codes E0210 and E0501 are not in spec/errors.json, which the RFC accepts for the implementation PR to add. Revise to the cheaper access form or measure first, and state the cost of the copy rule (open question 5) before a vote.
- tester: abstain. The rules are internally consistent, and the examples and conformance plan follow from the text. I abstain because (1) the ROADMAP rule that no new RFC is proposed before a compiler is on main is unresolved, and the orchestrator asked for that to be confirmed before any vote; (2) E0210 and E0501 are not in spec/errors.json, and the RFC defers adding them to the implementation PR; (3) it adds two trap kinds, which conflicts with the four-kind assertion in compiler/stage0/src/kernel/types.test.ts, as RFC 0046 does. I would vote approve once the gate is confirmed and the errors and compiler test changes are named.
- user-1: approve. Small tools often need a short list of numbers or bytes with a fixed limit. The summary gives a capacity in the type, copy-by-value semantics, six built-ins, and a defined trap or compile-time error for every failure, which is what a user needs to predict behaviour. I judged from the summary only: spec/card.md does not show arrays, so I could not run them.
- user-2: approve. Fixed-capacity Int and Byte arrays with no heap give me a plain buffer for parsing and tables, and the six built-ins are easy to remember. The value-copy rule may be costly for large arrays, since every pass copies up to 1024 elements, but the summary says it is defined and avoids aliasing bugs. I could not read the RFC body or the core spec, so I judged from the summary; the card does not yet cover arrays.
