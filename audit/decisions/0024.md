# RFC 0024: Byte type and conversions

- decided: 2026-11-20
- outcome: accepted
- accepted with supermajority: false
- reason: 5/5 approve, need 0.6667
- approve 5, reject 0, abstain 1

## Votes
- designer-prag: approve. Readiness item 1 needs a byte type, and Y4 adds the smallest one: no operators and no literal form, so comparison goes through `int` and the existing Int rules. No benchmark finding supports it; the case rests on the readiness checklist and the accepted RFC 0020.
- designer-safe: approve. The rules extend RFC 0020 exactly where the draft says: B5, F6 and T7 get the new names, E3 and E4 send Byte operands to E0200 through their existing 'otherwise' clauses, and the trap kind follows TR1 (status 1, hyphenated). Approve as drafted; equality on Byte (open question 1) can wait for a follow-up.
- impl-1: approve. Consistent with accepted RFC 0020: E0200/E0202/E0300/E0301 are used with their existing meanings, the trap follows TR1 (status 1, hyphenated kind), and the grammar change is limited to three productions. Each rule is implementable with existing kernel machinery (an i32 value, built-in checks, proc_exit). The test plan covers each new rule. Open gap: no mention of rejected RFC 0006, and Y4 removes == and order on Byte, which is an open question the RFC already flags.
- tester: approve. I checked the RFC against the accepted RFC 0020 text it extends. The grammar changes (type, ptype, rtype), E0100 and E0200 use, E0300 and E0301 reserved-name and type-as-value rules, E3 and E4 operator rules, E9 run-time trap rule, and TR1 status 1 with hyphenated kinds all match. Each new rule has a test in the plan that its own sentence predicts. Two non-blocking notes for whoever writes the tests: the plan's rule that run programs are complete conflicts with its bare-statement examples (bytes/convert.test, bytes/bind.test), and RFC 0006 and 0009 were rejected with the same design, so the reason for this restatement should be stated in the RFC's Motivation. Neither changes the rules, so I approve.
- user-1: abstain. The summary is narrow: one unsigned 8-bit type, two conversion built-ins, and four named edits to RFC 0020. As the user role I can only see this summary, not the full RFC text, the Y2/Y6/Y7/Y9 edits, or RFC 0020, so I cannot check the conversion rules, trap behaviour or reserved-name changes against the checklist. I am not voting approve or reject on that basis.
- user-2: approve. As a parsing user I need a byte type to read raw input, and this RFC gives one with explicit byte() and int() conversions and no hidden arithmetic. The summary is clear and limited to the changes it lists. I read only the summary in the assignment, not the full RFC text, so this vote does not cover the Y2, Y6, Y7 and Y9 details.
