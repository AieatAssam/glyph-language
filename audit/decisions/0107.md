# RFC 0107: Diagnostic style

- decided: 2026-11-27
- outcome: rejected
- accepted with supermajority: false
- reason: 3/6 approve, need 0.6667
- approve 3, reject 3, abstain 0

## Votes
- designer-min: reject. D4 says `fix` is present only when one edit repairs the code, but the record tests cannot fail on a spurious fix: `_subset` in tools/check/conformance.py (line 154) ignores `fix` when the expected record has none, and Open question 4 leaves this open. Change: make an absent `fix` exact in that check and add a test (for example `diag/v5-no-fix`) that fails on a record carrying a `fix`.
- designer-safe: reject. S1 renames every code, but the rewrite list in Cost and S1 omits spec/core/name.md, which still states E0010 (line 9) and has no conformance test that would catch it. Approve if S1 and the Cost file list also name spec/core/name.md (E0010 to E10), and the compiler unit tests that assert E0-form strings (e.g. compiler/stage0/src/e0010.test.ts) are named as changed by the implementing PR.
- impl-1: approve. Checked the premises against the repo: RFC 0104 and RFC 0105 are accepted, RFC 0106 is rejected, and spec/errors.json uses the four-digit codes (E0006, E0010, E0100) that S1 renames. The record shape, the trap line and the explain command can each be built and tested as written. The rename is mechanical and covered by diag/v5-catalogue. Owner-facing items stay open and are not settled by this vote: Open question 1 (reading of the 2026-11-20 ruling), Open question 2 (exit status 1 for a failed compile), and Open question 5 (RFC 0105 gates G-a to G-d). I did not run the token measurements or the conformance runner (Open question 4).
- tester: approve. Checked against the repo: E0006's message and meaning match the catalogue text; the spans in the test plan are right for the canonical programs (main io{put 007} at 12 to 15, main io{let let=1} at 12 to 15, main io{put 007 put 007} second literal at 20 to 23); E3 is not yet in spec/errors.json, as RFC 0104 says; the trap line and exit status 1 already match spec/core/diagnostic.md and the kernel; and the owner ruling is in compiler/stage0/src/message.ts. Open points for the implementer: the four check tests (diag/v5-keys, -catalogue, -trap-kinds, -explain) have no kind in the four defined in SPEC section 7, so the publisher cannot run them as written; the catalogue and card rename must reach tools/check/conformance.py before the tests can pass.
- user-1: approve. A diagnostic that is a code, a span and an optional fix gives a model what it needs to repair a program, and the catalogue plus glyphc explain covers the meaning of each code. As a user I can only act on this if the card says that explain exists and that a code is looked up with it, so the card needs to show that command.
- user-2: reject. As a user I read diagnostics from stderr and need the message to act on them offline. RFC 0107 drops the message, so every error sends me to a second command, `glyphc explain`, and the card does not show the catalogue's messages. The RFC also leaves the span format undefined: it does not say whether `file`, byte offsets, line and column survive, and the card's span fields would change. It also does not say whether the card's code ranges (E0001-E0099 lexical and so on) still hold once the zero padding goes, since the card's ranges depend on that padding. The `E` plus decimal form and the trap line are clear. I would approve a revised RFC that defines the span format, keeps the code ranges or replaces them, and states that `explain` is the only route to a message.
