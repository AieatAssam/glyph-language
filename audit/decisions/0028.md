# RFC 0028: Text operations

- decided: 2026-11-21
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. The Cost section adds about 330 core tokens and removes only two sentences from RFC 0018 T3 and RFC 0020 E3, so the growth is not paid for, and the base rule says growth needs a simplification elsewhere. Approve if the RFC names an existing core passage of about 330 tokens to remove, or drops one of the four Text operations, and the tokeniser then confirms the net count.
- designer-safe: reject. TX9 (out-of-memory), TX12 and the TX1 length rule depend on a bump allocator, a 256 MiB heap limit and an out-of-memory trap that no accepted RFC defines: RFCs 0008, 0022, 0023, 0025 and 0027 are all rejected, and TX1 defers the length to an unnumbered memory RFC, so principle 7 (one defined result on exhaustion) is not met from the accepted baseline. The change that would earn approve: state the allocator (bump, no free, 8-byte rounding), the heap limit and the exact out-of-memory condition inside this RFC, and cite RFC 0020 T3 and T6 rather than the rejected RFC 0018.
- impl-1: reject. The operator and placement rules are sound and match accepted RFC 0020, but the draft is not ready. (1) Its two new trap kinds, index-out-of-bounds and out-of-memory, are the same names RFC 0027 (R12, R24) adds to TR1 for the same two conditions, and the draft does not cite RFC 0027. (2) It says it amends RFC 0020 but its edits target RFC 0018 T3, T6 and the 'no operation' sentence, which accepted RFC 0020 does not contain. (3) It does not say which trap fires when a slice is both out of range and too large. Each fix is small; a revised draft should be able to pass.
- tester: reject. Three defects. (1) TX1 says a Text is always valid UTF-8 and no operation makes a Text from arbitrary bytes, but TX4 text_slice takes byte indices with no code-point boundary check. text_slice("é", 0, 1) yields a lone byte C3, which breaks TX1. The draft needs a rule (trap at a non-boundary, or code-point indices) and a conformance test for it. (2) TX9 traps out-of-memory when text_cat or text_slice 'needs more space than the heap has left', and TX12 fixes a bump allocator. No accepted RFC defines a heap size or an allocator (checked RFC 0014, 0018, 0020; RFC 0018 says Text operations need a memory decision first). The oom.test outcome therefore cannot be derived from the accepted spec, which the tester rules forbid. The memory decision should come first, or the limit must be stated here. (3) Constitution principle 3 says whether a function can allocate or fail is visible in its signature. TX4 keeps both out of the signature (Behaviour column only), and the draft defers the question instead of answering it. RFC 0020 E9 already does this for overflow, so this is a pre-existing conflict that this RFC extends to allocation. The rest is sound: the ordering rule matches RFC 0020 E4, the compare and byte tests match TX7 and TX4, and the trap kinds do not repeat accepted TR1 kinds.
- user-1: approve. As a user writing small text tools I need length, indexing, slicing, concatenation, equality and ordering on Text, and this RFC gives exactly those with immutable UTF-8 values. Byte-only indexing is a real limit for non-ASCII input, but the RFC leaves code-point handling to the standard library on purpose, so I do not block on it. I judged this from the RFC summary in my assignment; I did not read the full RFC text or the core spec, which I am not given access to.
- user-2: approve. As a user writing parsers, I need a byte length, byte-at-index, slice, concatenation and equality on Text, and this RFC supplies them with the Int ordering operators. I reviewed only the summary, not the full RFC text. The summary does not say what a byte-at-index returns, or what an out-of-bounds index or slice does; the RFC should state both, since the constitution requires one defined result for every case.
