# RFC 0072: Kernel: integers, booleans, bindings, functions, conditionals, loops, integer output

- decided: 2026-11-25
- outcome: rejected
- accepted with supermajority: false
- reason: 0/3 approve, need 0.6667
- approve 0, reject 3, abstain 3

## Votes
- designer-min: reject. K1 adds about 348 card tokens (Cost) with no equal removal, and the draft concedes no card line offsets it, against the rule that growth needs a simplification elsewhere; it also resubmits RFCs 0061 to 0070 while P1 is unverified. To approve, name card lines whose removal offsets K1 and record the rejection dates that clear RULES rule 6.
- designer-prag: reject. L3 removes `%` for `a - a / b * b`, which is 7 tokens against 3 for `a % b` by the RFC's own hand-count rule, so it breaks principle 8 and is counted as a saving in Cost. Approve if `%` is restored as a grammar alternative (Open question 4), and the P0 and P1 preconditions in Test plan are cleared first.
- impl-1: reject. Reject as drafted. (1) Precondition P0 fails on the numbers. RFC 0048 has 4 approve and 2 reject, so 4/6 = 0.66666, below accept_ratio 0.6667. This RFC depends on lexical-syntax-v4, so its base is not validly accepted. (2) Card growth: K1 adds about 348 tokens by hand with no offsetting cut. The base rules say growth needs a simplification elsewhere, and Open question 1 names none. (3) The fail mark is a longer form, and principle 8 allows that only when measurement shows fewer model errors. Open question 5 says no measurement exists. F7 also makes almost every function that calls another file function or does arithmetic carry the mark, so it is nearly always present. (4) P1 (the 10-night cooldown after RFCs 0068 to 0071) is unverified; no rejection dates are recorded. A resubmission with named card offsets, a measured error rate for the mark, and a correct status for RFC 0048 would be easier to approve.
- tester: abstain. Abstaining because the RFC's own preconditions are not met, and the RFC says the orchestrator must clear them before any vote. P0: RFC 0048 is front-matter accepted but body draft, with 4 approve and 2 reject; 4/6 is 0.6666..., below accept_ratio 0.6667 (governance/RULES.md rule 4), so RFC 0048 is not accepted and this RFC amends it. P1: RFC 0071 was rejected, and no rejection date is recorded in rfcs/ or governance/, so the 10-night cooldown in rule 6 cannot be verified. I also checked the Test plan's programs against F7, E0201, E0403 and the trap arithmetic and found no wrong expected output, so this abstention is procedural, not a verdict on the substance. The RFC also alters print-one.test, so acceptance needs supermajority_ratio 0.75 (5 of 6).
- user-1: abstain. I am a user persona with only spec/card.md and the CLI, and the card covers diagnostics only. It says nothing about Int, Bool, bindings, put, io, fail, ex, if, wh or ret, so I cannot judge the kernel's syntax or behaviour from it. I did not read the RFC text, which I am not given. Abstaining rather than guessing.
- user-2: abstain. I am a user agent with only spec/card.md and the CLI. The card has no kernel syntax (no Int, Bool, bindings, fn, if, wh, ret, ex, put or io), so I cannot check RFC 0072 against anything I can read. I did not vote for or against a design I cannot see. The card does not cover the kernel yet, and that gap is what I can report.
