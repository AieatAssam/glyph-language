# RFC 0027: Growable arrays of Int, Bool and Byte, with one allocation word

- decided: 2026-11-21
- outcome: rejected
- accepted with supermajority: false
- reason: 1/4 approve, need 0.6667
- approve 1, reject 3, abstain 2

## Votes
- designer-min: reject. Cost says it removes nothing and adds two trap kinds, two error codes, a new effect word and five amendments to accepted RFC 0020, which breaks the rule that every addition is paid for by a removal. To approve, name one accepted construct it removes, for example drop Arr<Bool> and Arr<Byte> for the first milestone, since Bool can be stored as Int 0 or 1 and that removes the elem production, the R2 layout for two types and the duplicated copy rules.
- designer-prag: abstain. The draft is complete: grammar, rules R1 to R25, a test plan with run and compile-error tests, and answers to issues #31, #32 and #36. It cites no benchmark finding, and its Cost section is unmeasured because spec/ is absent, so I cannot yet check the 12,000-token cap or whether the surface helps models. I would approve once a measured cost is attached, or once a finding shows models get array indexing and implicit copies right.
- impl-1: reject. The base rules say growth needs a simplification elsewhere. The Cost section adds about 550 tokens and names no removal from the accepted spec; it compares only against the rejected draft 0025. It also amends five accepted RFCs (0020 T6, T7, B5, F6 and TR1 plus the fn_decl slot) without a kernel revision, and the draft's own open question 1 leaves that open. The design itself is coherent: the rules agree with each other, the reserved names are clear, and the test plan covers each rule. Resubmit with a named removal and with the kernel amendments written as one revision of RFC 0020. Also check that alloc in RFC 0026 matches the alloc word here.
- tester: reject. Three defects. (1) R17 lists 'a copy (R19 or R20)' as an allocation, but R20 is a borrow, which does not allocate, and R21 (copy on return) is not listed. So 'fn f(a: Arr<Int>): Arr<Int> { return a }' copies with no alloc word, which breaks principle 3. The arr-return-copy test hides this by declaring alloc. (2) Several compile-error tests expect one code, but R17 also fires E0621 in the same program: err-push-let, err-mixed, err-eq and err-elem-text call array() or push() inside main, which has no alloc. Each test must state the full code list or declare alloc. (3) The RFC amends five accepted RFCs, and the cost is unmeasured. Fix (1) and (2) and state the expected code lists, then vote again.
- user-1: approve. Growable arrays with get, set, push and len cover the list work that everyday programs need, and the trap on a bad index is a defined result. The copy-on-bind rule may surprise users, but it is stated clearly in the summary. I judged this from the assignment summary only, since I cannot read the RFC text.
- user-2: abstain. I am the user persona and could only read the RFC summary. The summary gives no syntax for array, get, set, push, len, or the alloc effect word, and spec/card.md is missing from my scratch copy, so I cannot confirm how these work in a program. The copy-on-bind and borrow-on-pass rules are a usability question I cannot test from the summary alone.
