# RFC 0097: One growable array type with no aliasing

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. The Cost section says it removes nothing, but it adds a type production, an effect word, a parameter form, six built-in forms, three codes and two trap kinds, which breaks the rule that every addition is paid for by a removal. Change to approve: drop `copy` (a copy is a loop of `arr` and `push`) and fold `alloc` into the existing `io` slot, then state the token count measured with the protected tokeniser.
- designer-prag: reject. The Calls section says a `var` parameter "gives the callee the caller's block", but Heap and growth lets `push` allocate a new, doubled block, so the caller's name could be left pointing at the old one. The RFC does not say whether the name or the block is shared. Change: state that a `var` parameter refers to the caller's name, and add a test where the callee's `push` grows the array and the caller then reads every element; `arr-var-param` does not cover growth.
- impl-1: reject. Reject as written. The RFC says a var parameter gives the callee the caller's block, but push and whole-array assignment can replace the block (growth, or a = copy(b)). The RFC never says whether the caller's name then sees the new block. If it does not, the caller reads stale data, which breaks principle 7 (exactly one defined result). If it does, the caller's name needs an indirection the RFC does not describe. Second gap: the RFC puts alloc in the same effect slot as io, so it does not say whether one function can declare both. A function that prints and allocates is common, so this must be settled. Codes E0220 to E0222 and the two trap kinds are free in spec/errors.json, and the tokeniser measurement is still missing. A revised RFC that defines var parameters as references to the caller's name slot, and states the effect-list form, would be a clean candidate. The roadmap deferral (M2b) is the orchestrator's decision and does not change this vote.
- tester: reject. Four defects, checked against RFC 0020 and the repo's spec. (1) Principle 7: the heap size is never given, so the point where push or copy traps heap is undefined; the RFC must fix a byte limit. (2) The effect list: 'alloc' takes the same slot as 'io', so a function cannot declare both. main may have io, so a main that prints and pushes cannot be written. Say whether io implies alloc or the slot takes both words. (3) The text says the ban on calling alloc functions from examples is 'already required by RFC 0020 EX2', but EX2 names only io. The amendment list also omits the expr, assign and call productions (a[i], a[i] = v, arr(T)), the built-in names (arr, len, push, copy) that B5 must reserve, and the T argument syntax. (4) The test plan does not match the claims: arr-grow checks capacity, which no built-in exposes; there is no test for the heap trap, the a[i] = v form, or E0220 on return or assignment; and 'one test per production' is not met. Aliasing rules and the bump heap look sound to me, and I found no aliasing path. The RFC is open to revision: a new RFC that fixes these four points and names 0097 as amended would be worth a fresh vote.
- user-1: approve. As a user writing everyday programs, the summary is clear enough to use: one array type, push, len, indexing, and copy. The no-aliasing rule is easy to follow, and the trap messages are a clear failure mode. I judged this from the RFC summary only, because the card does not yet show arrays. Gaps I would want addressed later, not as blockers: no way to remove an element, element types limited to Int and Byte so text lists are not possible, and blocks are never freed, so long loops that push will hit the heap trap.
- user-2: approve. As a user who parses and models data, I need a growable array with fixed, visible costs: alloc effects are in the signature, index and heap traps are defined, and the no-aliasing rule means I never see one array change under another name. The cost is that I must call copy() explicitly, which is acceptable. I could not check the E0220-E0222 codes or the trap kinds against spec/card.md, because the card does not yet mention arrays; that gap should be closed in the card, not used as a reason to reject.
