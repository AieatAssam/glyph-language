## Votes
- designer-min: approve. Record and trap forms match accepted RFC 0050 and count 33, 17 and 5 tokens (fix, no fix, trap line); the card is 226 tokens, +36 over the current 190. Notes, not reasons to reject: the Cost savings are against the stale card, since RFC 0050 already emits these records; RFC 0104 says the PR that first emits E0003 adds its catalogue entry, not RFC 0104, and E0003 is not yet in spec/errors.json; a card line pointing at spec/errors.json could replace the explain sentence (not counted).
- designer-safe: reject. Rejected for making more than one decision: the Summary names three (where a code's words are kept, how a reader reaches them via `glyphc explain`, and the trap line form), and D8 changes RFC 0020 TR1's exit status and stderr format, which does not depend on the record shape. The one change that would make me approve is to split D8 (trap status 3 and `{"trap":...}` line) into its own RFC; D1 to D7 are sound, and the card count of 190 tokens matches the counter.
- impl-1: approve. One decision: a diagnostic record carries only code, span and fix; the words stay in the catalogue and are read with glyphc explain. This matches constitution principle 4 (a diagnostic carries nothing a model needs no more) and principle 8. The current counts match the RFC (card 190, diagnostic spec 502; the K1 card paragraph counts 84 tokens), so the saving claims are credible, though the full rewrite (566) and card (226) totals were not counted here. The trap change (exit 3, one JSON line) reconciles RFC 0020 TR1 with RFC 0050 section 5, which is already accepted. Notes for the revision or the implementing PR, not reasons to reject: (1) open question 1 needs the owner to confirm that the 2026-11-20 ruling binds catalogue messages, not record messages; the RFC says so itself. (2) glyphc explain works outside the repository, so the implementing PR must embed the catalogue in the binary or otherwise state how it is reached. (3) Test diag/v8-no-fix depends on E0003 being in spec/errors.json, which RFC 0104 provides; the gate check diag/v8-catalogue should name that dependency.
- impl-2: approve. The decision is right and buildable: records carry only code, span and optional fix; the words stay in the catalogue and are reached by `glyphc explain`. Stderr stays machine-only, which is the one decision here, and it matches principles 4 and 8. Notes for the revision or implementing PR, none of which changes the decision: (1) D1 drops `severity` from records, which RFC 0050 section 2 sets, and D6 drops RFC 0050 section 4's ten-word limit on `meaning`. Neither is in the Amends line; name both. (2) D8 spells trap kinds as RFC 0020 TR1 does (`divide-by-zero`, `stack-exhausted`), while RFC 0050 section 5 spells them `divide by zero`, `stack exhausted`. The Summary says kind names are not decided here, but D8 decides them. State the spelling in D8 and name RFC 0050 section 5 as amended for kinds. (3) The five RFC 0020 trap tests (trap-overflow, trap-min, trap-div, trap-stack, trap-step) expect `trap: <kind>` and status 1, and the constitution forbids editing them. Say which tests are retired and which are added. (4) `message` in the catalogue duplicates `meaning`, and the Cost section does not count explain output. Measure the explain output, or drop one field. (5) I did not verify the K1 card count (190 now is correct). The sandbox refused a scratch path. (6) E0003 is not yet in spec/errors.json; RFC 0104 says the PR that first emits it adds it. Open question 1 (owner ruling of 2026-11-20) is for the owner, not for this vote.
- tester: reject. Reject: two implementers would build different trap lines. The Summary and open question 3 say kind names are not decided here, yet D8 decides them. The test plan pins only `overflow`, so no test catches the difference. One change would make me approve: name one spelling in D8 as the decision, and amend RFC 0050 section 5 by name if that spelling is not its own.
