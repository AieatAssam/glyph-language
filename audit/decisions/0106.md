# RFC 0106: Diagnostic style

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The test plan is written in the superseded syntax: `fn main() io { ... }`, `put(...)`, and `;` in `diag/v4-trap-after-output` and `diag/v4-record-order`. RFC 0104 removes all three, so those programs fail to parse under the grammar this RFC depends on. Change: rewrite each test program in RFC 0104's canonical form (for example `main io{put 1 put 1/0}`, `main io{let let=1}` with its offsets recomputed) and recompute the spans.
- designer-prag: reject. D2 keeps the E0xxx code form, but principle 8 allows a longer form only when measurement shows models make fewer errors with it; the RFC cites no such measurement and the bench has no finding on code spelling (E0006 costs one token more per record than E6). Change: either add a measured repair-error comparison of E0006 against E6 to Cost, or switch D2, the examples and the tests to E6.
- impl-1: reject. The substance (one-line JSON record, plain trap line, exit 1) matches RFC 0105 and the core spec. But every test program is in the superseded syntax (fn main() io, put(...), spaces inside braces). Under lexical-syntax-v6 those fail in the lexer at the first non-canonical space (E0002) or at the name after fn (E0100), before the expected records, and the byte offsets are wrong for canonical programs. The RFC also does not name its dependency on RFC 0104 and RFC 0105, and it depends on the owner's reading of the 2026-11-20 ruling (open question 1). Resubmit with tests written in the v6 syntax and with the dependencies named.
- tester: reject. Its test programs use syntax that lexical-syntax-v6 (RFC 0104) removes: `fn main() io {`, and `()` on a declaration with no parameters (G9, G12, L3). It does not name RFC 0104 as a dependency. Under 0104, diag/v4-record-code (`fn main() io { let let = 1 }`) gives E0100 at `main` (bytes 3 to 7), not E0003 at bytes 19 to 22; diag/v4-record-fix and diag/v4-trap-line fail the same way. The Design and the trap, record and exit-status rules are otherwise consistent with RFC 0050 and TR1, and TRAP_LINE and TRAP_KINDS match the compiler. Resubmit with the test programs rewritten in the 0104 syntax (for example `main io{put 1}`), or with 0104 named as a dependency.
- user-1: abstain. The compact record is short, but a user who has only the CLI and the card gets a code and a byte span with no message. The RFC says the meaning lives in spec/errors.json, and I cannot confirm from the card or the CLI how a user reaches that file. The current card still describes the old message-bearing format, so I cannot check the new one against it. I would vote after the RFC says how the catalogue is reached from the CLI.
- user-2: approve. Compact records with code, span and fix cost fewer tokens than the current format and still give a stable code and exact bytes. A model can act on that. For a user who only has the card, a bare code is hard to read unless the card says where each code's meaning lives. The card's diagnostics section still describes the old fields (message, severity, file, line, column) and must be updated when this is adopted.
