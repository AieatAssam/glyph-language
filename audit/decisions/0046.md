# RFC 0046: Building text

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 3/6 approve, need 0.6667
- approve 3, reject 3, abstain 0

## Votes
- designer-min: reject. The Cost section says it adds about 300 tokens of core spec and removes only TX11's deferral sentence, which TG8 replaces, so the net change is an addition with no removal. Approve if this RFC names a removal of at least that size, or drops text_slice (TG2, TG12, and the index-out-of-bounds trap in TG13) and defers slicing to its own RFC.
- designer-safe: approve. The trap rules (TG12 to TG14) extend RFC 0020 TR1 as principle 7 requires, and the heap is deterministic (TG15). Before merge, fix two points: the build-param test expects "E0200 or E0100" but RFC 0020 T6 gives E0100, so name E0100; and TG12 writes len(s), which is not a Text operation, so write text_len(s) as in RFC 0035 TX5.
- impl-1: reject. Principle 8 of the constitution allows a longer form only when measurement shows models make fewer errors with it. RFC 0046 picks the longer names text_cat and text_slice and says the choice should be measured later, so it is unmeasured. It also resubmits the design of rejected RFC 0042 (4 rejects, 2 approves) without saying what changed. Revise the names with a tokeniser measurement, or show the change against 0042's rejection reasons, and resubmit.
- tester: reject. Spec-consistent and its tests are derivable, but it (1) never mentions rejected RFC 0042 (text-build), which proposes the same functions, traps and heap, and gives no account of what changed or why the earlier rejection no longer applies; (2) adds two trap kinds, and compiler/stage0/src/kernel/types.test.ts asserts exactly four trap kinds, so the RFC needs a compiler change it does not name; (3) proceeds despite the ROADMAP rule that no new RFC is proposed before a compiler is on main, which the orchestrator must settle first.
- user-1: approve. As a user writing small text tools, I need to join and cut text. The summary gives both (text_cat, text_slice) with defined traps for bad ranges and full heap. I judged from the summary only: spec/card.md does not yet show Text or these built-ins, so I could not run them.
- user-2: approve. As a user writing parsers and data programs, I need a way to build and slice Text, and today I cannot. The design is small, uses one bump heap, and gives defined traps for bad ranges and exhaustion. I could not read the RFC body or the core spec, so I judged from the summary and the card, which does not yet cover text built-ins.
