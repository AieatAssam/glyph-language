# RFC 0013: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. Its Lexical section depends on RFC 0003, which is rejected (see rfcs/0003-lexical-syntax.md status), and it contradicts RFC 0012 on the `\t` escape and on the lexed-but-unused `[ ]` and `.`. Change: take the lexical rules from the accepted lexical RFC, delete the `\t` escape, and drop `[ ]` and `.` from the lexed token set.
- designer-prag: reject. The lexical rules are 'those of RFC 0003 sections 1 to 12, without change' and the .gl rule comes from RFC 0002, but both are rejected in rfcs/, so an implementer has no normative lexical base. Change: restate the lexical rules the kernel depends on inside this RFC's Design section, including the reserved-word list that replaces RFC 0003 section 7, so the kernel stands without the rejected RFCs.
- impl-1: reject. The design is mostly sound, but it cannot be built alongside RFC 0012. It reserves io as a word, where RFC 0012 makes !io one token. It keeps the tab escape and the [ ] and . tokens that RFC 0012 removes. It gives leading-zero and bad-escape errors codes that differ from RFC 0012. Its NEWLINE rule differs from RFC 0012's. It also takes its lexical rules from RFC 0003, which is rejected. Resubmit it on RFC 0012's lexical base with these points settled. Its non-termination rule (no trap, no status) also needs a reviewer decision under principle 7.
- tester: reject. Conflicts with RFC 0012 on points that decide what programs mean. (1) Effect marker: RFC 0013 writes fn name(...): R io { and reserves io as a word, but RFC 0012 makes !io one token and says io is not a keyword; the RFC 0012 test fn main() !io { would not parse under RFC 0013. (2) Escapes: RFC 0013 lists \t as valid and uses it in kernel/print.test, while RFC 0012 makes \t an E0005 error. (3) [ ] . : RFC 0013 lexes them and gives E0100, RFC 0012 gives E0001 because they are not in the token set; RFC 0013 also suppresses NEWLINE inside [ ], which RFC 0012 rejects. (4) NEWLINE: RFC 0013 emits it only after statement-ending tokens, RFC 0012 emits it after any line end outside parens. (5) It takes its lexical rules from RFC 0003, which RFC 0012 replaces. Separately, kernel/loop-forever.test cannot be a stable conformance test because it depends on the harness killing the process, and the RFC's choice that a non-terminating program has a defined result with no status sits badly with constitution principle 7. Revise against RFC 0012 and drop or redesign the loop-forever test before resubmitting.
- user-1: approve. Int, Bool, Text, print, if, while, functions and example checks are enough for a first useful program, and the rules for overflow, division by zero and stack exhaustion are defined, which I need as a user. Two concerns, not blocking: (1) the summary names the I/O marker as io, but RFC 0012 tokenises it as !io; these must agree. (2) Bool cannot be printed in the kernel, so a user has to write their own text for true and false. The RFC states this clearly, so I accept it for the kernel. I only had the summary, not the full text.
- user-2: approve. Covers the minimum for a small program: Int, Text, bindings, functions, if, while, return and printing, with defined traps. Concern for later RFCs: Bool cannot be printed and Text has no operations, which will limit the parsing programs I write.
