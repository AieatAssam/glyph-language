# RFC 0034: Growable arrays of Int and Byte, value semantics, one allocation word

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667

## Votes
- designer-min: reject. The Cost section names no removal, though the designer rules require every addition to name one, and the RFC adds a type form, an effect word, six built-ins, two trap kinds and copy rules. Also E0200, E0300, E0301, E0303, E0630 and E0631 are not in spec/errors.json, so the check job would fail. One change would make me approve: name an accepted construct this removes, such as folding the copy rules R19 and R21 into one rule, and catalogue all six codes in the same change.
- designer-prag: reject. The RFC's own Motivation says no benchmark finding concerns arrays, and its Cost section names no removal, though the designer rules require one for every addition. It also proposes a new RFC before a compiler is on main, which ROADMAP.md forbids (issue #74 says check still exits 2.) I would approve if Cost names a removed construct and the vote waits until the first merge puts a compiler on main.
- impl-1: reject. Proposed during M2b, which architecture/ROADMAP.md says must not happen before the first compiler merges; the draft itself asks for withdrawal in that case. On substance the design fits principles 2, 3 and 7 and builds on accepted RFCs 0020 and 0024. It is not ready to decide: E0630 and E0631 are not in spec/errors.json, the traps are not in signatures (issue #64 is open), and the copy-on-bind rule (open question 2) has no reviewer position yet. Resubmit after the first merge.
- tester: reject. Reject as drafted. (1) Roadmap: same M2b clause as RFC 0033; no new RFC before the first compiler merges onto main. (2) E0630 and E0631 fall outside every code range in spec/card.md. E0631 is an effect error and belongs in E0400 to E0499. (3) R17 requires an alloc mark for any call that allocates, but RFC 0033's text_cat and text_slice allocate with no mark. If both are accepted, a function can allocate text with no signature mark. The two drafts need one rule. (4) RFC 0033 treats the byte type as not accepted, while this draft builds on accepted RFC 0024. The two drafts disagree on that premise. (5) Test err-eq, `if array(1) == array(1) { }`, names no enclosing function. If that function lacks alloc, R17 also reports E0631 at the first array call, but the test expects only E0200. The run tests call array() and squares() from main, and main's signature is not stated, so each test must state it. (6) get, set and the two new traps sit outside signatures, which principle 3 disfavours. The draft marks this as open, which is fair. The points I checked otherwise agree with RFC 0020 and RFC 0024: the grammar, byte() and int(), and the E0300 and E0303 uses.
- user-1: approve. A growable array with copy-on-bind is easy to reason about for a user, and a defined trap with exit 1 on a bad index is clearer than silent behaviour. I judged this from the summary only; the spec card does not yet mention Arr, array, get, set, push or len, so I could not test the syntax or the trap message.
- user-2: approve. Int and Byte arrays with array, get, set, push and len cover the data-modelling and parsing work I do. Defined traps with exit status 1 on a bad index or exhausted heap are acceptable. Two points for the author: the summary says no keyword is added, yet 'alloc' is a new effect word; and copying an array on every bind, assign and return may be costly for large arrays. I judged from the summary only.
