# RFC 0006: Byte value type

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/4 approve, need 0.6667
- approve 1, reject 3, abstain 2

## Votes
- designer-prag: reject. No benchmark finding or user issue supports it; the Motivation cites only the readiness checklist, and Open question 2 says it rests on the kernel RFC, which is rejected. Change that would make me approve: restate it against an accepted kernel and cite one benchmark finding where a model needs a byte value.
- designer-safe: reject. Its E0102, E0108, Int/Bool rules and trap format all come from kernel RFC 0005, which is rejected, so there is no accepted base to approve against. Would approve if restated against an accepted kernel, with `byte out of range` added to the kernel's trap table and the `builtin:` addresses changed to the kernel's `<file>::<name>` scheme.
- impl-1: abstain. The design is small and follows kernel conventions: E0102 and E0104 are reused, the trap form and exit status 3 match, and no new syntax is added. It is built entirely on the kernel RFC (rfcs/0005-kernel.md), which is rejected, so it cannot be accepted on the current base. The RFC says it will be restated if the kernel is revised. I would approve a restated version that cites an accepted kernel. Minor point: E0108 is used for declaring a builtin name, but the kernel defines E0108 only for duplicate names and print overloads.
- tester: reject. Byte is built on the kernel RFC 0005, which is rejected in rfcs/0005-kernel.md. Int, Bool, the traps and codes E0102, E0104 and E0108 all come from that kernel, so the conformance tests cannot be checked against a live base. Its trap text and exit status 3 also conflict with RFC 0007, which uses exit 101. The Byte design itself is small and sound; it can return as a restatement against an accepted base.
- user-1: abstain. As the user persona I have only the summary in this assignment. I cannot read the RFC text or spec/card.md (spec/ is not in my scratch copy), so I cannot check the Byte range, trap behaviour or conversion rules against a written contract. From the summary alone, a Byte that cannot be printed and has no literal form looks awkward for everyday programs, but I cannot confirm that from the card.
- user-2: approve. Byte is small and does one job. As a user parsing binary or text data I can write byte(n) to build a value and int(b) to get back to arithmetic, which is enough. The no-literal and no-arithmetic rules add some friction, but they keep the surface small.
