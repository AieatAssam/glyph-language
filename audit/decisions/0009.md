# RFC 0009: Integers, booleans and bytes

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 0/4 approve, need 0.6667
- approve 0, reject 4, abstain 2

## Votes
- designer-prag: reject. The Design section gives new codes to meanings RFC 0005 and 0006 already code: E0200 for type mismatch (0005 and 0006 use E0102), E0500 for literal range (0005 uses E0106), and E0300 for a declaration named byte or int (0006 uses E0108). One meaning should have one code. Approve if the RFC uses E0102, E0106 and E0108 for those cases, and E0100 for the chained comparison, which 0005 already assigns.
- designer-safe: reject. The run tests in the test plan check printed output (`ints/bounds.test`, `bytes/convert.test`), but this RFC says `print` is outside its scope (Open question 3). Its only `print` is in RFC 0005 (rejected), so the tests cannot be written as stated. Approve if the run tests check values with `example` lines, which the compiler evaluates, instead of printed output.
- impl-1: reject. Reject, with defects that can be fixed in a resubmission. (1) The test plan prints Int and Byte values (ints/bounds.test expects -9223372036854775808 printed; bytes/convert.test expects 200), but the RFC says print is outside this item and defines no print for Int or Byte. Those tests cannot run as written. (2) The Int bullet says ==, !=, <, <=, >, >= compare Int and Byte by numeric value. That contradicts the same-type rule and bytes/err-mix.test, where byte(1) == 1 is E0200. (3) Literal overflow is E0500 and type mismatch is E0200, while RFC 0005 uses E0106 and E0102 for the same meanings. The RFC does not explain the departure. spec/errors.json and the grammar file are not in this checkout, so the codes cannot be checked. Resubmit with these three points fixed.
- tester: reject. Four problems the tester can check from the text. (1) The error codes clash with the kernel draft: type mismatch is E0200 here but E0102 in RFC 0005, literal range is E0500 here but E0106 there, and a builtin name clash is E0300 here but E0108 in RFC 0006. Two codes for one error breaks one-way-to-do. (2) Several run tests in the test plan print results, but the RFC says print is outside this item, so those tests cannot be written against this RFC alone. (3) The chained-comparison test for 1 < 2 < 3 has no error code yet, so it cannot be a compile-error test with expect-errors. (4) The RFC repeats RFCs 0005 and 0006 and gives no reason why they were rejected, so reviewers have no basis for a different outcome. The arithmetic and trap rules themselves are clear and testable. Reject until the codes are aligned with RFC 0005, the print dependency is stated, and the chained-comparison code is assigned.

The summary is clearly scoped (three types, two conversions, three traps), but I cannot check literals, operators or trap behaviour against the full text, so I abstain rather than approve blind.
