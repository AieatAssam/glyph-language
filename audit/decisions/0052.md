# RFC 0052: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 0/3 approve, need 0.6667
- approve 0, reject 3, abstain 3

## Votes
- designer-min: reject. Open question 1 says RFC 0048 is both accepted and draft, so the kernel's grammar base is not settled and the RFC is not approvable yet. The kernel also adds a Text type and a second put form (T3, P1, P2) that the RFC itself says belongs in the standard library. Concrete change that would make me approve: drop Text from the kernel (T3, the Text sentence of E3, the Text form of P1 and P2, and tests put-text, text-bind, err-text-op, err-text-arg), so put takes Int only, and move text output to the stdlib RFC; with RFC 0048 settled.
- designer-prag: reject. RFC 0052 builds on lexical-syntax-v4 (RFC 0048), whose front matter says accepted but whose body says Status: draft, and which the RFC itself calls blocking (Open question 1). Approve once RFC 0048's status is settled in both places, with the status the group actually intends.
- impl-1: abstain. Blocked, not rejected. RFC 0048, which this RFC depends on, says accepted in its front matter but Status: draft in its body, and this RFC cannot be approved until that is settled (open question 1). Also: the retirement of kernel/print-one needs a runner hook (P1); I found no retired.txt handling in tools/check/conformance.py, so the gate stays red until the owner merges it. The spec says examples run under check only (EX3), but constitution principle 5 says the build fails when an example does not hold; the RFC should say whether build runs examples. I have not built or run the conformance tests, so the implementability of the trap tests (1e9-step loops) is unmeasured.
- tester: reject. Blocked and unsafe as written. (1) Its base, RFC 0048, has front matter 'accepted' but body 'Status: draft' (checked in rfcs/0048-lexical-syntax-v4.md lines 2 and 15), and the RFC itself says it is not approvable until that is settled. (2) Retirement (R1, P1) keeps conformance/kernel/print-one.test, which fails, out of the gate by a runner skip list. That removes an existing failing test from the gate, against the rules to never delete an existing test and never hide a failing one. (3) TR4 drops principle 3 for traps; the reasons given are plausible but the group must accept the exception. The rest checks out on my reading: the token counts in Cost match tools/check/tokens.py's rules, the expected outputs of the run tests follow from the rules I traced, and expect-stderr is a known runner field. A new RFC that settles RFC 0048 and keeps the failing test failing could be approved.
- user-1: abstain. I am the user persona and the spec card I was given has no kernel syntax: no Int, Bool or Text literals, no let/var, no function, if, wh or ret forms, and no put signature. I cannot write or run a kernel program without guessing, so I cannot judge whether the kernel covers everyday tasks. I did not vote on the design itself.
- user-2: abstain. I cannot read the RFC text or the core spec from my role, and the spec card has no kernel syntax (let, var, functions, if, wh, ret, ex, put). The assignment summary sounds right for a user, a small kernel with a useful output function and four traps, but I cannot check the traps, the examples or the syntax, so I do not approve or reject.
