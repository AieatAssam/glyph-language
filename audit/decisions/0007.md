# RFC 0007: Text

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The Cost section says it removes nothing, so about 350 core tokens are added with no removal, which breaks the rule that every addition names what it removes. Approve if the four ordering operators and the `\0` escape are cut (open question 2 already calls `\0` redundant with `\u{0}`) and Cost states the net token change.
- designer-safe: reject. It defines `text` while kernel RFC 0005 already defines `Text` for the same concept, and rule 9 makes runtime traps catalogued diagnostics where the kernel says a trap is 'not a diagnostic'. Would approve if it uses the kernel's `Text` name and trap kinds with exit status 3, drops the duplicate escapes (`\0`, `\r`, `\t` next to `\u{...}`, which breaks principle 1), and cites the right RFCs: 0003 is lexical syntax in this repo, and the effects `alloc` and `trap` are defined nowhere.
- impl-1: reject. Wrong sources: RFC 0003 (lexical syntax) has no effect, trap or alloc model, and RFC 0002 is the name RFC, so the cited dependencies do not hold. Trap exit codes conflict: 101 here, status 3 in the kernel and RFCs 0006 and 0008, status 1 in RFC 0004. Trap is listed as an effect in signatures, but kernel traps are not in signatures. Names clash with the kernel and RFC 0006: lowercase text, int, byte and bool, where the kernel uses Int, Bool and Text and RFC 0006 uses Byte and int() as a function. len gets a second signature, but the kernel says print is the only overloaded name. The escapes give two spellings each (\n and \u{A}, \0 and \u{0}), which breaks one way to do each thing. Trap codes are catalogued as diagnostics, against RFC 0004 rule 5, and new codes are numbered from the next free number, not from the block rule in RFC 0004.
- tester: reject. Four problems. (1) Traps exit 101 (rule 9), but RFCs 0006 and 0008 use the kernel trap form with exit 3. (2) Type names are lowercase text, int and byte, while the kernel and RFC 0006 use Text, Int and Byte; RFC 0006 also makes int a built-in function name. (3) len is defined here for text and in RFC 0008 for arrays, so one built-in name has two signatures. (4) Rule 11 relies on arenas, which RFC 0008 says are not part of its scope and which no RFC defines. The compile-error tests name no codes, so they cannot be written yet. The \0 escape duplicates \u{0}, against principle 1.
- user-1: abstain. As the user persona I have only the summary in this assignment. I cannot read the RFC text or spec/card.md (spec/ is not in my scratch copy), so I cannot check the literal form, UTF-8 validity rules or slicing behaviour against a written contract. The summary's scope (no code-point handling, no number formatting) would limit everyday text work, but I cannot confirm what the card will say.
- user-2: approve. Text with literals, byte length, byte indexing, slicing and concatenation covers what a parser needs. Keeping code points and formatting out of the core is reasonable for a small kernel.
