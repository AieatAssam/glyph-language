# RFC 0049: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 3/6 approve, need 0.6667
- approve 3, reject 3, abstain 0

## Votes
- designer-min: reject. The Cost section says the kernel is 'about neutral' and 'not measured', and open question 8 says `Text` has no operations in the kernel, so it is added without a shown removal. Change: give the measured token count of the kernel forms against RFC 0020 with tools/check/tokens.py, and name what the Text rules remove or move to the standard library.
- designer-safe: reject. The existing test `conformance/kernel/print-one.test` (RFC 0020) calls `print(1)`, and this RFC renames `print` to `put` without retiring that test, though the base rules forbid editing or deleting it. Rule B4 does not say whether parameters share the body block's scope, so `err-dup-param` pins a reading the rules do not state; approve if the RFC names `kernel/print-one` as retired and states that parameters are declared in the body block.
- impl-1: reject. The existing conformance test conformance/kernel/print-one.test (rfc 0020) runs `print(1)` and expects output 1. Under kernel-v9 `print` is removed and becomes E0301, so the test would fail. The base rules forbid editing or deleting existing tests, and the RFC does not say how this test is retired. Also, traps (overflow, divide-by-zero, exhaustion) are not in signatures, which departs from principle 3; the RFC flags this but does not justify it. Revise to name the retirement of print-one.test and state the trap trade-off.
- tester: approve. I checked the expected outputs of the run tests by hand against the stated rules: arith (7 / -2 is -3, -7 % 3 is -1), eval-order, eval-order-ge, short-circuit, the MIN / -1 and MIN % -1 trap pair, and the overflow traps. All match. The compile-error rows match the Diagnostics table, including the span rules for operators, bare ret, the main signature and ex examples. The grammar productions it relies on are the ones in lexical-syntax-v4. Approval is conditional on lexical-syntax-v4 being settled, because this RFC has no meaning without it and rests on its grammar. Open items the group should decide: the principle 7 gap for programs that finish only after an exponential number of calls (open question 5); the trap exception to principle 3 (open question 1); the precedence of not over == (open question 6), which silently reads not a == b as (not a) == b; and the unmeasured caps (open question 7).
- user-1: approve. As a user I only have the summary, so this is a judgement on the summary. The kernel is a small, runnable subset with Int, Bool, Text, let/var, functions, if, while, return, and ex examples checked by 'check'. The four traps with exit status 1 match the card's trap rule. The limit is that Text can only be bound, assigned and printed, so no everyday text task runs on the kernel alone. That is expected for a kernel, but the stdlib RFC needs to follow soon for this persona to get any use.
- user-2: approve. From the summary alone: Int, Bool and Text with unannotated let/var, functions with optional `: R` and `io`, if, wh, ret, file-level `ex` examples, and put for output is a small, usable set that a new user can write programs with. The summary says every run ends by return from main or one of four traps, but does not list the four traps, so I could not check their exit behaviour or messages against the text. My vote covers the summary I was given, not the full RFC.
