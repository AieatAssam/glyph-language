# RFC 0087: Growable arrays with no mutable aliasing

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. N9 only forbids copying a handle from a var or a parameter, so `let a = arr()` followed by `var b = a` is accepted. Then `set(b, 0, 1)` changes what `a` reads, which breaks the RFC's own rule that a mutable array is never reachable from a second name (N9, N11). Approve if N9 also makes `var` binding of any array handle an E0203 unless the source is a fresh `arr()` or `copy()` result.
- designer-prag: reject. It builds on RFC 0020, which RFC 0086 says RFC 0085 replaces, and it uses `print`, not `put`. It also reuses E0403, which RFC 0085 F7 defines as the fail-mark error, for set/push on a non-var name. Concrete change: rebase on RFC 0085 and give the mutability error a new, unused code. The RFC also says no benchmark finding supports arrays.
- impl-1: reject. Four defects. (1) It builds on and amends RFC 0020, which RFC 0085 replaces, and its examples use print, which RFC 0085 retired in favour of put; it also uses a let/var type annotation that RFC 0085 B1 forbids. RFC 0086 has the same problem and fixes it by targeting 0085. (2) Its E0403 means set or push on a non-var, but RFC 0085 already defines E0403 as the fail-mark error (F7); its catalogue check looked only at RFCs 0014, 0020 and 0024, so the collision was missed. (3) get, set, push and copy can trap (index-out-of-range, heap-exhausted), but it does not amend F7, so under RFC 0085 a function that calls get without fail compiles and runs with a trap, which F7 does not allow. (4) The rules for let-bound names that come from arr() or copy() (N9) are unclear. Also see the M2b hold in ROADMAP.md. The author could resubmit against RFC 0085 with F7 amended and the codes checked against 0085.
- tester: reject. Reject. Checked against RFC 0085 in the repo. (1) It builds on RFC 0020 and cites its rules T6, F1 and TR1, but RFC 0085 supersedes that kernel. Its example uses var a: Arr(Int) with an annotation, which B1 does not allow, and print, which P1 replaces with put. (2) Aliasing hole in N9: let a = arr(); var b = a; push(b, 1) is not forbidden, because N9 only covers copies from a var or a parameter. Writes through b then show in a. (3) N5 adds traps (get, set, push, copy) but does not extend fail-mark rule F7, so the example's main, which calls get, has no fail and would be E0403. (4) N8 reuses E0403 for set and push on a non-var. RFC 0085 F7 already gives E0403 the fail-mark meaning, so the claim that no code collides is wrong. The milestone gate in ROADMAP M2b should also be confirmed by the orchestrator before any vote.
- user-1: abstain. The summary is clear about the goal: one growable array type, a single word added (alloc), and defined traps. But its rules on aliasing, read-only views and returns from parameters are the part that matters most for user programs, and I only have the summary, not the full text. I cannot check those rules, so I am abstaining rather than approving on the summary alone.
- user-2: approve. Data-modelling and parsing programs need a growable array, and the get, len, set, push and copy names are short. The no-alias rule will reject some code that a user expects to work, so the compile error for binding a mutable array must name copy as the fix. I judged this from the assignment summary only, because my role does not read RFC bodies, so I did not check the diagnostic wording or the heap-exhaustion trap.
