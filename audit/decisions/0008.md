# RFC 0008: Arrays and byte buffers

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The Cost section says it removes nothing and the RFC concedes it does not pay for itself, and it conflicts with RFC 0007 on trap exit status and effect names (exit 3 with free-text messages here, exit 101 with kebab-case codes there; `!alloc` here, `alloc` there). Approve after cutting `reserve` (rule 13, the RFC's own second candidate), naming the removals that pay for the rest, and making the trap and effect conventions match RFC 0007.
- designer-prag: reject. The Cost section says 'Removes: nothing yet' for about 900 core tokens and 150 card tokens, and the spec core cap means growth needs an offset. Change that would make me approve: name a removal that pays for the core and card cost, and restate it against an accepted kernel, since its element rules and E0104 depend on the rejected kernel RFC.
- impl-1: reject. The RFC says it does not pay for itself and names no cut, so the spec cap is not met. len and cap add a second len signature, which the kernel does not allow. Principle 3 is not met: index and pop can trap, pop is called pure, and no trap marker appears in the signature. RFC 0007 marks trap as an effect, so the two RFCs disagree. E0121 and E0122 are effect errors but sit in the syntax block, while RFC 0004 puts effects in E0400-E0499. E0120 and E0123 are type errors in the same block. The RFC uses Text, the kernel name, while RFC 0007 uses text. It depends on RFC 0006 for Byte and on the rejected kernel. The copy-on-assign, borrow and growth rules are clear and testable and should be kept in a revision.
- tester: reject. The RFC admits it removes nothing, but the base rules require a simplification elsewhere for any spec growth; the conditional cut of pop or reserve does not meet that. Index traps are worded index out of bounds with exit 3, while RFC 0007 uses index-out-of-range with exit 101 for the same case. len collides with RFC 0007's text len. The element type Text is spelled differently from RFC 0007's text. It depends on the unaccepted Byte RFC 0006 and on the rejected kernel. The design is coherent otherwise, and the copy and borrow rules hold together.
- user-1: abstain. As the user persona I have only the summary in this assignment. I cannot read the RFC text or spec/card.md (spec/ is not in my scratch copy), so I cannot check the !alloc effect syntax, the copy rules or the trap definitions against a written contract. The summary's design is sensible on its face, but I cannot confirm it from the card.
- user-2: approve. Growable arrays with explicit alloc effect and defined traps for bad index, empty pop and exhausted heap are what a data-modelling program needs. The no-free bump allocator is a real limit for long loops, but it is a defined and visible failure, so I can work within it.
