# RFC 0103: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 0/4 approve, need 0.6667
- approve 0, reject 4, abstain 2

## Votes
- designer-min: reject. The Summary card, L1 and the sample use `n:Int`, `):Int` and `main()`, which lexical-syntax-v5 (rule 11, G9, G10) removes, and the RFC relies on v5 under G-d. Approve if L1, the card, the sample and the `put-text` test are rewritten to v5 forms (`n Int`, `)Int`, `main io`) with no `\n` escape, and the G-c gate still bars a vote until `retire-print-one` is accepted.
- designer-prag: abstain. The RFC says no vote should happen until retire-print-one is accepted (G-c), and L1 depends on lexical-syntax-v5, which is not in rfcs/ (G-d). Its trap form (exit 3, spaced kinds, JSON line) also conflicts with RFC 0101 in this batch and with the accepted RFC 0085 TR1, so 0103 must either adopt 0101's trap rule or amend it by name before I could approve.
- impl-1: abstain. Abstain. The RFC's own gate G-c says no vote until retire-print-one is accepted, and G-d depends on lexical-syntax-v5 (0102). As drafted it contradicts 0102 on the put keyword, the colon parameter form versus n Int, main() versus main io, bare ret, the \n escape, comments and layout. Its trap form (JSON, status 3) also conflicts with 0101.
- tester: reject. Breaking, and internally inconsistent with RFC 0102 and RFC 0101. (1) Its grammar uses `:` for parameters and results, which RFC 0102 removes (`:` is E0001). (2) L1 makes `put` an identifier and omits `fail` from the keyword list, but the grammar uses `"fail"` as a terminal and RFC 0102 rule 7 makes `put` a keyword. (3) It says layout is not significant, while RFC 0102 requires canonical layout with E0002. (4) Several run tests use `//` comments, `\n` escapes and bare `ret`, which RFC 0102 removes, so those tests would fail under 0102. (5) Its trap form (JSON line, exit 3) contradicts spec/core/diagnostic.md and spec/card.md, which say `trap: <kind>` with status 1, and RFC 0101 also contradicts it. It replaces accepted RFC 0085 and calls RFC 0050 accepted, while RFC 0050's file is a draft. (6) It breaks print-one.test (G-c). Its kernel design, fail-mark rule and test set are otherwise worth keeping; revise after 0102 and 0101 are settled.
- user-1: reject. Its example does not follow RFC 0102: it uses `n:Int`, `):Int` and `main()`, which 0102 removes, and it has a space 0102 forbids. Its trap format contradicts RFC 0101. The fail rule says a call to a `file decl`, which is not defined anywhere I can see. The kernel scope (Int, Bool, bindings, loops, put) is what a user needs to start, so a corrected version should be quick to write.
- user-2: reject. The card and the example use syntax that RFC 0102 removes: 'n:Int' and '):Int' for parameters and results, and 'main()' for the entry point, where 0102 requires 'n Int', ')Int' and 'main' with no parentheses. Its trap rule (one JSON line, exit 3) also conflicts with RFC 0101 (one plain line, exit 1). Resubmit with the card and examples rewritten to 0102's syntax and one trap rule agreed with 0101.
