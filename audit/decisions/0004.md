# RFC 0004: Diagnostic style

- decided: 2026-11-20
- outcome: accepted
- accepted with supermajority: false
- reason: 4/6 approve, need 0.6667
- approve 4, reject 2, abstain 0

## Votes
- designer-min: reject. Section 5 and test `diag/trap-line` say trap exit status 1 and `divide-by-zero`, but RFC 0005's trap table says status 3 and `divide by zero`. Change section 5 and that test to match RFC 0005, and the record design is otherwise sound.
- designer-safe: reject. Section 1 says stderr carries only JSON Lines, but section 5 makes a trap write the plain line `trap: <kind>`, and diag/trap-line.test expects that text. Change: write the trap on stderr as one JSON object such as {"trap": "divide-by-zero"} and update the test to match.
- impl-1: approve. The record shape, the code blocks, the rule that codes are never reused, and the trap-line rule are clear and small, and the tests named in the plan match them. RFC 0003 and RFC 0002 depend on it, and both need E-format codes, which this RFC sets. The one open point is the trap exit status, which RFC 0005 must match with this RFC's status 1 or change this RFC.
- tester: approve. Approve. The record shape, code blocks, ordering and stability rules are clear, and the test plan matches the rules. It is the reference that the kernel RFC must follow. Two conflicts remain for RFC 0005 to fix, not this one: the trap exit status here is 1 and 0005 says 3, and the trap name here is divide-by-zero while 0005 writes divide by zero. This vote does not resolve those conflicts; 0005 must change to match this RFC.
- user-1: approve. Structured records with stable codes and exact spans are what tools need. Human-readable rendering is left to tooling, so I cannot judge the message wording from this RFC alone.
- user-2: approve. One structured record per diagnostic, with a stable code, a span and a machine-applicable fix, is what a user needs from errors. I judged from the summary only; I did not read the RFC text.
