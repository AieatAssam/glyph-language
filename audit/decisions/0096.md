# RFC 0096: Building text (text-cat)

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 0/4 approve, need 0.6667
- approve 0, reject 4, abstain 2

## Votes
- designer-min: reject. The Cost section adds about 220 tokens of core spec and removes only a prose sentence in RFC 0035 TX11, not a construct, and the cost is an estimate that the tokeniser has not measured. Approve if the RFC names a grammar rule, built-in or trap kind of at least the same measured token size that it removes, and reports the tokeniser count for the added text.
- designer-safe: reject. TC4 fixes a 1048576-byte heap and TC7 forbids `memory.grow`, but the Design never says where the heap sits in linear memory, how many initial pages the module declares, or how a `Text` value points into it, so an implementer who has not seen the discussion cannot build it. Approve if a Design subsection fixes those three things; I re-derived the 19-call and 20-call counts in `cat-fill` and `cat-exhaust`, and they hold.
- impl-1: reject. The constitution's principle 3 says that whether a function can allocate or fail must be visible in its signature. RFC 0096 adds a built-in that allocates from a heap and can trap heap-exhausted, and TC9 says the trap is not in the signature. Its allocation is not marked either. The constitution makes this conflict a merge-bot rejection whatever the votes, so the RFC cannot be accepted as written. The rest is sound: the arithmetic checks in TC6 and the test sizes in cat-fill and cat-exhaust are correct. The RFC should be revised so that text_cat carries an allocation and fail mark, or a new RFC should settle how marks work for built-ins. It also cites RFC 0020 (kernel-v8) as its base, and that is not the only kernel draft in the repo, so the amendment target needs a check.
- tester: reject. Three problems. (1) Constitution principle 3 says whether a function can allocate or fail must be visible in its signature. text_cat is the first built-in that allocates, and TC9 keeps its signature as (Text, Text) -> Text, deferring the question to issue #64 without weighing it against principle 3. (2) TC9 cites RFC 0020 E9 for the rule that the trap stays out of the signature, but E9 only says overflow and divide-by-zero are run-time traps. (3) The test plan asserts 'stderr contains trap: heap-exhausted' in text/cat-exhaust and text/cat-arg-order. SPEC section 7 defines no stderr field for kind trap, so these two tests cannot be written in the container as specified. What I checked and found correct: the byte counts in cat-fill (19 doublings give 2^19, using 2^20 - 2 bytes), cat-exhaust (the 20th call traps), and cat-arg-order (2 bytes remain, so the call traps). Reconsider after the signature question is decided and the trap assertion format is defined in SPEC section 7.
- user-1: abstain. As a user I cannot judge this RFC. The assignment gives a summary only, and spec/card.md does not mention a Text type, string literals or any built-in function, so I cannot check how text_cat would be written or what Text values look like. I would vote approve if the card showed Text and the call form.
- user-2: abstain. I want text building, since my parsing and serialising programs need to join strings. But the card does not mention Text or any text function, so I cannot confirm the feature from my side. The RFC also seems to conflict with the constitution: principle 3 says a function's allocation and failure must show in its signature, and text_cat allocates and traps on exhaustion while its type is only (Text, Text) -> Text. Principle 8 also favours short names, and text_cat is longer than the alternatives. I abstain so the authors can answer the signature question before I decide.
