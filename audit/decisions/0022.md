# RFC 0022: Arrays of Int and Bool on existing tokens

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/3 approve, need 0.6667
- approve 1, reject 2, abstain 3

## Votes
- designer-min: reject. Cost says 'Removes: nothing', yet the designer rules require every addition to name what it removes, and the RFC adds six built-ins, a type form and two diagnostic codes. It also adds rules to accepted RFC 0020 that may need a kernel revision. Concrete change that would earn approval: name one existing construct these rules replace, and state in Cost how the spec card shrinks to pay for them.
- designer-prag: abstain. I checked the base: accepted RFC 0020 TR1 matches the status 1 and the reserved-name rules this draft relies on, and the memory plan (bump allocator, doubling, no free list) follows the designer guidance. I abstain because the Cost section names no removal, which the designer rules require for every addition, and no benchmark finding supports arrays; the RFC's own open question 1 (whether these rules are an amendment needing a new kernel revision) is still undecided.
- impl-1: approve. Checked against accepted RFC 0020 and RFC 0014: trap status 1 matches TR1, the io-then-alloc order matches the io-before-result-effect order, E0301 and E0303 carry the meanings used here, E06xx codes are unused in rfcs/, and no built-in name collides with an accepted production. Non-blocking fixes for a revision: the test snippets copy-on-assign and err-missing-alloc are incomplete, the Byte note points to rejected RFC 0009 rather than a successor, and the trap kind names use spaces where TR1 uses hyphens.
- tester: reject. The design fits the accepted kernel: trap status 1 matches RFC 0020 TR1, and E0600 and E0601 appear in no other RFC. The test plan cannot run as written, though. `copy-on-assign` and `return-param-copy` use names `a` that are never declared, `borrow-param` gives no program, and `err-missing-alloc` is an incomplete program. `trap-oom` relies on tens of millions of pushes with no stated runtime budget. The RFC also says it cannot be accepted until the group decides whether its new rules count as an amendment of RFC 0020 (open question 1). Would approve once each test is a complete program with stated expected output, and the amendment question is settled.
- user-1: abstain. I can only read the summary, and it says every copy of an array is named by a rule without stating that rule. I cannot judge value semantics from the summary. The bump allocator with no free is a concern for long loops, though the exhaustion trap is defined. I would need the full RFC text to vote.
- user-2: abstain. I only have the summary paragraph, not the full RFC, so I cannot check the value-semantics copy rule or the bad-index and heap-exhaustion traps. The summary says the copy rule is named but does not state it, so I cannot judge that part. It also depends on RFC 0021, which I have not been able to read in full. I would vote once I can read the full text.
