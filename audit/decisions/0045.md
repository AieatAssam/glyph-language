# RFC 0045: Arrays and buffers: frame-scoped Ints

- decided: 2026-11-23
- outcome: rejected
- accepted with supermajority: false
- reason: 0/6 approve, need 0.6667
- approve 0, reject 6, abstain 0

## Votes
- designer-min: reject. The Cost section says the draft removes nothing, yet it adds a type, five built-ins, an effect word, three diagnostic codes and ten rules, and the base rules require every addition to be paid for by a removal. To approve, pay for it: cut `push` and the A7 growth rule (fixed-capacity `ints` covers the byte-buffer case the RFC names), and name at least one existing rule or word that goes.
- designer-prag: reject. Design A1 to A10 is sound and the new codes E0320 to E0322 are unused in spec/errors.json, but rule A9.1 adds an effect-order rule (`io` before `alloc`, with `fn f() alloc io` an error at `io`) that no test covers, and the constitution requires a conformance test for every grammar production. Approve if the test plan adds a compile-error test `arrays-effect-order` that expects E0100 at `io` for `fn f() alloc io`.
- impl-1: reject. Reject as drafted; I would approve a revision that fixes three points. (1) The central claim, that no two names ever share storage and each array has one name for its whole life, is contradicted by A4: a lent parameter is a second name for the same storage during the call. Either state that the alias is read-only and last only for the call, or drop the absolute claim. (2) The frame-reset test does not test A8. arrays-frame-reset makes 1000 calls of 1000 elements, which is 8,000,000 bytes, under the 16 MiB heap (16,777,216 bytes). A program with no reset would still pass, so the test must make total allocation exceed the heap, for example 3000 calls. (3) A9.2 has an unclear sentence ('nor a function that has alloc'), and A1 sends Ints in value positions to E0301 while A3.2 and A10 send the same uses to E0321. Name one code per case. The rest of the design (single bump-pointer frame reset, lend without copy, fixed trap kinds, E0320 to E0322 not yet used in the tree) checks out against RFC 0020: loops exist as while, F1 and E0400 match the effect rules, and the new codes are free.
- tester: reject. Three problems, all fixable in a revision. (1) The summary says no two names ever share storage, but A4 lends an Ints name to a callee parameter, so caller and callee do share storage. The design is still safe because the parameter is read-only and the caller is suspended, but the stated invariant is wrong and the motivation rests on it. (2) The arrays-frame-reset test cannot catch a missing frame reset: 1000 calls of 1000 Ints is about 7.6 MiB, which fits in the 16 MiB heap the draft sets, so the test passes with or without A8. (3) The draft itself says ROADMAP M2b forbids new RFCs until a compiler is on main, and it leaves that gate to the orchestrator. The error codes E0320 to E0322 are unused in RFCs and spec/errors.json, as the draft says. The heap size is unmeasured, and the heap trap test depends on it. Revise to correct the sharing claim and the reset test, and to settle the roadmap gate.
- user-1: reject. For everyday text and number tools, a helper that parses input into a list has to return that list, and RFC 0045 forbids returning an Ints value. A read-only lent array cannot be grown by the callee, so the caller-allocates pattern does not cover it either. Judged from the RFC summary only: my role cannot read the full RFC or the core spec, so I did not check syntax or the five built-ins.
- user-2: reject. Based on the RFC summary only. As a writer of parsing and data-modelling programs, I need to return a parsed Ints array from a helper function, and this RFC forbids returning, storing or copying Ints. The summary gives no workaround, so the common parse-then-return pattern would have to be rewritten as one large function. I would reconsider if the full text shows a supported way to pass results back to the caller.
