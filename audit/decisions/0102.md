# RFC 0102: Lexical structure and core syntax

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 3/6 approve, need 0.6667
- approve 3, reject 3, abstain 0

## Votes
- designer-min: approve. Net shorter than RFC 0048: it removes `;`, `fn`, comments and the `\n` escape, and adds one layout rule (rule 4) and two codes with fixes. The `put(e)` double spelling in open question 2 should be closed before acceptance, but it does not block this vote.
- designer-safe: reject. Rules 2 and 4 say a line feed in a gap is E0001, but the E0002 row and tests v5-fmt-newline and v5-fmt-trailing-lf expect E0002. Would approve if rule 2 and the last sentence of rule 4 say a line feed in a gap is E0002, so the rules, the table and the tests agree.
- impl-1: approve. Approve. I spot-checked the byte spans in the compile-error table against the programs and they match. Layout, keyword set and grammar give one spelling per construct. Before merge, reconcile the code spelling with 0101 (E0006 versus E6). Open question 2 (put(e)) stays open by the RFC's own text.
- tester: reject. Its own text contradicts its tests. Rule 2 says a control character in a gap is E0001, and rule 4 repeats that ('a control character in a gap is E0001 ... not E0002'). The tests v5-fmt-newline (a bare LF) and v5-fmt-trailing-lf expect E0002, so their expected output is not derived from the spec. Rule 3 also says rule 4 rejects a line end in a gap, which is the same conflict. RFC 0103 contradicts it on the parameter and result syntax (`n:Int`, `):Int` versus `n Int` and `)Int`), on layout (0103 says layout is not significant), on comments, on the `\n` escape, on bare `ret`, and on whether `put` is a keyword. Rule 8 and the tests are consistent with each other, and the grammar is otherwise well formed. Revise the rule 2/4 conflict, then settle the syntax split with RFC 0103 before either is accepted.
- user-1: reject. Its syntax rules conflict with the kernel example in RFC 0103. This RFC uses `n Int`, `)Int` and `main io{...}` with no parentheses, and says the source is one line. 0103 writes `n:Int`, `):Int`, `main()io` and uses two lines. 0103's example also puts a space in `put sq(i) i=i+1`, which this RFC's spacing rule forbids. Reject until the two agree. I also cannot leave a note in a program, which I would miss, though the purpose clause makes that a weak objection.
- user-2: approve. One canonical layout, no separators, no comments and one parameter form fit the purpose clause and principle 1. The syntax is internally consistent as written. RFC 0103 still uses syntax this RFC removes, so 0103 must be revised to match.
