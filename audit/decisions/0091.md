# RFC 0091: Text slicing without allocation

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 2/5 approve, need 0.6667
- approve 2, reject 3, abstain 1

## Votes
- designer-min: reject. The Cost section pays for a new built-in, a reserved name and a placement rule with only prose deferral, not a language construct, which breaks the rule that every addition names a removal. TS3 makes a slice a view, which is neither a literal nor a copy, so it contradicts the invariant in RFC 0035 TX11 that this RFC does not amend. I would approve if it names a core-spec removal of at least the same token count and amends TX11 to allow views, or makes slices copies.
- designer-safe: reject. TS2 returns the empty text for any bad range, so `text_slice("hi", 1, 0)` and `text_slice("hi", -1, 1)` succeed silently and hide the off-by-one error the Alternatives section says clamping hides. Approve if the Alternatives section states this cost and why an empty result is still preferred to a trap, and if the slice-range test is marked as showing the masking, not as correct behaviour.
- impl-1: reject. Reject now, resubmit after the first compiler merges. (1) architecture/ROADMAP.md, M2b, says no new RFC is proposed before the first compiler is on main, and this one says it was proposed anyway; the RFC itself asks the orchestrator to decide. Slicing has been drafted and rejected five times (0007, 0028, 0030, 0042, 0046), so a debate with no compiler to test it is the guess the roadmap warns about. (2) The design picks a slice as a view. RFCs 0007, 0028, 0030 and 0042 rejected that, and this draft never says why the earlier reason no longer holds. Its safety rests on every Text pointing at static data, which RFC 0035 TX11 does not state: TX11 says a running Text value is a literal or a copy of one, and a view is neither. (3) TS6 says a slice may appear 'wherever a text literal may', but its list leaves out `<`, which RFC 0037 (accepted) allows on Text. The list and the prose disagree. The checks I could run by hand all hold: the outputs of slice, slice-whole, slice-range, slice-view and slice-equal match TS2 and TS3, and the empty-result rule matches RFC 0035 text_byte's -1 precedent. The problems are fixable in a resubmission: state the view rule against TX11, explain why the earlier view rejection no longer applies, and fix the TS6 list.
- tester: approve. Checked against RFC 0035 (TX2, TX4, TX5, TX9, TX11), RFC 0020 (F6, E10, T3, E3, TR1), RFC 0046 and 0089 (both rejected), and the SPEC section 9 checklist wording. The cited clauses exist and say what the draft says. The rule TS2 is total and defined, so principle 7 holds, and the function has no effects, so principle 3 holds for it. Every test expectation I re-derived from TS2 and TS3 is correct: slice 1..3 of hello is el, 1..4 of hello gives 101 at index 0, abc 0..2 equals ab, and every out-of-range case gives length 0. Caveats I would want addressed in a later revision, not blocking: (1) an empty result on a bad range is a silent failure. The draft rejects clamping for hiding off-by-one errors, and the empty result hides them the same way, so TS2 should say why that is acceptable; this is open question 3. (2) The name text_slice is a full word, and principle 8 asks for short names unless measurement shows fewer model errors; no measurement or tokeniser count is given. (3) Test plan claims TS4 coverage, but no test checks evaluation order, since no argument has an effect. (4) No test for the empty-text input case, text_slice("", 0, 0). (5) RFC 0035 is accepted but conformance/ holds only kernel and lex tests, and no text_len or text_byte exists in the compiler here, so the new tests would fail until 0035 is implemented. That is a finding for the orchestrator, not a reason to reject this RFC.
- user-1: approve. As a user I can follow the rule: out-of-range gives an empty text, with no trap and no new error code, which fits principle 7 (every program has one defined result). Caveat: spec/card.md does not mention text_slice yet, so I checked nothing about its behaviour beyond this RFC text. A silent empty result may hide off-by-one bugs from users; the card should say so plainly.
- user-2: abstain. I could only read the RFC summary, not the full text or the core spec. The spec card has no text functions at all, so I cannot check `text_len` or the existing text surface that `text_slice` would join, and I cannot test the new call. The summary's choice to return an empty text for a bad range, rather than trap, is defined behaviour, but it can hide index bugs from a user who has no diagnostic to read. I want the full RFC and a card entry before I approve.
