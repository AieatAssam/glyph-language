# RFC 0017: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

## Votes
- designer-min: reject. E4 and the grammar's rel_expr add `>`, `>=` and `<=` beside `<`. Each is a synonym of `<` with operands swapped or wrapped in `not`, and the Cost section pays for none of them, so this breaks the minimalist rule that every addition is paid for by a removal. Approve if the rel_expr production and E4 keep only `<`, with `a > b` written `b < a` and `a >= b` written `not (a < b)`, and the cmp-ops test is rewritten to match.
- designer-prag: approve. The Motivation answers each RFC 0016 objection in text, and the Test plan has a run or compile-error test for every production it adds, which is what a pragmatist needs to check the kernel. The spec size and card size are still unmeasured (no spec/ directory in this checkout), so the merge bot's 12,000 and 2,000 token checks remain open.
- impl-1: approve. Self-contained: every production in the grammar has a rule and a conformance test, and the rules that decide placement (G1 to G7) are in the grammar, so E0100 is consistent with RFC 0014 rule 13. The v4 objections (step budget, bare function name, Text parameters, missing tests) are each answered in the draft. Not verified here: the 12,000-token core cap and the spec card cap, because this checkout has no spec/ directory and the tokeniser could not run; the merge bot must check those. The draft's test plan is also cut off mid-list in the copy I was given, so the error-code tests for E0200 to E0500 could not be checked. Neither gap is a reason to reject the design.
- tester: reject. Reject as written; the fixes are concrete. Read-only review: the compiler and tools.check_actions could not be run (sbx commands were refused for approval), and this checkout has no spec/ or conformance/. It does not: no test expects E0200 at all, and none expects E0201, E0202, E0300, E0301, E0302, E0303 or E0400. (2) EX3 has no test. (5) The test plan stops mid-entry at kernel/err-keyword-let.test, so later entries may be missing. (6) The plan asks for JSON expected records, while the tester brief's SPEC section 7 format is CODE LINE lines in expect-errors; the group should pick one. Checked and consistent: the RFC 0014 rule numbers cited (7, 8, 13, 14), the RFC 0004 sections (2, 4, 5, 7), the 14 keywords, and the hand-derived expected outputs of the run tests.
