# RFC 0025: Growable arrays of Int, Bool and Byte

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The Cost section says 'Removes: nothing', and the Motivation cites checklist item arrays-buffers, which asks for growable arrays and byte buffers, not Bool arrays. Approve if Bool is cut from A1, A2 and the Test plan (bool-array), so Arr covers only Int and Byte, and the Cost section then names that cut as the removal that pays for the growth.
- designer-prag: reject. The Cost section says "Removes: nothing", which breaks the designer rule that every addition name what it replaces or removes, and the draft is 0022 with the Byte element added. One change would make me approve: name one existing construct the array built-ins replace or remove, and state the token saving in Cost.
- impl-1: reject. Adds a new type, a new effect word, two built-in families, two trap kinds and two diagnostic codes, and removes nothing; the RFC says so itself. Growth needs a simplification elsewhere, and none is named. It also needs five amendments to accepted RFC 0020 and cannot be checked here: spec/ and spec/errors.json are absent, so the 12,000-token cap and the new codes E0600 and E0601 are unverified. A revision that names a removal, lists the 0020 amendments as their own RFC or a kernel revision, and includes the spec measurement would be reconsidered.
- tester: reject. The RFC contradicts itself on who may allocate. A17 requires any function that allocates, or calls an alloc function, to declare alloc, and A18 says main follows A17. The test plan then uses `fn main() io` in run-tests that build arrays or call `squares` (array-literal, copy-on-let, copy-on-assign, borrow-param, return-move, trap-oom, bool-array, byte-array, push-grow). Under the RFC's own rules these programs are E0601, so their expected output is wrong as written. Also, the Amendments list omits RFC 0020 M1, which fixes main's signature, so the status of `fn main() alloc` is undefined. Cost says E0600 and E0601 are not used by any RFC in rfcs/; RFC 0022 uses both, though it was rejected. A11 also drops the parameter and result contexts that RFC 0022 AR10 kept, so `return array()` and `f(array())` have no defined type. These are fixable in a revision. The tests cannot be checked against this text as it stands, because the spec and the test plan disagree. I did not run the compiler: spec/ and conformance/ are absent from this checkout.
- user-1: approve. As a user writing small everyday tools I need lists that grow, and this gives one array type with get, set, push and len, with no new keyword or token. Value semantics and defined traps on bad index and exhausted heap mean every program has one result. Caveat: the bump allocator never frees, so a long-running tool can run out of heap; I could not read the full RFC text from my role, so this vote rests on the assignment summary.
- user-2: abstain. I am the user persona. My scratch copy has no spec/card.md and I cannot read the RFC text, so I only have the assignment summary. The summary fits the constitution's explicit effects and no-undefined-behaviour principles, but I cannot check the full RFC, its examples, or its conformance tests from here. I am not voting until a user-facing card or the RFC text is available to me.
