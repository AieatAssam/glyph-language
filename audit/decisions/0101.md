# RFC 0101: Diagnostic style

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 3/5 approve, need 0.6667
- approve 3, reject 2, abstain 1

## Votes
- designer-prag: approve. Matches the accepted baseline: spec/card.md, spec/core/diagnostic.md and compiler/stage0/src/kernel/types.ts all use status 1 and the hyphenated trap kinds, and the measured saving is 62 core tokens with one token per record. Owner confirmation of the reversed 2026-11-20 message ruling and of exit status 1 (Open questions 1 and 2) must come before merge.
- designer-safe: reject. As written it respells every code (E0006 to E6) and expects `let let` to give E100, where RFC 0102 gives E0003 and keeps E0006, so both cannot be accepted. Would approve if its codes and the `let let` expectation match RFC 0102 (or 0102 is amended in the same batch and named), and the owner confirms the removal of the message checker in open question 1.
- impl-1: approve. Approve the record and trap design. It keeps code, span and fix, drops keys that can be derived, and matches the constitution's principle 4. It cannot land as drafted: its code spelling (E6) conflicts with 0102 (E0006), and its trap line (status 1, hyphenated kinds) conflicts with 0103 (JSON line, status 3, spaced kinds). Owner must confirm open question 1 (message checker) and open question 2 (status 1 for a failed compile) before merge.
- tester: reject. The trap part matches the repo: spec/core/diagnostic.md and spec/card.md give status 1 and a plain `trap: <kind>` line, and RFC 0103 contradicts both. But the RFC cannot be accepted as drafted. It respells codes to E6/E100, while RFC 0102 and RFC 0103 use E0006/E0100 and the repo's errors.json uses E0xxx. Its test diag/v3-record-code expects E100 for `let let`, where RFC 0102 rule G3 gives E0003. It removes message text, which reverses the owner's 2026-11-20 ruling on the message checker (its open question 1). It also calls RFC 0050 superseded, while RFC 0103 calls it accepted. Revise: keep E0xxx codes, follow the owner ruling, and settle the RFC 0050 status first.
- user-1: abstain. The code-and-span format is coherent by itself, but it contradicts RFC 0103 on traps: 0101 says a trap is a plain line `trap: <kind>` with exit 1, while 0103 says a JSON line `{"trap":"K"}` with exit 3. One of them has to change before I can vote. As a user I also lose the message text the current card gives, which I would need to understand an error I have never seen.
- user-2: approve. Structured diagnostics with a stable code, a byte span and an optional fix fit principle 4. Conflict to fix: the trap line here is plain text ('trap: <kind>') with exit status 1, but RFC 0103 makes a trap one JSON line with exit status 3. One of the two must change.
