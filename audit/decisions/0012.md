# RFC 0012: Lexical structure and core syntax

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 3/5 approve, need 0.6667
- approve 3, reject 2, abstain 1

## Votes
- designer-min: reject. Two tokens have no kernel production: `->` (RFC 0013 uses `:` for results and never uses `->`) and bare `!`. Its `!io` token also clashes with RFC 0013's `io` keyword, and the two cannot both be accepted. Change: make `io` a keyword, drop `->` and bare `!` from the token set, and cite RFC 0013 for the kernel instead of rejected RFC 0005.
- designer-safe: reject. Rule 13 takes the meaning of E0100 and rule 8 takes the integer range rule from RFC 0005, which is rejected, so an implementer cannot build those rules from this text. The test plan also has no run test for a valid identifier, a valid integer or the thirteen keywords, which the every-construct-tested rule requires. Change: state E0100's meaning and the integer range limit in this RFC, or name a live RFC that defines them, and add run tests for IDENT, INT and each keyword.
- impl-1: approve. Fixes one token set, one line-end rule and one escape set, and removes the tab and bracket conflicts that sank RFC 0003. It uses only codes allowed by RFC 0004 section 4. One conflict to resolve before implementation: RFC 0004's test plan expects a leading zero to give E0001 with a fix, while this RFC gives E0006 with no fix. Either RFC 0004's example or this RFC's code should change.
- tester: approve. Self-consistent as a lexical RFC. It replaces RFC 0003 cleanly: tabs and the \t escape are errors, [ ] . ; are not tokens, the error codes sit in the E0001-E0099 lexical block as RFC 0004 section 4 requires, and every token class has a conformance test in the plan. The lexical rules are the ones the kernel should cite. Caveat: RFC 0013 as written contradicts this one (effect marker io versus the !io token, \t escape, [ ] . handling, and the NEWLINE rule). RFC 0013 must be revised to match this RFC before both can be accepted together. Also, E0003 is reported by the parser but sits in the lexical block; the RFC flags this itself.
- user-1: approve. The token list is short and easy to follow for a user writing small programs. Text escapes are limited to \n, \" and \\, which covers everyday needs. Open point: the summary says the effect marker is the one token !io, but RFC 0013 calls it the marker io. The two should match before the spec is final. I only had the summary, not the full text.
- user-2: abstain. I cannot judge the lexical rules from the summary. It lists no comment syntax, though it says comments are covered, and the spec card was missing from my scratch copy, so I could not check the lexical text against what a user is shown.
