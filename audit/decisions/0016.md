# RFC 0016: Kernel: integers, booleans, bindings, functions, conditionals, loops, text output

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 2/5 approve, need 0.6667
- approve 2, reject 3, abstain 1

## Votes
- designer-min: reject. EX3 defines an example step as a function entry or a while evaluation, but TR3 counts only while evaluations and says calls are not counted, so the claim that examples run with the same semantics does not hold. Make EX3 count only while evaluations (or state in TR3 that calls count too) and I would approve.
- designer-prag: approve. TR1 to TR3 give every run a defined result (overflow, divide-by-zero, stack-exhausted, step-exhausted), and Motivation answers each RFC 0015 objection by pointing at the text. The gap in Open question 3 (naive recursion such as fib(60) finishes too slowly without trapping) is real, but the RFC states it and it sits outside this kernel's contract. The leading-zero conflict is between accepted RFC 0014 rule 8 and RFC 0004's diag/fix-present test, not in this RFC.
- impl-1: reject. Reject as drafted. The draft is close, but two normative rules conflict. (1) F6 and the err-fn-value test say a bare function name used as a value is E0100. The grammar accepts a bare IDENT as a primary, and accepted RFC 0014 rule 13 defines E0100 as a token the grammar does not accept, so an implementer cannot satisfy both. Name the code the checker should use, such as E0301 or E0200. (2) EX3 says an example step is a function entry or a while evaluation and that examples use run-time semantics. TR3 says calls are not counted, and the Alternatives section rejects counting calls. The 10000000-step example budget therefore has no single meaning. Fix these two and I will approve. The test gaps (no test for E4 non-Int comparisons, E5 non-Bool operands, or the combined `: R io` form in F1) are minor and can be added as new tests.
- tester: reject. Reject as drafted. (1) Hard constraint: every grammar production needs a conformance test. The test plan has none for the `or` operator, `>`, `>=`, the parenthesised form `( expr )`, the `Bool` type, or a `Bool` parameter (`ptype`). The RFC's claim that every production is exercised is false, so the coverage script would fail. (2) The test kernel/err-fn-value.test expects E0100 for a function name used as a value, but the grammar's `primary` accepts a bare IDENT, so this is not a syntax error. E0100 is the syntax code under RFC 0014 rule 13, and the diagnostic table gives unknown-name cases to E0301. (3) EX3 counts function entries as steps for examples, but TR3 says calls are not counted at run time. The same program can then pass `check` and behave differently in `run`. (4) Open question 3 accepts that a finite but very slow program, such as naive fib(60), has no practical result. This is a judgment for reviewers, not a blocker on its own. Revise to cover the missing productions, make the E0100 test and EX3 agree with the grammar and TR3, and this can be voted again.
- user-1: approve. As a user I can judge only from the summary; the full RFC text is not in my scratch copy. The summary gives defined results for overflow, division by zero, and call and loop exhaustion, and file-level examples the compiler runs, which covers the constitution's no-undefined-behaviour and examples rules. My concern is that Text can only be bound, assigned and printed, so everyday text work will wait for later RFCs. I approve the kernel as a minimal base, and I ask that the stdlib RFC add text operations next. I could not check the lexical rules, which come from RFC 0014 and are not in my copy.
