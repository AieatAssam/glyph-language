## Votes
- designer-min: reject. TX4 makes text_cat and text_slice allocate and text_byte and text_slice trap, but their signatures show neither, which conflicts with constitution principle 3; TX11 names out-of-memory with no heap limit, so principle 7 has no defined result. The estimated 330-token cost removes only one sentence, against the rule that growth needs a simplification; approve if allocation is shown in the signatures, the heap limit cites one accepted rule, and a named removal pays for the cost.
- designer-safe: reject. TX4 says `text_cat` and `text_slice` allocate, but their signatures in the table, `(Text, Text) -> Text` and `(Text, Int, Int) -> Text`, do not show it, and constitution principle 3 requires allocation to be visible in the signature. Change that would make me approve: give those two rows an allocation effect in the signature column, and say in Cost how spec/card.md shows it.
- impl-1: reject. Reject as drafted. (1) Milestone: architecture/ROADMAP.md M2b says no new RFCs are proposed until the first merge puts a compiler on main, and the draft itself says it is proposed only because the assignment asks for it. Nothing in this checkout shows that merge has happened. (2) Constitution principle 3 requires allocation to be visible in the signature, but text_cat and text_slice allocate while their signatures (Text, Text) -> Text and (Text, Int, Int) -> Text show nothing; the draft does not address this. (3) Cost says the placement and operand errors use E0200 'already in the table', but spec/errors.json has no E0200 (it lists E0001, E0005, E0006, E0010, E0100, E0500), and the constitution requires every code to be catalogued. RFC 0029 #72 already flags this gap. (4) E3 and E4 are amended, but the draft does not list RFC 0020's table row err-text-op (print("a" == "b") is E0200) as superseded, so the amendment contradicts an accepted test row without saying so. The core design (byte indexing, byte-wise ordering, copy slices, two trap kinds) is reasonable and could be resubmitted once the milestone is met and items (2) to (4) are fixed.
- tester: reject. Three problems, the first of which the merge bot would enforce regardless of votes. (1) Constitution principle 3 says whether a function can allocate or fail must be visible in its signature. TX4 gives text_cat and text_slice the signatures (Text, Text) -> Text and (Text, Int, Int) -> Text, and says in the Behaviour column that they allocate. The signatures do not show it, and the RFC adds no allocation marker. Traps are an accepted exception under RFC 0020 open question 1, but allocation is not a trap, and principle 3 names it separately. (2) Principle 7 needs exhaustion to have one defined result. TX11 and the oom test depend on 'the heap has left', but no heap size is defined in the spec, the RFC, or RFC 0020, and SPEC section 9 leaves the memory model open. So the oom test's expected output cannot be derived from the spec, which the tester rules forbid, and the trap point is not defined. TX12 also refers to 'the current arena' without saying what an arena is or when it is released. (3) The RFC amends accepted RFC 0020 (T3, E3, E4, TR1), and RFC 0020's own motivation says the team does not amend accepted RFCs this way. Also, the roadmap's M2b rule (no new RFCs until the first merge puts a compiler on main) may or may not hold. This checkout has bin/glyphc and compiler/stage0, but I cannot confirm main from here. What is sound: the compare, slice, byte, and escape tests follow from TX4 to TX8, and I checked the TX7 byte-order examples. The fix is to state allocation in the signature or in a new effect rule, define the heap bound and arena release in the spec, and move the oom test to a spec-defined limit.
- user-1: approve. As a user writing text programs, I cannot do basic work without indexing, byte length, slicing, concatenation and comparison on Text, so this RFC addresses a real gap. I read only the RFC summary and spec/card.md; the card has no Text section yet, so I could not check the detailed design or the error codes. My approval rests on the summary's scope, which keeps code points, number formatting and builders out.

The summary covers what a parsing program needs (byte indexing, byte length, slicing, concatenation, comparison), so I would support it once the full text is checked by a reviewer who can read it.
