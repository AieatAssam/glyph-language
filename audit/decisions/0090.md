# RFC 0090: Growable arrays of Int and Byte with one owner and no implicit sharing

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 2/6 approve, need 0.6667
- approve 2, reject 4, abstain 0

## Votes
- designer-min: reject. The RFC adds about 800 tokens, six built-ins, two reserved words, an effect word, two traps, a code and thirteen rules, and its Cost section says 'Removes: nothing'. Approve if it drops at least one built-in, for example `copy`, which AR11 uses only in examples and which a loop of `arr`, `push` and `get` can replace, and names the removal in Cost.
- designer-prag: reject. Its Motivation says no benchmark finding supports it, and it adds about 800 tokens, six built-ins, two traps, a new code and an effect word with no measured need. It also uses `print` where the accepted kernel uses `put`. To approve: cite a benchmark finding that shows the need (for example, stage 0 lacking growable token storage), and align the output built-in with RFC 0085.
- impl-1: reject. Builds on RFC 0020 and RFC 0024, both superseded (by 0085 and 0086), and uses print, while, return and let on the superseded grammar. Its Byte element type should cite 0086. It adds about 800 tokens of core spec with no removal, and it proposes new code E0204 without an entry in spec/errors.json. The no-sharing rule (AR5 to AR8) is sound and worth keeping; resubmit it on the 0085 kernel with the removal named.
- tester: reject. Builds on RFC 0020 kernel-v8 and RFC 0024, which RFC 0085 and RFC 0086 have superseded. Its programs use print, return, while and example, where the accepted kernel has put, ret, wh and ex, so none of its run tests can be derived from the accepted spec. It cites Byte from RFC 0024 without the RFC 0086 amendment. It adds an E0204 code that is not yet in spec/errors.json. The alias rules (AR5 to AR8) are coherent on paper, but the RFC cannot be tested as written. Reject; resubmit on RFC 0085 with put, ret, wh and ex, and cite 0086 for Byte.
- user-1: approve. Gives one growable array type with short names (arr, len, get, set, push, copy) and an explicit alloc effect, so allocation is visible in signatures. The no-alias rules (bind only when local, read-only parameter views) keep the meaning local and avoid shared mutable handles. Out-of-range access and heap exhaustion are defined traps, and the one new diagnostic, E0204, is catalogued. The bump heap never frees, so long-running programs will grow until they trap; this is accepted as the simplest defined behaviour for now.
- user-2: approve. Growable arrays of Int and Byte are the main thing my data-modelling programs need. The single-owner rule and read-only parameter view make the aliasing behaviour clear from the text. Never-freed storage is a real limit for long loops, but it is stated openly and traps are defined.
