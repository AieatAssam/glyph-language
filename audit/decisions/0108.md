## Votes
- designer-min: reject. Makes more than one decision: its Scope lists code spelling (S1), record keys (D1-D5), the explain command (D7), compile exit status (X2, still open question 2), the trap line (T1-T4) and the runner rule (R1). The record counts do not reproduce: the counter gives 32 tokens for the E6 record with fix and 59 for the current form, not 64 and 115, so the saving is 27 per record, not 51. Approve if split into one RFC for records and explain, one for the trap line and exit status, and one for the spelling change.
- designer-safe: reject. - impl-1: approve. The decision is right against the purpose clause. Dropping the leading zeros from every code, and dropping message, file, line, column and severity from records, saves tokens in every record and in the spec. A message needs no record field, because RFC 0050 already removed message, file, line and column from records, and the catalogue carries the message. The trap line follows RFC 0085 TR1 and RFC 0105 TR1, which resolves the RFC 0050 contradiction. Notes for revision, none of which changes the decision: (1) The token figures do not reproduce. I counted the v6 record with fix at 32 tokens (draft says 64), the current-format record at 59 (draft says 115), and spec/core/diagnostic.md at 502 (draft says 677). The direction holds, but the draft should restate its figures from the counter. (2) Line references are off. _matches is at conformance.py:168, not 147 or 154, and the defect it describes is real: line 175 passes when expected has no fix, whatever the actual record carries. R1 fixes that. (3) R1 and the trap substring match are owner work, so diag/v6-no-fix proves nothing until R1 lands. Open question 2 (exit status 1 for a failed compile) should be confirmed by the owner before the implementing PR.
- impl-2: reject. Reject: the RFC makes more than one decision. It changes the record keys, renames every code's spelling, rewrites the catalogue fields, adds the explain command, sets the exit status (X2, which open question 2 says is still open), rewrites the trap line, and changes the runner (R1). Each can be judged alone, and a defect in one would sink the rest. Measured with the protected counter: the E6 record with fix is 32 tokens, and the four-digit E0006 form is 33, so the code rename saves 1 token per record, not the 51 the RFC cites. I could not reproduce the 115-token and 64-token figures because the draft does not give the exact strings. The cross-reference to conformance.py line 154 points at the JSON parse in _diagnostics; the fix rule is at line 175 of _matches. The one change that would earn approval: split into (a) record keys, code spelling and the explain command, and (b) exit status and trap line, each with its own open question. Keep R1 in its own RFC for the owner.
- tester: approve. It is fewer tokens than RFC 0050's record, and it is buildable: each key, the code blocks, the trap line and the exit statuses are stated. I checked the runner claim: `_matches` in tools/check/conformance.py (line 172) only checks `fix` when the expected record has one, so an extra fix passes. R1 fixes that; the test diag/v6-no-fix is written to catch it once R1 lands. Notes for revision, not reasons to reject: (1) The token figures do not reproduce. My count of a v6 E6 record is 32 tokens and of a current-format E0006 record (with file, line, column, message, severity) is 59; the RFC says 64 and 115. The direction and rough saving hold, but the RFC should cite the counter output it used. (2) Open question 1 is a real dependency: if the owner reads the .gl-suffix ruling as binding records, the message stays and this RFC needs a rewrite. The RFC's reading is stated and reasonable.
