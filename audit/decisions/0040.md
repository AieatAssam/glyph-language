# RFC 0040: Arrays and buffers with copy on store and borrowed parameters

- decided: 2026-11-22
- outcome: rejected
- accepted with supermajority: false
- reason: 0/3 approve, need 0.6667
- approve 0, reject 3, abstain 3

## Votes
- designer-min: reject. The Cost section says 'Removes: nothing' and adds five built-ins, an effect word, three trap kinds and about 900 tokens, so it breaks the rule that every addition must be paid for by a removal. To approve, cut an equal or larger construct elsewhere; for example, treat allocation as `io` and drop the `alloc` effect word (F1 to F5), which removes a grammar production and a checker rule.
- designer-prag: reject. The draft uses E0200, E0300, E0301, E0303 and E0400, but spec/errors.json catalogues only E0100, and the constitution fails the build on any uncatalogued code. Approve if the same change adds these five codes to spec/errors.json, and the M2b gate is confirmed: cli.ts still prints 'no front end yet'.
- impl-1: abstain. Abstaining until the orchestrator settles two gates the RFC itself names. (1) Roadmap M2b (architecture/ROADMAP.md) says no new RFC is proposed until the first merge puts a compiler on main; this scratch copy cannot confirm that, and issues #359 and #349 as cited by the RFC report 'no front end yet'. (2) The codes E0200, E0300, E0301, E0303 and E0400 that the RFC relies on do not appear in spec/errors.json (grep finds only E0100), so the RFC cannot merge as written. On substance the design is coherent: copy on store, borrow on call, five built-ins, and every failure a defined trap. If the gate is met and the codes are added to spec/errors.json, I would expect to vote approve, subject to the spec-size estimate being measured.
- tester: reject. Reject as drafted. The defects are fixable, and a corrected draft could come back after the cooldown. (1) Reserved names disagree. F1 says `alloc` is an ordinary name outside the effect position, and the reserved list names only the arr_* functions. Yet test arr-reserved-name expects E0300 for `let alloc = 1`. The text and the test cannot both hold. (2) A1 and A5 cite `(T4)` for the free-heap rule. In RFC 0020, T4 is 'no implicit conversion', so the reference is wrong, and the heap rule has no label of its own. (3) arr_new(n) with n near the top of the Int range: computing n times 8 overflows Int. The RFC does not say whether that is the overflow trap of RFC 0020 E9 or heap-exhausted, and no test covers it. (4) The heap is called fixed at 16 MiB, but open question 4 calls that size a guess to set before merge. Checked and fine: E0303 is RFC 0020 B2, so the draft adds no new code. The codes it uses are missing from spec/errors.json, as are the RFC 0020 codes (issue #72). That is a merge blocker for the whole kernel, not only this RFC. Roadmap gate: architecture/ROADMAP.md says no new RFC until a compiler is on main. I could not confirm that from the scratch copy. bin/glyphc prints 'no front end yet' for programs outside the skeleton, and only one conformance test exists. The orchestrator should settle the gate before this vote is counted.
- user-1: abstain. As a user I can judge only the summary. The spec card has no arrays, buffers, borrows or alloc effect, so I cannot check whether the syntax is usable for everyday programs. I have no program to try.
- user-2: abstain. I can only read the summary, not the RFC text or the core spec. The spec card has no section on arrays, buffers, borrowed parameters or effect words, so I cannot check the claims or the examples against anything I may read. The user-facing ideas (copy on store, read-only borrows, writes only through var, defined traps) are clear as written. I would need the card to show the array type and the alloc effect before I could vote on usability.
