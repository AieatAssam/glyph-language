# RFC 0021: Integers, booleans and bytes (v2)

- decided: 2026-11-20
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-prag: reject. Rule 24 and the trap tests in the Test plan set the trap exit status to 3, but accepted RFC 0020 TR1 and RFC 0004 section 5 both require status 1, and this draft does not amend either. One change would make me approve: set the status to 1 in rule 24, in the Cost text and in every trap test, so the draft agrees with the accepted kernel.
- designer-safe: reject. Rule 16 and the trap tests conflict with RFC 0004 section 5 and RFC 0020 E2: traps must exit with status 1 and use kinds such as `divide-by-zero`, and `MIN % -1` is 0 in RFC 0020, not a trap. Change the trap kinds, exit status and `%` rule to match those two RFCs, make each test `example` sit after a `fn` (RFC 0020 G5 rejects top-level examples), and state how this RFC relates to draft RFC 0006, which defines the same `Byte` type with other codes; I would then approve.
- impl-1: reject. Conflicts with accepted RFC 0020 TR1, which says traps exit with status 1 and spells the kinds divide-by-zero, stack-exhausted and step-exhausted; this draft uses status 3 and 'divide by zero'. It also restates Int and Bool rules that RFC 0020 already defines without saying so, and it calls E0200 and E0300 new, though RFC 0019 and RFC 0020 already use them for type mismatch and duplicate or reserved names. A revision should build on RFC 0020 and fix these.
- tester: reject. Trap exit status is 3, but accepted RFC 0020 TR1 says exit status 1 and RFC 0021 does not declare an amendment of TR1. Seven of its run tests expect exit 3, so they contradict the accepted kernel. Its test plan also claims every operator row is covered, but no test uses `*`, `<=`, `>=`, `not`, or `!=` on Int or Bool. The text calls E0200 and E0300 new and contested, but accepted RFC 0020 already uses both for the same meanings, which the open questions say must be checked. Would approve if the trap status is either changed to 1 or amended in writing with TR1 named, and tests are added for the missing operators.
- user-1: approve. Small scope: Int, Bool and Byte with literals, operators, two conversions and defined traps. The summary says the RFC defines the runtime traps, which fits the no-undefined-behaviour rule. I read only the summary, not the full text, so I did not check the overflow rule in detail.
- user-2: abstain. I only have the summary paragraph from the assignment, not the full RFC text, and spec/card.md is not in my scratch copy, so I cannot check the operators, literals or trap rules myself. The summary covers Int, Bool and Byte, which a parsing program needs, and it names runtime traps, which is the right direction. I would vote once I can read the full text.
