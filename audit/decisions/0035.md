# RFC 0035: Text length, byte access and equality

- decided: 2026-11-22
- outcome: accepted
- accepted with supermajority: false
- reason: 4/6 approve, need 0.6667
- approve 4, reject 2, abstain 0

## Votes
- designer-min: reject. Adds about 150 core-spec tokens (two built-ins, a Text case of == and !=, two reserved names) and removes only two restated sentences from RFC 0020 T3 and E3, so it does not pay for itself under the rule that every addition needs a removal. To approve, name in Cost a removal from the core spec that covers the net growth; TX7 and TX8 can also name E0200 now, as RFC 0020 E3 and E4 already do, instead of waiting on issue #31.
- designer-safe: approve. TX2 gives both built-ins one defined result for every argument (`-1` out of range), and TX3 rules out traps and allocation, so principles 3 and 7 hold without deciding #64. The codes it uses (E0001, E0005, E0100, E0200, E0300) are already in spec/errors.json, and TX8's mixed-type case already falls under E3's E0200 wording.
- impl-1: approve. Small and total: two built-ins that cannot fail, no trap kind, no allocation, and no decision on issue #64 needed. Checked against the repo: the rules it amends (T3, E3, F6) and the codes it uses (E0001, E0005, E0100) match RFC 0020 and spec/errors.json. Non-blocking note: E3 already sends any operand pair without a matching type to E0200, so the mixed-type == case in TX8 does not need to wait for issue #31. The RFC could state E0200 now, with its test.
- tester: reject. The test plan contradicts RFC 0020 P1 and P2. P1 says print takes only Int or Text, and print(true) is E0200 (test err-print-bool). So the run tests text/equal.test, which expect print("ab" == "ab") to print true, have no valid expected output as written. Fix: print an Int inside an if, for example if "ab" == "ab" { print(1) }, and then the tests can be derived from the spec. The design itself is sound: the two functions are total and add no trap. Also, TX8 says the mixed-type code is unsettled, but RFC 0020 E3 already gives E0200, so that sentence is out of date. I would change to approve once the equality tests are fixed.
- user-1: approve. As a user writing small text tools, I need to check the length of a string and read its bytes, and I need to compare two strings with ==. This RFC adds exactly those and nothing else, and both functions are total with a defined result, which fits the no-undefined-behaviour principle. I could not check the details: spec/card.md has no Text section yet, so I cannot confirm the signatures or the == rules from the card.
- user-2: approve. As a parsing user I need to measure a text and compare two texts, and this RFC gives exactly that with total functions and no new heap values. I could only judge from the summary: the spec card does not mention Text, so I have not checked the exact semantics of text_byte past the summary.
