# RFC 0092: Growable arrays that live in one binding and are passed by reference

- decided: 2026-11-26
- outcome: rejected
- accepted with supermajority: false
- reason: 1/5 approve, need 0.6667
- approve 1, reject 4, abstain 1

## Votes
- designer-min: reject. The Cost section says 'Removes: nothing', but the minimalist rule requires every addition to be paid for by a removal. The 600-token growth figure is unmeasured, and the designer rules require measurement with the tokeniser. Would approve if it names one removal (for example, fold the `alloc` effect word into `io`, which drops a grammar slot and the E0100 ordering case) and reports a measured token count.
- designer-prag: reject. The Cost section says it removes nothing and adds about 600 spec-core tokens, but the team rules require growth to be paid for by a named simplification elsewhere, and the RFC names none. The 540-UNKNOWN benchmark table it cites is not in the non-heldout bench tree, and ROADMAP M2b bars new RFCs until a compiler is on main, which the RFC itself could not confirm. Would approve if Cost names an equal or larger spec-core cut and the RFC cites a benchmark finding that array programs fail.
- impl-1: reject. Two reasons. (1) Roadmap gate: architecture/ROADMAP.md M2b says no new RFC is proposed until the first merge puts a compiler on main, and that merge has not happened (the founding RFCs are still on one unmerged shared PR). The RFC itself says it could not confirm the gate. (2) Principle 8 of the constitution: the RFC chooses the longer forms (Arr(T), arr(T), alloc, and a separate effect word) without any measurement, and the constitution allows a longer form only when measurement shows fewer model errors. Its own brackets alternative is deferred behind a measurement it does not propose to run. Also, E0205 is not in spec/errors.json, which the check job requires. The rules themselves (single owner, one-call aliasing check, bump heap with traps) are coherent. A retry after the first compiler merge, with the token measurement, could be voted on fairly.
- tester: reject. Two problems. (1) Internal contradiction: AV3 says arr(T) is allowed only as the whole initialiser of a let or var binding and is E0200 anywhere else, but AV9 says `example len(arr(Int)) == 0` is valid, and the test plan's arr-empty-len (print(len(arr(Int)))) and arr-check-examples expect it to compile and print 0. As written, the RFC's own tests would fail under its own rules. (2) Roadmap gate: architecture/ROADMAP.md (M2b, current) says no new RFC is proposed until a compiler is on main, and its done criteria (40 passing conformance tests, grammar coverage) are not shown to be met. The RFC itself says the gate is unconfirmed. Principle 8 is also not supported by measurement: the RFC picks the longer forms (Arr(Int), arr(Int), index-out-of-range) and defers the shorter bracket form to a follow-up without a tokeniser result. A corrected draft that fixes AV3 and the tests, and shows the gate is met, can be re-proposed as a new RFC.
- user-1: abstain. I can only judge from the summary; the full RFC and the rule set were not available to me, and spec/card.md says nothing about arrays, so I cannot test the rules. Concern for the author: as summarised, an array cannot be returned, copied, or stored, so a common everyday task such as collecting lines into a list and handing them back from a helper would have no direct form. Please say how that case is meant to be written before this is approved.
- user-2: approve. Judged from the RFC summary only, since the RFC text is not in my scratch copy. For data-modelling and parsing programs, one growable Int or Byte array with a defined trap on out-of-range access is what I need, and the single-owner, pass-by-reference rule keeps the aliasing story small. Concern: the ban on returning arrays and storing arrays in arrays rules out nested records and parse helpers that build and return a list. A later RFC should say how to work around that.
